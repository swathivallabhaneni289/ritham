  <behavior>
    - weekStart for a Wednesday 10:00 returns that same week's Monday at 03:00 local.
    - weekStart for a Monday at 02:50 local returns the *previous* Monday 03:00 — that instant is still inside the previous Momentum week.
    - weekStart for a Monday at exactly 03:00:00 local returns that same instant (the boundary instant belongs to the week it opens).
    - weekStart for a Sunday 23:30 returns the Monday 03:00 six days earlier.
    - Locale independence: the same instant evaluated with a Gregorian calendar whose locale defaults to a Sunday-first week and one whose locale defaults to a Monday-first week returns the identical Date.
    - DST spring-forward (America/New_York, the March transition): a Monday instant in that week returns a boundary that is exactly the Monday 03:00 wall-clock time in that zone, and the returned value is identical whether evaluated at 09:00 or 21:00 that day.
    - DST fall-back (America/New_York, the November transition) and a Southern-Hemisphere transition zone (Australia/Sydney): same two assertions.
    - Non-existent-local-03:00 fallback: on a synthetic day where the hour-setting call cannot produce 03:00, two calls at different instants on that day still return the identical Date (the fallback is derived from the candidate day, never from the call instant).
    - weekEnd(startingAt:) returns exactly seven calendar days after the given week start, computed via calendar day arithmetic, so it stays correct across a DST week (that week is 167 or 169 wall hours, never 168 fixed seconds).
    - weekRange(containing:) lower bound equals weekStart and upper bound is strictly before the next week's start.
  </behavior>
  <action>
Create `MomentumWeek` as a public, uninstantiable `enum` namespace in a new
`RithamCore/Sources/RithamCore/Momentum/` directory. Import Foundation only — no SwiftData,
UIKit, SwiftUI or networking import may appear in any file under `Momentum/`.

Declare `public static let anchorWeekday: Int = 2` and `public static let anchorHour: Int = 3`,
with a doc comment stating that Gregorian weekday numbering is fixed (1 = Sunday) regardless of
locale, so Monday is always 2 — and that this value is deliberately NOT derived from the
calendar's own first-weekday preference, because Momentum's week starts on Monday for every
user unconditionally (03-RESEARCH.md Anti-Patterns).

Implement:
- `public static func weekStart(containing now: Date, calendar: Calendar) -> Date`
- `public static func weekEnd(startingAt weekStart: Date, calendar: Calendar) -> Date`
- `public static func weekRange(containing now: Date, calendar: Calendar) -> ClosedRange<Date>`
- `public static func nextWeekStart(after weekStart: Date, calendar: Calendar) -> Date`

`weekStart` computes `daysSinceMonday = (calendar.component(.weekday, from: now) - anchorWeekday + 7) % 7`,
subtracts that many days from `now` via `calendar.date(byAdding: .day, ...)` to get the candidate
Monday, then sets the hour to `anchorHour` on that candidate day. If the candidate boundary is
strictly after `now`, subtract seven days (the Monday-before-3am case) and return that.

CRITICAL correction to 03-RESEARCH.md's sketch (state this in the file's doc comment as a locked
deviation): the research sketch's failure fallback returns `now` itself. Do not do that — it
makes the function's result depend on the call instant rather than on the week, and plan 03-03's
reconciliation is keyed on this value being a stable per-week anchor (its idempotence requirement
would silently break on a DST transition day). Every fallback in this function must be derived
from the *candidate day*: fall back to `calendar.date(byAdding: .hour, value: anchorHour, to: calendar.startOfDay(for: candidateDay))`,
and if that also fails, to `calendar.startOfDay(for: candidateDay)`. Never force-unwrap and never
trap, matching `ConditionTagValidity.expiry`'s documented fail-safe discipline.

Take `calendar` and `now` as required, non-defaulted parameters on every function. Never read the
process-wide current calendar and never construct a current-instant Date inside this file — the
caller in `RithamApp` supplies both (03-RESEARCH.md Pitfall 3).

Also lock, in the file's header comment, the week-assignment rule: a session belongs to the week
containing its `startedAt` timestamp, matching the existing `HealthDataStore.loadCardioSessions(in:)`
/`loadLiftSessions(in:)` predicates, so a session started 02:50 Monday and ended 03:30 Monday
belongs to the *previous* week. This is a locked decision, not an implicit side effect.

Write `MomentumWeekTests.swift` as a `@Suite("MomentumWeekTests")` covering every behavior above.
Construct a dedicated `Calendar(identifier: .gregorian)` per test with an explicit
`TimeZone(identifier:)` value — never the process default time zone or calendar, which vary by
CI/simulator configuration and would make the DST fixtures non-reproducible. Build fixture dates
from explicit `DateComponents` against that same calendar.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user device clock / locale → Momentum domain | Device time zone, DST rules and locale first-weekday preference are attacker-uncontrolled but user-mutable inputs that determine every week boundary |
| derived Momentum state → user-visible motivational state | An incorrect boundary silently mis-credits a week, which in a gamified system is functionally a trust-boundary defect |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
