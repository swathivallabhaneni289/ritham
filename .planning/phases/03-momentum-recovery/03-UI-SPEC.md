# Phase 3 — UI Design Contract

> Visual and interaction contract for Momentum & Recovery. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Platform:** Native iOS (SwiftUI), same target/floor as Phases 1-2 (iOS 17+, iPhone only for v1, full Dynamic Type + Dynamic-Island/non-Dynamic-Island support). This phase has **no existing UI to extend** — it is new screens built entirely on top of Phase 1's design system (`RithamApp/Ritham/DesignSystem/`) and Phase 2's interim `HomeHubView`/`SettingsView` navigation pattern. Sourced from `03-CONTEXT.md`, `03-RESEARCH.md`, `docs/roadmap.md` §4, `.planning/REQUIREMENTS.md` (MOMENTUM-01–08, RECOVERY-01), and direct inspection of `01-UI-SPEC.md` plus every DesignSystem/Component file it governs.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — native SwiftUI, no npm/shadcn/component-registry tooling applies to this platform |
| Preset | not applicable |
| Component library | SwiftUI native controls only, extended by this app's own `RithamApp/Ritham/Components/` set (`PrimaryCTAButton`, `SecondaryCTAButton`, `ChoiceQuestionView`/`ChoiceChip`) |
| Icon library | SF Symbols |
| Font | SF Pro (system default) via Dynamic Type — no custom typeface |

**Theme:** unchanged from Phase 1 — fixed dark (charcoal-dominant) theme, not system-light/dark-driven.

**Tokens are inherited, not redeclared.** `RithamColor`, `RithamSpacing`, and `RithamType` (all in `RithamApp/Ritham/DesignSystem/`) are this phase's exact color/spacing/type source of truth — every value below is a *usage* of those existing tokens, never a new hex literal, new spacing constant, or new font role. This spec adds zero new tokens to any of those three files.

## Spacing Scale

Inherited from `RithamSpacing.swift` unchanged:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4pt | Icon gaps, inline padding |
| sm | 8pt | Compact element spacing, chip/button corner radius |
| md | 16pt | Default element spacing, standard screen margin |
| lg | 24pt | Section padding |
| xl | 32pt | Layout gaps |
| 2xl | 48pt | Major section breaks |
| 3xl | 64pt | Page-level spacing |
| minimumTapTarget | 44pt | Every icon-only or button control — non-negotiable, applies to every new Momentum/Recovery control (shield tap targets, chip options, flag actions) |

Exceptions: none new. The 44×44pt floor applies to the Recovery Week flag button, the injury-freeze flag/clear button, and every sleep-check-in/target-picker chip, same as every other control in the app.

## Typography

Inherited from `RithamType.swift` unchanged — exactly 4 roles, nothing renders below `label` (16pt):

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Display | 28pt | Semibold | 1.2× |
| Heading | 22pt | Semibold | 1.2× |
| Body | 17pt | Regular | 1.5× |
| Label | 16pt | Regular | 1.5× |

**New requirement for this phase — numerals:** `RithamType.numerals()` (`.monospacedDigit()`) is **mandatory** on every counting/ticking value this phase introduces: the current streak-week count, the shield count ("2 of 3"), the weekly progress count ("2 of 3 this week"), and every milestone week number (4/12/26/52). This is not new policy — `RithamType.numerals()`'s own doc comment already states "any ticking or counting value" — this phase is simply the first to have several such values at once, so it is called out explicitly rather than left to be rediscovered per-screen.

**Milestone-badge copy** (icon + week count + one competence line, per Claude's Discretion) uses `heading` for the week count and `label` for the one-line copy — no new type role, no smaller size for the badge's supporting line.

## Color

Inherited from `RithamColor.swift` unchanged. No new hex literal anywhere in this phase — every color decision below is a *usage rule* over the existing five tokens.

| Role | Value | Usage in this phase |
|------|-------|-------|
| Dominant (60%) — ink | `#0E100D` | Base field for every Momentum/Recovery screen |
| Secondary (30%) — paper | `#F5F3EC` | Body/label text on charcoal; the *unfilled* state of every progress element (shield outline, progress block outline, milestone-not-yet-earned state) at `paper.opacity(0.2)`, matching `RadialSessionTimer`'s existing track treatment |
| Accent — Coral (hot) `#FF5C39` | Primary CTA fills (Comeback Session CTA, "Log a session," "Done"), the *filled* state of a weekly-progress block, the *filled* state of an earned shield, the selected state of every chip (sleep check-in Great/OK/Poor, weekly-target 2-5 picker) — same reserved list as Phase 1, extended only with "filled Momentum progress/shield state" |
| Accent — Lime (volt) `#C6F24E` | **Unchanged reservation: ornament-only.** Zero use anywhere in this phase's progress, streak, shield, or milestone UI. `RithamColor.swift`'s own doc comment reserves volt for "the static ring-and-dot brand ornament... never a progress indicator" — this phase introduces several genuine progress/count displays and every one of them uses coral, never lime |
| Destructive | `#FF3B30` | **Stays unused in this phase**, same as Phase 1. No action in Momentum/Recovery is a delete/irreversible action — clearing an injury flag is a state change, not a destructive one (see Copywriting Contract). This is also a deliberate anti-threat-framing lock: **no red appears anywhere near streak, shield, or comeback-window state**, full stop — a missed week, an open comeback window, and a rebuilt streak all render in the same paper/coral/charcoal palette as a successful week, never in red |

**Accent discipline, extended for this phase:** coral now also means "this is live, real progress" (weekly-progress blocks, shield fill) — consistent with `RadialSessionTimer`'s existing precedent that coral, not lime, is the color that means "genuine data-bearing progress" app-wide.

**Contrast:** no new color pair is introduced (see Contrast Verification table in `01-UI-SPEC.md` — every pair used here, paper-on-ink, hot-on-ink, ink-on-hot, already has a measured, passing ratio). Any label drawn on a coral fill (a filled progress block's own accessibility label, a selected chip) uses `RithamColor.label(on:)` — never a hardcoded color — exactly as `ChoiceChip`/`PrimaryCTAButton` already do.

## Component Inventory

### 1. Weekly progress display — `MomentumProgressBlocks` (NEW component; resolves the ring-vs-blocks question)

**Binding decision, resolving a direct conflict in the source material:** the orchestrator's framing named "a ring/progress indicator." `01-UI-SPEC.md`'s own Ring-and-Dot section (locked decision #2) states: *"Sketch 002's carried-forward hard rule already forbids using a ring/badge/bloom shape as a progress or completion indicator anywhere in the app (data forms — bar strips, block grids — are used for Momentum instead, per that research)."* This sentence names Momentum specifically. **Decision: build a block-grid strip, not a ring**, for three concrete reasons:

1. It is the form the codebase's own prior research already named for exactly this feature, not a new exception requiring its own vetting (the way `RadialSessionTimer` had to justify itself against the same rule for a session timer's different use case).
2. `HomeHubView` currently renders with `DecorativeSurface.boundedHeaderOnly` (`ringAndDot: true`). A ring in that screen's content area would recreate the "two circular motifs in one viewport" collision `.calibrationSession` exists specifically to prevent — forcing a new `DecorativeSurface` constant and a change to `HomeHubView`'s own surface. A block strip requires neither; it is placed in the scrollable content area below the header, never the header itself, exactly as `RadialSessionTimer`'s own placement rule already requires for any genuine progress element.
3. The weekly target is a small discrete count (2-5), which a segmented block grid represents more legibly than a continuous arc — each block *is* one qualifying session, not a fraction of one.

**Shape:** `weeklyTarget` (2-5) `RoundedRectangle` blocks laid out horizontally with `RithamSpacing.sm` gaps, each `RithamSpacing.minimumTapTarget`-tall minimum (44pt) so the row reads clearly at accessibility text sizes without needing to shrink.
- **Filled block** (a completed qualifying session, including the week-one endowed session): `RithamColor.hot` fill, `RithamSpacing.sm` corner radius.
- **Unfilled block:** `RithamColor.paper.opacity(0.2)` fill (no stroke-only outline — a filled translucent block, not a stroke, reads unambiguously distinct from the filled coral block by both color *and* the outline/opacity combination, satisfying WCAG 1.4.1 "not color alone" without adding a second visual channel per block).
- A single `RithamType.body` + `numerals()` label above or beside the strip: **"This week: {n} of {target}"** — the row's accessibility label combines the count and the strip into one VoiceOver announcement ("This week: 2 of 3 qualifying sessions"), never two separate elements per `RadialSessionTimer`'s own precedent for combining a decorative visual with its numeric readout.
- **Never** uses `RithamColor.volt`. **Never** appears inside a `ScreenHeader` decorative region. **Never** sits adjacent to `RingAndDot` in the same viewport (this is structurally satisfied by placement alone, not by a new enforcement mechanism, since it never enters the header).

### 2. Shields — `ShieldRow`

Up to 3 shield icons (SF Symbol `shield.fill` for earned, `shield` outline-only glyph variant at `paper.opacity(0.2)` for not-yet-earned — the SF Symbol's own filled-vs-outline distinction is a second, non-color channel alongside the fill-color change, same WCAG 1.4.1 discipline as the progress blocks) laid out left-to-right, each at minimum 32pt (below the 44pt tap-target floor deliberately — these are display-only, non-interactive glyphs, not buttons; do not wrap them in a `Button`).
- Earned shield: `RithamColor.hot`.
- Not-yet-earned shield (of the 3 max): `RithamColor.paper.opacity(0.2)`.
- A `RithamType.label` + `numerals()` caption: **"{n} of 3 shields"**.
- **No consumption animation.** When reconciliation auto-consumes a shield to cover a missed week, the shield row simply renders its new (lower) count the next time the screen appears — no shrink, fade-out, shatter, or "spent" transition of any kind. This generalizes the "no reset-to-zero animation" rule from MOMENTUM-05: any animated loss of a game-like asset (a shield, a streak number ticking down) reads as punishment, exactly what this phase's framing rule forbids. A shield *appearing* (a newly-earned one) may use a plain, brief fade-in — never a celebratory burst/confetti/bespoke animation, per Claude's Discretion's "no bespoke celebration animation" rule extended to shields.

### 3. Milestone badges — `MilestoneBadgeList`

A simple vertical list, one row per milestone tier (4/12/26/52 weeks), each row: an SF Symbol icon (`rosette` for earned, `circle.dashed` at `paper.opacity(0.2)` for not-yet-reached — again, shape difference, not color alone), the week count at `RithamType.heading` + `numerals()`, and one line of competence-framed copy at `RithamType.label` (see Copywriting Contract for exact strings). No bespoke celebration animation, no confetti, no full-screen takeover on a milestone being newly reached — the row simply renders as "earned" the next time the screen appears, same reconciliation-on-read discipline as shields.

### 4. Comeback Session CTA — plain card, no wizard

Visible only when a `ComebackWindowRecord` is open (`claimedAt == nil && windowClosesAt > now`). A single `RithamColor.paper`-outlined card (matching `SecondaryCTAButton`'s outline treatment, not a full coral fill — this is informational-plus-action, not an alarm) containing: a `RithamType.body` line stating the window and its deadline, plus a `PrimaryCTAButton` that routes into the existing session-logging entry points (`flow.open(.cardioActivityPicker)` / `.strengthSession)`) — no new multi-step flow, no separate wizard screen, per Claude's Discretion. Never rendered with a countdown timer, a shrinking bar, or any time-pressure visual — a static "by {date}" statement only.

### 5. Recovery Week flag and injury/pain freeze — two visually and structurally separate controls

Per D-03 (RithamCore-level) and its direct UI consequence: these render as **two clearly separate rows/buttons on the Momentum detail screen**, never combined into one "Recovery" control, one shared icon, or one shared confirmation sheet.
- **Recovery Week flag:** a `SecondaryCTAButton`-style row, label "Flag Recovery Week," opens a plain `.alert` (not a sheet — this is a single yes/no decision, not a form) confirming the action; see Copywriting Contract for exact text. Shown as flaggable any week, any time, per D-12 (retroactive whole-week pause).
- **Injury/pain freeze:** a second, visually distinct `SecondaryCTAButton`-style row, label "Flag pain or injury," own `.alert` confirmation. Once active, the row's label changes to "Clear injury flag" (same row, now representing the clear action) with its own separate confirmation — never silently auto-clearing, never sharing a confirmation dialog with the Recovery Week flag.
- Both rows may appear on the same screen (the Momentum detail screen) but must never be merged into a single row, a single icon, a single enum-driven picker, or a single "Recovery" section header implying they are one mechanic. Two distinct labeled rows, two distinct icons (suggest `figure.walk.motion` or similar for Recovery Week vs. `bandage` or similar for injury — exact SF Symbol left to the executor, but must be two different symbols).

### 6. Sleep check-in — `SleepCheckInView`

A lightweight daily prompt, reusing `ChoiceQuestionView`'s existing chip pattern exactly (mode `.single`, three options: Great / OK / Poor — same selected-coral/unselected-paper-outline `ChoiceChip` styling already used everywhere else in the app, no new chip visual). An optional note field below (plain `TextField`/`TextEditor`, `RithamType.body`, no character-count pressure UI). No required interaction — the screen/prompt must be fully dismissible/skippable with zero visual consequence anywhere else in the app (see RECOVERY-01 UI Invariants below).

### 7. Recovery-aware suggestion display (RECOVERY-01) — plan-level banner only, never per-session

Per D-11 (RECOVERY-01 applies uniformly across the whole displayed plan, not a specific day): when the day's check-in is Poor, `RecommendationsView` shows **one plain-text banner at the top of the plan** (`RithamType.label`, `paper` color, no icon, no colored background) stating the plan has shifted lighter — see Copywriting Contract. This is the **only** UI surface this adjustment gets. Per RECOVERY-01's own invariants (restated as UI requirements below), the individual session rows in the plan carry **zero** differentiating marks.

### 8. Daily Movement Snapshot — `MovementSnapshotView` + Settings toggle

A separate, opt-in Settings entry (toggle) and its own plain calendar-style view (a grid of day cells, marked/unmarked per day with logged activity — no color beyond the existing paper/ink field, no streak-adjacent coral fill on this screen at all, since coral in this phase's vocabulary means "Momentum progress" and this screen must carry none of that association). See item 9 below for the toggle control decision.

### 9. Settings toggle for the Daily Movement Snapshot — `ChoiceChip` Yes/No, not a native `Toggle`

**Binding decision:** the app has zero existing `SwiftUI.Toggle` precedent anywhere in the codebase. A native `Toggle`'s on-state track is system blue by default; tinting it `RithamColor.hot` would put a white knob on a coral track — measured at roughly 2.8:1, which fails even the 3:1 non-text-contrast bar, and is exactly the "intuitive-but-wrong" default `RithamColor.label(on:)` exists to make unreachable elsewhere in this app. Rather than introduce a first-ever `Toggle` with an unverified custom tint, **this opt-in uses the same two-option `ChoiceQuestionView`/`ChoiceChip` Yes/No pattern already used throughout the app** (e.g. `DietPlanView`'s severity Yes/No/Not-sure question) — already contrast-verified, already the sanctioned binary-choice control. Label: "Show Daily Movement Snapshot," options "On"/"Off" (not "Yes"/"No" — this is a feature state, not a question answer).

### 10. Weekly-target picker — `MomentumTargetView`

Follows `WorkoutFrequencyView` exactly: `DecorativeSurface.flat`, a `ChoiceQuestionView` with `mode: .single` over the four supported values (2/3/4/5), same `ChoiceChip` styling, same `PrimaryCTAButton(title: "Done")` dismissal, same inline save-error text (`OnboardingCopy.Errors.savingFailed`) on failure. No new visual pattern — this is a direct reuse of an existing, shipped screen shape with a different value set.

### 11. Manual-vs-sensor session labeling (MOMENTUM-01)

Reuses the exact existing strings and styling verbatim — `RithamApp/Ritham/Cardio/Views/CardioHistoryView.swift:165`'s `Text(session.source.isSensorVerified ? "Sensor-verified" : "Manually entered")` at `RithamType.label`, `RithamColor.paper` (both branches identical styling — deliberately non-differentiating, no badge, no icon, no color distinction between the two labels; "labeled distinctly" means the *text* differs, not the *visual weight*). **Lift session rows show no verification label at all** in any Momentum history/combined view — `LiftSessionRecord` has no capture-source field (all lift sessions are manually logged), so a combined cardio+lift history list must render lift rows with zero label in that column, never a default "Manually entered" invented for a field that doesn't exist on that record type.

## Decorative Surface Assignments

Following `ScreenHeader.swift`'s existing `DecorativeSurface` rule ("any screen that collects, confirms, or blocks on health or age data stays flat") and Phase 2's own precedent of assigning surfaces case-by-case without amending Phase 1's onboarding-scoped nine-screen enumeration comment (Phase 2 added several new `.flat` screens — `DietPlanView`, `WorkoutFrequencyView`, `SettingsView` — without touching that comment, since it is explicitly scoped to onboarding screens, not a living whole-app registry):

| Screen | Surface | Rationale |
|--------|:---:|---|
| `HomeHubView`'s Momentum summary section | *(no change — stays `.boundedHeaderOnly`)* | D-08 adds a section to the existing hub; `MomentumProgressBlocks`/streak/shield summary render in the hub's existing flat content area below the header, never inside the header region itself |
| `MomentumView` (detail: progress, streak, shields, milestones, comeback CTA, Recovery Week/injury flags) | `DecorativeSurface.flat` | Launches health-adjacent actions (injury/pain flag) from this screen; flat keeps it consistent with every other screen in the app that touches self-reported health state, and avoids introducing a decorative header this information-dense screen doesn't need |
| `SleepCheckInView` | `DecorativeSurface.flat` | Collects a health self-report (sleep quality) — governed by the existing flat-for-health-data rule |
| `MovementSnapshotView` | `DecorativeSurface.flat` | D-09: deliberately plain, no streak/shield/target visual association of any kind — flat reinforces that this is the "quiet" counterpart to Momentum |
| `MomentumTargetView` (Settings) | `DecorativeSurface.flat` | Direct precedent match with `WorkoutFrequencyView`, an identical-shape Settings preference screen |

**Optional hygiene note for whoever implements this** (not a blocking requirement — Phase 2 did not do this either): `ScreenHeader.swift`'s `.flat` doc comment currently enumerates "exactly nine" flat screens scoped to Phase 1 onboarding. It does not need updating for this phase's new flat screens (the comment is explicitly onboarding-scoped, not a whole-app registry), but if a future phase decides to generalize that comment into a living registry, Phase 3 adds `MomentumView`, `SleepCheckInView`, `MovementSnapshotView`, and `MomentumTargetView` to it.

## RECOVERY-01 — UI Invariants (binding, testable)

These restate `03-RESEARCH.md`/`03-CONTEXT.md`'s D-05 seven invariants specifically as **UI requirements**, since several are easy to satisfy at the domain-logic layer while still failing at the presentation layer:

1. **No differentiating visual mark of any kind** on an adjusted (lighter) session vs. an original session in the displayed plan — no badge, no asterisk, no "lighter" tag/chip, no tint or color change on the session row, no icon. The only adjustment-related UI is the single plan-level banner (Component 7 above); individual session rows are visually identical whether or not the plan was adjusted.
2. **"Do the original session instead" is an equal-weight control**, never styled as a secondary, muted, or discouraged action (e.g. never gray-out, never smaller text, never below a "recommended" label on the lighter option). If both options are shown side-by-side, they use identical button styling (both `PrimaryCTAButton` or both `SecondaryCTAButton` — never one of each).
3. **Skipping the sleep check-in produces zero visual consequence anywhere in the app**: no red dot, no badge count, no "you haven't checked in" banner on `HomeHubView` or `MomentumView`, no grayed-out or dimmed state on anything. A skipped day is indistinguishable, app-wide, from a day where the check-in screen was never shown to begin with.
4. **The qualification bar never changes.** No UI anywhere shows a different "10 minutes" / "3 sets across 2 exercises" threshold depending on sleep check-in state — the qualifying-session bar is not sleep-dependent, and no copy anywhere implies it is.
5. A lighter suggested session that meets the bar shows the exact same "counts toward Momentum" treatment (progress block fill, session history entry styling) as any other qualifying session — no distinguishing mark there either.
6. The sleep check-in screen/prompt itself contains no shield or Recovery-Week-related copy or affordance — it is a single-purpose screen (Great/OK/Poor + optional note), with no button, link, or mention of shields, Recovery Week, or streak state anywhere on it.
7. No milestone, shield, or streak-count display anywhere reads differently based on sleep check-in history — the two systems (RECOVERY-01 and MOMENTUM-01–08) share zero UI surface beyond the one plan-level banner in Component 7.

## Copywriting Contract

### Framing rule (governs every row below)

Per `docs/roadmap.md` §4 and MOMENTUM-05: all copy is informational/competence-framed, describing what happened as a fact the user can act on — never threat-framed, never urgent, never punitive.

**Banned lexicon** — the following tokens/patterns must not appear anywhere in Momentum/Recovery-surface copy (source-grep test recommended, mirroring 02-13's "zero occurrences of X" pattern):

| Banned | Why |
|--------|-----|
| `lost` / `you lost` | Threat-framed loss language |
| `broken` (describing a streak) | Threat-framed |
| `don't lose` / `don't break` | Anxiety-inducing imperative |
| `reset` (describing streak/shield state going to zero) | Implies erasure rather than "rebuilt" framing |
| `zero` (describing the user's own count going back to it) | Same — "Week 1 of your rebuilt streak," never "back to 0" |
| `failed` / `failure` | Punitive |
| `expire` / `expires` / `expired` (describing the comeback window) | Countdown-of-doom framing; use "by {date}" instead |
| `countdown` | Same |
| `!` (exclamation point) anywhere in Momentum/Recovery copy | Urgency signal explicitly forbidden by the roadmap's own framing rule |
| `you missed it` / accusatory second-person framing of a miss | "a missed week" (neutral, matches MOMENTUM-04's own requirement text) is fine; "you missed it" aimed at the user is not |

**Allowed, neutral vocabulary:** "missed week" (as a factual noun phrase, e.g. "A missed week — log a Comeback Session by {date}"), "Recovery Week," "injury freeze," "comeback window," "rebuilt streak."
