`@MainActor public struct MomentumSummaryReader` — constructed with a `HealthDataStore` and a
`Calendar` (defaulting to the process calendar at this app-layer call site only; RithamCore's own
functions still take it as a required parameter). Implement
`public func summary(now: Date) throws -> MomentumSummary`:

1. Load the ledger and the two guardrail histories from the store.
2. Compute `isStreakLossProtected` via `MomentumReconciliation.isStreakLossProtected(tags:)` over
   `store.activeConditionTags(now:)` — reusing the shipped guidance catalog rather than a second
   list. Document that applying the currently-active protection to every week being reconciled is
   the deliberately forgiving direction: it can only ever protect a week, never punish one.
3. Compute the current week via `MomentumWeek.weekStart(containing:calendar:)` and the anchor for
   the endowed credit via `store.earliestSessionStart()` mapped through the same function.
4. Build the ascending list of fully-elapsed `MomentumWeekInput` values from the ledger's
   last-reconciled anchor (or the earliest session's week when the anchor is nil) up to but
   excluding the current week, fetching each week's sessions through the store's existing date
   range queries and setting each week's endowed credit via
   `MomentumTarget.endowedCredit(weekStart:firstSessionWeekStart:)`. Cap the number of weeks
   assembled at a documented upper bound so a store that has been idle for years cannot produce an
   unbounded fetch loop; when the gap exceeds the bound, fold the most recent bounded window and
   advance the anchor accordingly, documenting the tradeoff.
5. Build the current week's `MomentumWeekInput` the same way.
6. Call `MomentumReconciliation.reconcile(...)`, then persist the returned ledger via
   `store.saveMomentumLedger(_:)` — but only when the returned ledger differs from the loaded one,
   so an unchanged read performs no write at all.
7. Assemble and return the `MomentumSummary` from the reconciled ledger plus the current week's
   derived counts, with `recentSessions` built from the current week's cardio and lift sessions
   sorted by start descending.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| stored sleep signal → Momentum ledger | RECOVERY-01's invariants forbid any automatic effect; the read path must be provably write-free for guardrails and shields |
| repeated screen appearance → persisted ledger | Every screen appearance re-enters the reader; a non-idempotent write path corrupts state even with an idempotent pure fold |
| long-idle store → elapsed-week assembly | An unbounded fold over years of elapsed weeks is an availability risk on the main actor |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-3-02 | Tampering | `MomentumSummaryReader.summary(now:)` | high | mitigate | Persists the reconciled ledger only when it differs from the loaded one, and is pinned by `readingTheSummaryTwiceLeavesTheStoredLedgerUnchanged` asserting both ledger equality and unchanged stored row counts |
| T-3-08 | Elevation of Privilege | sleep signal to guardrail state | high | mitigate | No read path calls a guardrail write method; pinned by `readingTheSummaryNeverFlagsARecoveryWeekOrAnInjury` and `aPoorSleepCheckInNeverConsumesAShield`, both exercised with a Poor check-in stored |
| T-3-03 | Information Disclosure | `MomentumSummary` member set | medium | mitigate | No sleep member exists, pinned by a Mirror-based test, so no Momentum surface can render differently based on check-in history (RECOVERY-01 invariants 3 and 7) |
| T-3-10 | Denial of Service | elapsed-week assembly | medium | mitigate | The number of weeks folded per read is capped at a documented bound with the anchor advanced accordingly, so a long-idle store cannot produce an unbounded main-actor fetch loop |
| T-3-09 | Information Disclosure | `SleepCheckInRecord` | medium | accept | New health-adjacent self-report at rest inside the existing protected container; per D-01/D-04 it never leaves the device and is never added to the workout-plan request's three-field boundary |
| T-3-SC | Tampering | `RithamApp/project.yml` | low | accept | This plan adds no package dependency; the Package Legitimacy Gate is not applicable this phase |
</threat_model>
