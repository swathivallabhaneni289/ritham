<objective>
Build the shared components every screen in this phase composes: the screen scaffold, the primary
action button, the fixed-choice question component, and EXPLAIN-01's tap-to-expand glossary term.

Purpose: HEALTH-01's fixed-choice constraint is easiest to honour if there is exactly one question
component and it has no free-text mode — then no screen can accidentally introduce a text field.
Building the component once also means the twenty-plus question screens across the gate section, the
condition checklist, the severity follow-ups, and the eating-disorder follow-up become short
declarations rather than twenty hand-built layouts, each of which would be an independent opportunity to
drift from the spacing, contrast, and tap-target rules 01-UI-SPEC.md locks.

EXPLAIN-01's tap-to-expand belongs here for the same reason: reading the register from the environment
means changing it in Settings updates every definition in the app at once, with no screen holding its
own copy.

Output: Five composable components plus the register environment key, with tests for the fixed-choice
and glossary behaviours.
</objective>

  <action>
    Create `ChoiceChip`, a selectable control rendering one option. Selected state fills with
    `RithamColor.hot` and takes its label from `RithamColor.label(on:)`; unselected renders as an
    outlined control on charcoal with `RithamColor.paper` text. Both states hold at least
    `RithamSpacing.minimumTapTarget` in both dimensions. Expose selection through
    `accessibilityAddTraits(.isSelected)` so the state is conveyed to assistive technology and not by
    colour alone.

    Create `ChoiceQuestionView`, generic over an option type conforming to `Hashable` and `Identifiable`,
    taking a prompt string, an optional helper string, the options, a selection mode, and a binding.
    Define `enum ChoiceMode { case single, multiple(exclusiveOption: AnyHashable?) }`. In the multiple
    mode with an exclusive option supplied, selecting that option clears the others and selecting any
    other clears it — which is §1.3's None-of-the-above behaviour. Note in a comment that
    `ChecklistSelection` in core already enforces this invariant for the checklist specifically, and this
    component's job is to present it consistently, not to re-derive it; where a `ChecklistSelection` is
    the binding, defer to its `toggle`.

    This component must expose no free-text mode. HEALTH-01 forbids free text anywhere in this flow, so
    do not add a text-entry variant, an "other, please specify" affordance, or a `TextField` of any kind.
    Record that as a header comment stating that adding one would breach HEALTH-01, and that the sole
    numeric entry in the entire questionnaire is the age field, which the age screen implements directly
    with its own bounded validation rather than through this component.

    Lay out the prompt at the `body` role, the helper at the `label` role via `fineprint()`, and the
    chips in a layout that wraps rather than truncating, so long option strings remain fully readable at
    accessibility text sizes.

    Write `ChoiceQuestionTests` asserting the selection logic, extracted into a testable
    `ChoiceSelectionReducer` so the behaviour can be asserted without rendering: single mode replaces the
    selection; multiple mode accumulates; selecting the exclusive option clears all others; selecting a
    non-exclusive option while the exclusive one is selected removes the exclusive one; deselecting in
    multiple mode removes only that option; and that the reducer never produces a state holding both the
    exclusive option and another option.
  </action>
