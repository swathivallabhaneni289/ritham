<objective>
Build the design system 01-UI-SPEC.md locks: the four-token palette with its contrast rule, the
four-role type scale with its size floor, the spacing scale, and the band motif re-expressed as a custom
`Shape` that computes its geometry rather than porting a landscape SVG's coordinates.

Purpose: 01-UI-SPEC.md documents the portrait-crop problem as a real, computationally verified bug rather
than a hypothetical — sketch 003's polygon points were solved for a 1440 by 720 canvas, and slice-cropping
that composition into a roughly 390 by 844 portrait viewport keeps the middle and discards exactly the
flat margins that made room for text. Making the geometry a pure function lets that property be asserted
by a unit test at real portrait header sizes instead of checked by eye.

The typography floor and the contrast rule are both accessibility requirements with a cross-generational
justification, not stylistic preferences: 01-UI-SPEC.md ties the sixteen-point floor directly to
CROSSGEN-05, on the grounds that refusing an age-segmented mode also means refusing a small-type track
that only younger users are assumed to read comfortably. HEALTH-05's standing footer disclaimer is the
element most likely to be shrunk into fine print, so the floor is enforced in the type scale itself.

Output: One theme object, one type scale, one spacing scale, a tested band geometry, and a header that
reflows correctly at accessibility sizes.
</objective>

  <files>RithamApp/Ritham/DesignSystem/BandGeometry.swift, RithamApp/Ritham/DesignSystem/BandMotif.swift, RithamApp/RithamTests/BandGeometryTests.swift</files>

    - `.planning/phases/01-onboarding-safety-intake/01-RESEARCH.md` — Pattern 2 and Pitfall 1

  <action>
    Create `BandGeometry` as a pure struct with no SwiftUI dependency beyond `CGRect` and `CGPoint`,
    so its behaviour is unit-testable without rendering. It takes the band angle in degrees, defaulting
    to 57 to match sketch 003, and exposes:
    - `func bandEdges(in rect: CGRect, bandCount: Int) -> [(top: CGPoint, bottom: CGPoint)]` computing
      where each band boundary crosses the rect's top and bottom edges, derived from `rect.width` and
      `rect.height` at call time.
    - `func flatMarginFractions(in rect: CGRect) -> (leading: Double, trailing: Double)` returning the
      fraction of the rect's width that remains free of any diagonal band at every visible row, on the
      leading and trailing sides.

    Recompute these from the rect's own aspect ratio using the edge-crossing method sketch 003's README
    describes. Do not port sketch 003's solved figures of roughly 25 percent and 20 percent, and do not
    embed any coordinate traceable to its SVG — those were solved for a 1440 by 720 canvas and, per
    01-UI-SPEC.md, transferring them is a real verified bug rather than a hypothetical one. Add a header
    comment recording that any hardcoded numeric coordinate in this file is a defect, and that the only
    fixed input is the angle.

    Create `BandMotif: Shape` whose `path(in rect: CGRect) -> Path` delegates entirely to `BandGeometry`.
    The shape must contain no arithmetic on literal coordinates of its own. Expose a `band` index so a
    host can fill each band with a different palette token.

    Write `BandGeometryTests` asserting, at the real portrait header sizes this app renders — at minimum
    390 by 250, 393 by 280, and 430 by 220 — that: both `flatMarginFractions` values are strictly
    greater than zero, so a content-safe region exists on both sides at every tested size; the computed
    band edges stay within the rect's bounds; the geometry is deterministic across repeated calls with
    the same rect; scaling the rect's width while holding height constant changes the fractions, proving
    the computation actually depends on the rect rather than returning constants; and that supplying
    sketch 003's original 1440 by 720 rect yields different fractions than the portrait sizes, which is
    the direct assertion that the values were not ported.
  </action>

    `.welcome` with all four; `.boundedHeaderOnly` with the band motif and an optional ring for the
    register picker and the privacy explainer; `.calibration` with the band motif and ring; and `.flat`
    with all four false. Add a header comment carrying the inventory's closing rule verbatim in meaning:
    any screen that collects, confirms, or blocks on health or consent data stays flat charcoal, with no
    bands, no halftone, no arcs, and no mascot. Enumerate in that comment which screens must use `.flat`
    — age, dietary pattern, the consent halt, the teen partial-gate notice, the gate section, both
    clearance interstitials, the condition checklist, the eating-disorder follow-up, and the
    required-blocking message — so a later screen plan does not have to re-derive the mapping.

    Create `RingAndDot` as a static decorative view: one thin lime stroke ring with a single solid centre
    dot, drawn with `RithamColor.volt`. Per 01-UI-SPEC.md's binding rule it may only ever be a static,
    non-data-bearing ornament: it must never gain a second concentric ring, never fill or animate to
    represent a fraction, never serve as a progress, streak, or loading indicator, and never sit adjacent

    keeps it from reading as an Activity-Rings-style data widget. Give it no parameter that could carry a
    progress value, so the misuse is not expressible.

    Add the halftone and arc ornaments as simple decorative views bounded within the header region. Keep
