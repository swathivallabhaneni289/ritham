<objective>
Expose the consent domain over HTTP, add the delayed second confirmation email that makes the flow meet
the FTC's email-plus bar, and serve the Apple association file that lets the confirmation link open the
app instead of Safari.

Purpose: D-05 corrected requires two parent actions separated by a delay, because a single link click is
not "email plus" by the FTC's own description of the method — building it as one hop risks failing
LAUNCH-05, which gates public App Store submission. 01-RESEARCH.md's Environment Availability section
records that neither the backend nor the Universal Links domain exists yet and that there is no viable
client-only fallback for either, so provisioning them is part of this phase rather than an assumption.

Output: A running Go service with the five consent endpoints, the scheduler for the delayed email, and
the association file — all tested with `net/http/httptest` and no live network.

Language and dependency posture: Go per D-13, standard library only, continuing plan 01-02's choice. No
router package is introduced; `http.ServeMux` handles the routing this service needs.
</objective>

    Create package `httpapi` with a `Server` struct holding a `consent.Store`, an `email.Sender`, a
    `PublicBaseURL string`, a `Now func() time.Time` for deterministic tests, and a
    `SecondEmailDelay time.Duration`. Build routes on `http.ServeMux` using Go's method-and-path pattern
    syntax. No third-party router — `go.mod` must still declare no third-party module.

    Endpoints:
    - `POST /v1/consent` accepting a JSON body of `minor_profile_ref` and `parent_email`. Validates the
      email syntactically with `net/mail.ParseAddress`, creates a record in `StatePending`, issues an
      initial-link token with `token.DefaultInitialTTL`, advances state through
      `consent.Apply(current, consent.EventEmailSent)`, sends
      `email.BuildInitialConsentEmail` with a confirm URL of `PublicBaseURL` plus
      `/v1/consent/verify?t=<secret>`, and returns the record ID and current state. Never echo the token
      secret in the response body — it belongs only in the email.
    - `GET /v1/consent/verify` reading the token from the `t` query parameter. Looks the record up by
      token hash, redeems the token as `PurposeInitialLink`, advances via `EventLinkRedeemed`, sets
      `SecondEmailDueAt` to now plus `SecondEmailDelay`, and responds with a human-readable HTML page
      telling the parent a second confirmation email is coming and that consent is not yet complete. The
      state after this endpoint is `StateLinkClicked` and never `StateConfirmed` — that is the whole
      point of D-05's correction. Map the token sentinel errors to distinct, non-revealing responses:
      expired and already-redeemed produce a page offering a re-send, and malformed or not-found produce
      a generic failure page. Do not disclose which of the two occurred, and do not reveal whether a
      given record exists.
    - `GET /v1/consent/confirm` reading the second token from `t`, redeeming it as
      `PurposeSecondConfirmation`, advancing via `EventSecondConfirmationRedeemed`, and responding with a
      success page. This is the only endpoint that can reach `StateConfirmed`.
    - `GET /v1/consent/{id}/status` returning only the state string and, when awaiting, whether a second
      email has been scheduled. This is what the app polls. It must be read-only: it may never mutate a
      record and must never return the parent's email address, the token, or the minor profile
      reference. Returning the state alone keeps the response free of personal data.
    - `POST /v1/consent/{id}/resend` accepting an optional corrected `parent_email`. This covers the
      resend and edit affordance CONTEXT.md leaves to discretion, and it is also the recorded mitigation
      for the email-client link-prefetch problem 01-RESEARCH.md flags — a prefetch-consumed token must
      not permanently strand the parent. Invalidate the outstanding token for that stage by issuing a
      fresh one, re-send the appropriate email for the record's current state, and leave the state
      unchanged. Rate-limit per record to a small number of resends in a rolling window using an
      in-process counter, so the endpoint cannot be used to send unlimited mail to an address.

    Every state change goes through `consent.Apply`; no handler may assign a `State` value directly.
    Return the appropriate status code when `Apply` returns `ErrInvalidTransition` rather than silently
    proceeding.

    Create `cmd/consentd/main.go` reading `CONSENT_PUBLIC_BASE_URL`, `IOS_APP_ID`, `RESEND_API_KEY`, and
    `CONSENT_MAIL_FROM` from the environment, failing fast with a message naming any missing variable,
    wiring `email.NewResendSenderFromEnv`, `consent.NewMemoryStore`, and an `http.Server` with read,
    write, and idle timeouts set. Document in `README.md` that the in-memory store is not durable across
    restarts and that a durable `consent.Store` implementation is required before any deployment that
    real parents use — the interface exists precisely so that substitution touches no transition logic.

    Write handler tests with `httptest` and `email.FakeSender` and an injected `Now`: creating a consent
    sends exactly one email and leaves the record at `StateEmailSent`; the response body does not contain
    the token secret; verifying with the emailed token moves the record to `StateLinkClicked` and not
    `StateConfirmed`; verifying twice returns the re-send page and does not advance state; confirming
    with a second token from `StateLinkClicked` reaches `StateConfirmed`; attempting to confirm from
    `StateEmailSent` does not reach `StateConfirmed`; the status endpoint returns only the state and
    contains neither the parent email nor the token; the status endpoint does not mutate the record;
    resend issues a new token, leaves state unchanged, and refuses beyond the rate limit; and an
    invalid email address is rejected at creation.

  <action>
    Implement `Scheduler` in package `consent`, holding a `Store`, an `email.Sender`, a
    `Now func() time.Time`, a `PublicBaseURL string`, and a `Delay time.Duration`.

    `func (s *Scheduler) Tick(ctx context.Context) (sent int, err error)` finds records via
    `DueForSecondEmail(s.Now())`, and for each: issues a `PurposeSecondConfirmation` token, stores it on
    the record, sends `email.BuildSecondConfirmationEmail` with a confirm URL of `PublicBaseURL` plus
    `/v1/consent/confirm?t=<secret>`, advances via `consent.Apply(rec.State, EventSecondEmailSent)`, and
    clears `SecondEmailDueAt` so the record is not picked up again. Per the transition table
    `EventSecondEmailSent` leaves the state at `StateLinkClicked` — sending the email is not the parent's
    action and must not advance consent.

    Add `func (s *Scheduler) Run(ctx context.Context, interval time.Duration)` looping on a ticker until
    the context is cancelled, logging counts but never logging an email address or token.

    Choose a default `Delay` of four hours and expose it as `DefaultSecondEmailDelay`. Record on the
    constant why the delay exists: D-05 identifies the delayed second confirmation as the "plus" factor
    that makes this method meet the FTC's email-plus bar, chosen because it requires no parent-identifying
    data beyond the email address already collected, which is what MINOR-02 demands. Note that shortening
    this to zero collapses the flow back into the single-click design the correction rejected.

    Make the send idempotent per record: if a record already has a non-nil `SecondToken`, do not issue a
    second one on a subsequent tick — re-sending is the explicit resend endpoint's job, not the
    scheduler's, so a slow store or a duplicated tick cannot flood the parent.

    Write `scheduler_test.go` with `FakeSender` and an injected clock asserting: a record whose
    `SecondEmailDueAt` is in the future is not selected; one whose due time has passed is selected and
    receives exactly one email; after a tick the record holds a `SecondToken` and its state is still
    `StateLinkClicked`; a second tick sends nothing more for the same record; the emailed URL contains
    the confirm path and the freshly issued secret; and a record in `StateEmailSent` is never selected
    because it has no due time set.
  </action>

    breaks the whole flow, so follow the documented JSON structure rather than improvising: an `applinks`
    object containing `details`, each entry carrying an `appIDs` array and a `components` array. Restrict
    the matched paths to the two consent routes — the verify and confirm paths — so the app is not
    claiming every URL on the domain.

    Serve it with content type `application/json`, over HTTPS in deployment, with no redirect and no
    authentication. Apple fetches this file directly and a redirect breaks verification. Read the app
    identifier from `IOS_APP_ID` rather than hardcoding it, and fail startup when it is unset.

    Also add a short-lived cache header rather than a long one, so a change to the app identifier during
    development does not persist in caches for days.

    Update `README.md` with a Universal Links section recording, for the human who provisions this: the
    domain must be the same one registered in the app's Associated Domains entitlement; the file must be
    reachable over HTTPS with a valid certificate and no redirect; the confirmation links in both emails
    must point at this same domain unwrapped, because a tracking-wrapped redirect URL is a different
    domain and will open Safari instead of the app; and the flow should be verified on a physical device
    using Apple's documented approach of emailing yourself the link and long-pressing it to confirm the
    app appears as the opener. Note that plan 01-19 performs that end-to-end verification as a
    checkpoint, and that a custom URL scheme is a degraded fallback only if domain verification cannot be
    completed — it is not the intended design.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public internet → HTTP endpoints | Every endpoint is unauthenticated by necessity; the parent has no account and the token is the only credential |
| app → status endpoint | The iOS client reads consent state across the network and mirrors it locally |
| Apple's CDN → association file | Apple fetches the association document unauthenticated to verify domain ownership |
