<objective>
Encode ONBOARD-01's calibration completion rules and the baseline they produce, as pure logic that does
not depend on any sensor framework.

Purpose: ONBOARD-01 replaces a self-reported fitness-level dropdown with a real session, so the
definition of "a real session" is the requirement. D-01 was corrected on 2026-08-23 after
01-RESEARCH.md's Conflict 1 found the originally inferred lift threshold did not match MOMENTUM-01: the
locked value is now three or more working sets across two or more exercises, matching MOMENTUM-01's
wording verbatim, so calibration and the Phase 3 Momentum bar are one consistent definition. Keeping the
rules pure means they are testable now, and means the CoreMotion and stopwatch adapters in plan 01-15
are interchangeable sources feeding one decision rather than two divergent implementations of it.

Output: Calibration completion rules, the session protocol both later adapters conform to, and baseline
derivation — tested with no Xcode and no sensor hardware.
</objective>

  <action>
    Define `public enum CalibrationMode: String, CaseIterable, Sendable { case walk, lift }`.

    Define the thresholds as named public constants so the numbers appear exactly once in the codebase
    and Phase 3 can reference the same symbols rather than restating them:
    - `public static let qualifyingWalkDuration: TimeInterval` — 600 seconds, ten minutes.
    - `public static let qualifyingWorkingSets: Int` — 3.
    - `public static let qualifyingExercises: Int` — 2.
    Put these on a `public enum CalibrationThreshold` namespace. Add a header comment recording that
    these match MOMENTUM-01 verbatim per D-01 as corrected on 2026-08-23, that an earlier inferred value
    of two sets across one exercise was wrong, and that changing either number here silently desynchronises
    calibration from the Momentum qualifying-session bar in Phase 3.

    Define `public struct WalkProgress: Sendable, Equatable` holding `continuousDuration: TimeInterval`
    and `wasInterrupted: Bool`. D-01 says *continuous* minutes, so a paused or broken session must not
    accumulate toward the bar. Model that by having the caller reset `continuousDuration` on
    interruption, and expose `public mutating func recordInterruption()` that zeroes the accumulated
    duration and sets `wasInterrupted`. The interruption flag is retained so the completion screen can
    explain a restart rather than appearing to lose progress silently.

    Define `public struct LiftProgress: Sendable, Equatable` holding
    `workingSetsPerExercise: [String: Int]`, keyed by an exercise identifier, with
    `public mutating func recordWorkingSet(exercise: String)`, plus computed
    `public var totalWorkingSets: Int` and `public var distinctExercises: Int`. Only working sets count —
    add a comment noting warm-up sets are not recorded through this path.

    Define `public enum CalibrationProgress: Sendable, Equatable { case walk(WalkProgress), lift(LiftProgress) }`
    and `public enum CalibrationCompletion: Sendable, Equatable { case incomplete, complete }` with
    `public static func evaluate(_ progress: CalibrationProgress) -> CalibrationCompletion`:
    - walk: `.complete` when `continuousDuration >= CalibrationThreshold.qualifyingWalkDuration`
    - lift: `.complete` when `totalWorkingSets >= qualifyingWorkingSets` AND
      `distinctExercises >= qualifyingExercises`. Both conditions, not either.

    Define `public protocol CalibrationSessionSource: Sendable` with
    `var mode: CalibrationMode { get }` and `var progress: CalibrationProgress { get }`. The CoreMotion
    pedometer adapter and the manual stopwatch in plan 01-15 both conform to this. Add a comment
    recording D-02's rule and 01-RESEARCH.md's Assumption A1: completion is decided from this progress
    alone, so it never depends on location authorisation; GPS, when the user has granted it, enriches
    displayed pace and distance but is never the completion gate.

    Write `CalibrationThresholdTests` asserting: a walk at 599 seconds is incomplete and at exactly 600
    is complete; 601 is complete; a walk that reaches 600 seconds then records an interruption is
    incomplete afterward with `wasInterrupted` true; a lift with 3 sets across 1 exercise is incomplete
    (this is the specific value the superseded D-01 wording would have wrongly accepted, so assert it
    explicitly); 2 sets across 2 exercises is incomplete; exactly 3 sets across 2 exercises is complete;
    4 sets across 3 exercises is complete; an empty lift progress is incomplete; and that the three
    threshold constants equal 600, 3, and 2.
  </action>

    Define `public struct PaceZone: Sendable, Equatable` holding `slowestSecondsPerKm: Double` and
    `fastestSecondsPerKm: Double`, with an initialiser that orders the pair so `slowest` is always the
    larger number regardless of argument order. D-04 calls this a comfortable pace-zone *range*, so it
    is always an interval, never a single number that could read as a performance figure.

    Define `public struct CalibrationBaseline: Sendable, Equatable` holding
    `paceZone: PaceZone`, `safeStartingWeightKg: Double`, `source: BaselineSource`, and
    `establishedAt: Date`, where
    `public enum BaselineSource: String, Sendable, CaseIterable { case measured, provisional }`.

    Add `public static func provisional(establishedAt: Date) -> CalibrationBaseline` returning a generic
    but usable starting point with `source: .provisional`. Per D-03, skipping calibration must still give
    cardio and strength suggestions something to work from and must never block core app use — so this
    returns real conservative values, not zeros or optionals. Choose a deliberately cautious pace zone
    corresponding to a comfortable walk and a light starting weight, and record in a comment that these
    are intentionally conservative defaults chosen so that a skipped calibration errs toward
    under-loading rather than over-loading a user whose capacity is unknown.

    Add `public static func derive(from progress: CalibrationProgress, establishedAt: Date) -> CalibrationBaseline?`
    returning `nil` when `CalibrationCompletion.evaluate` reports `.incomplete` — a baseline is only
    derivable from a session that actually qualified. For a completed walk, derive the pace zone from the
    measured average pace by widening it into a comfortable band around the observed value; for a
    completed lift, derive the safe starting weight from the recorded working-set load. Carry the
    unmeasured half of the baseline forward from `provisional` values, since a walk tells us nothing
    about starting weight and a lift tells us nothing about pace. Set `source: .measured`.

    To satisfy D-04, `CalibrationBaseline` and `PaceZone` must expose nothing that reads as a score,
    grade, level, percentile, or rating: declare no `CustomStringConvertible`, no `displayName`, no
    `level`, `score`, `grade`, `rating`, or `tier` property. Add a header comment stating that these
    values exist only to set safe initial targets and must never be surfaced to the user as an
    assessment of their fitness.

    Write `CalibrationBaselineTests` asserting: `PaceZone` normalises reversed arguments so slowest is
    always the larger seconds-per-km value; `provisional` returns `source == .provisional` with a
    non-zero pace zone and a non-zero starting weight, so a skipped calibration is never a blank state;
    `derive` returns nil for an incomplete walk and an incomplete lift; `derive` returns a baseline with
    `source == .measured` for a completed walk and for a completed lift; a derived walk baseline has a
    pace zone whose slowest value is strictly greater than its fastest; and, as a D-04 guard, that
    `CalibrationBaseline` has no member whose name contains "score", "grade", "level", or "rating" —
    assert this by reflecting over `Mirror(reflecting:)` children labels and checking none matches those
    substrings case-insensitively.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| sensor or manual input → completion rule | Session measurements originate from device sensors or from a user-controlled stopwatch; both are untrusted with respect to accuracy |
| baseline → later training suggestions | The derived values seed the initial intensity targets every Phase 2 suggestion builds on |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-20 | Tampering | `CalibrationCompletion.evaluate` — a threshold that diverges from MOMENTUM-01 means a session that calibrates the user does not count toward their first Momentum week, or the reverse | high | mitigate | Thresholds are named constants declared once, matching MOMENTUM-01's wording verbatim per corrected D-01; a test asserts the specific 3-sets-across-1-exercise value that the superseded wording would have wrongly accepted is rejected. |
| T-01-21 | Tampering | `WalkProgress` — accumulating across a break would let a discontinuous walk qualify, seeding an unsafely high baseline | medium | mitigate | `recordInterruption` zeroes accumulated duration; a test asserts a session that reached the bar becomes incomplete after an interruption. |
| T-01-22 | Information Disclosure | A rendered fitness score, grade, or level would contradict D-04 and reintroduce exactly the comparative framing the product forbids | medium | mitigate | The type surface declares no score, grade, level, or rating member and no `CustomStringConvertible`; a reflection-based test fails the build if such a member is added later. |
| T-01-23 | Denial of Service | Requiring location permission to decide completion would block users who decline, contradicting D-02 | medium | mitigate | The completion rule lives in a Foundation-only target where CoreLocation cannot be imported, so the dependency is impossible to introduce at this layer; GPS is enrichment only per Assumption A1. |
| T-01-24 | Tampering | A skipped calibration yielding zero or nil values would leave downstream suggestions with no safe floor | medium | mitigate | `provisional` returns real conservative values rather than zeros or optionals, per D-03; tested for non-zero pace zone and starting weight. |
| T-01-SC | Tampering | package-manager installs | low | accept | SUPERSEDED by D-13; structurally impossible here — `RithamCore` is Foundation-only and this plan adds no dependency. |
