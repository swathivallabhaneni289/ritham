<objective>
Build the domain core of the parental-consent backend in Go: cryptographic token handling, the
four-state consent machine, and a pluggable email sender.

Purpose: MINOR-01's under-13 gate cannot be client-only — the parent's email client is not running the
iOS app, so a server must mint the token, send the mail, and validate the click. D-05 (corrected)
requires this to be modelled as `pending → email_sent → link_clicked → confirmed`, never a boolean,
because a single link click does not meet the FTC's "email plus" bar and Phase 5's LAUNCH-05 review may
require a stronger method without a schema rewrite. MINOR-02 additionally caps what may be collected:
the email address, and nothing more.

Output: A `consent-service` Go module whose domain logic is fully unit-tested with no network and no
third-party dependencies. HTTP surface and the delayed second email land in plan 01-08.

Language note: Go per D-13, overriding 01-RESEARCH.md's TypeScript/Supabase-Edge-Functions suggestion.
Framework choice is Claude's Discretion under D-13; this plan exercises that discretion by choosing the
Go standard library only — no router, no vendor SDK. That removes third-party dependency risk from the
one component in this phase with real security exposure, and it makes the `[SUS]` npm packages
01-RESEARCH.md's Package Legitimacy Audit flagged unreachable rather than merely unused.
</objective>

  <action>
    Initialise the Go module: `cd consent-service && go mod init ritham/consent-service` with Go 1.26.
    The module must have no third-party requires — standard library only, per this plan's objective.

    Create package `token` with:
    - `type Token struct` holding `Hash []byte`, `ExpiresAt time.Time`, `RedeemedAt *time.Time`, and
      `Purpose Purpose`.
    - `type Purpose string` with two constants, `PurposeInitialLink` and `PurposeSecondConfirmation`.
      Two purposes exist because D-05's "plus" factor is a second, distinct confirmation — a token
      minted for the first email must not be redeemable as the second confirmation.
    - `func Issue(purpose Purpose, ttl time.Duration, now time.Time) (secret string, t Token, err error)`.
      `secret` is 32 bytes read from `crypto/rand` and encoded with `base64.RawURLEncoding` so it is
      URL-safe for the confirmation link. Never generate this from `math/rand` or a timestamp.
      `t.Hash` stores `sha256.Sum256` of the raw secret bytes, not the secret itself — the plaintext
      secret leaves the process in the email and is never persisted, so a store compromise does not
      yield redeemable tokens.
    - `func (t Token) Verify(secret string, purpose Purpose, now time.Time) error` returning distinct
      sentinel errors `ErrMalformed`, `ErrNotFound`, `ErrExpired`, `ErrAlreadyRedeemed`, and
      `ErrWrongPurpose`. Compare hashes with `crypto/subtle.ConstantTimeCompare`, never `bytes.Equal`,
      to avoid a timing side channel on the token hash.
    - `func (t *Token) Redeem(secret string, purpose Purpose, now time.Time) error` which verifies then
      sets `RedeemedAt`; a second call returns `ErrAlreadyRedeemed`.

    Choose a TTL default of 72 hours for `PurposeInitialLink` and expose it as an exported constant
    `DefaultInitialTTL`. 01-RESEARCH.md's Security Domain flags that some email clients prefetch links
    to build previews and can consume a single-use token before the parent ever clicks; a short window
    plus the re-send affordance planned in 01-08 is the recorded mitigation, so do not shorten this to
    minutes.

    Write `consent-service/README.md` recording: the module is standard-library-only by decision D-13;
    the two environment variables the service will require (`RESEND_API_KEY`, `CONSENT_MAIL_FROM`); and
    the open legal question from D-05 that whether a third-party email vendor under a data-processing
    agreement counts as third-party disclosure under email-plus's internal-use-only limitation is
    unresolved and flagged for LAUNCH-05 counsel review, not settled by this implementation.

    Write `token_test.go` covering: two `Issue` calls never produce the same secret; a correct secret
    verifies; a wrong secret returns `ErrNotFound`; a secret verified after `ExpiresAt` returns
    `ErrExpired`; redeeming twice returns `ErrAlreadyRedeemed` on the second call; a token issued for
    the initial link returns `ErrWrongPurpose` when redeemed as a second confirmation; the persisted
    `Hash` does not contain the plaintext secret bytes.
  </action>

    Create package `consent` with `type State string` and exactly four constants: `StatePending`,
    `StateEmailSent`, `StateLinkClicked`, `StateConfirmed`. Do not add a boolean anywhere in this
    package — 01-RESEARCH.md names a boolean consent field as an explicit anti-pattern because it
    conflates "parent clicked the link" with "consent is legally valid", which are different events
    under the FTC's email-plus definition.

    Define `type Event string` with `EventEmailSent`, `EventLinkRedeemed`, `EventSecondEmailSent`,
    `EventSecondConfirmationRedeemed`. Implement
    `func Apply(current State, e Event) (State, error)` as an explicit transition table:
    - pending + EventEmailSent → email_sent
    - email_sent + EventLinkRedeemed → link_clicked
    - link_clicked + EventSecondEmailSent → link_clicked (the delayed second email does not itself
      advance state; only the parent's second action does)
    - link_clicked + EventSecondConfirmationRedeemed → confirmed
    Every other pair returns `ErrInvalidTransition`. There must be no path from pending or email_sent
    to confirmed — that is the entire point of D-05's correction, and it is what
    `ConsentStateMachineTests` asserts.

    Add `func (s State) GrantsAppAccess() bool` returning true only for `StateConfirmed`. Per D-06 the
    under-13 account is fully locked in every earlier state — no preview, no partial functionality.

    Create `store.go` with `type Record struct` holding: an opaque `ID string`, `MinorProfileRef string`
    (an opaque identifier for the app-side profile — never the minor's name, age, or answers),
    `ParentEmail string`, `State State`, `InitialToken token.Token`, `SecondToken *token.Token`,
    `SecondEmailDueAt *time.Time`, `CreatedAt`, `UpdatedAt`. MINOR-02 caps the parent-identifying data
    at the email address: do not add parent name, phone, postal address, or any identity document
    field, and record that constraint as a comment on `ParentEmail`.

    Define `type Store interface` with `Create`, `Get`, `Update`, `FindByTokenHash`, and
    `DueForSecondEmail(now time.Time) ([]Record, error)`. Provide `NewMemoryStore()` implementing it
    with a mutex-guarded map. The interface exists so plan 01-08 can substitute a durable store without
    touching transition logic.

    Write `state_test.go` asserting: the full happy path pending → email_sent → link_clicked →
    confirmed; that `Apply(StatePending, EventSecondConfirmationRedeemed)` errors; that
    `Apply(StateEmailSent, EventSecondConfirmationRedeemed)` errors; that redeeming the initial link and
    stopping there leaves the record at `StateLinkClicked` and `GrantsAppAccess()` is false; that
    `GrantsAppAccess()` is true only for `StateConfirmed`. Write `store_test.go` asserting create/get
    round-trip, that `FindByTokenHash` matches on hash, and that `DueForSecondEmail` returns only
    records whose `SecondEmailDueAt` is at or before the supplied time.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| parent's email client → service | The confirmation link is a bearer credential arriving from an untrusted network path; whoever holds it is treated by the service as the consenting parent |
| service → transactional email vendor | The parent's email address crosses to a third-party processor |
| service → persistent store | Consent records at rest hold the one piece of parent PII this phase collects |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-03 | Spoofing | `token.Issue` — a guessable consent token lets an under-13 user approve their own account | critical | mitigate | 32 bytes from `crypto/rand`, base64url-encoded; never derived from a timestamp or `math/rand`. Test asserts two issues never collide. |
| T-01-04 | Elevation of Privilege | `consent.Apply` — reaching `confirmed` without the second confirmation | high | mitigate | Explicit transition table with no pending→confirmed or email_sent→confirmed edge; `ErrInvalidTransition` on every other pair; `state_test.go` asserts the single-click case terminates at `StateLinkClicked` and `GrantsAppAccess()` is false. |
| T-01-05 | Tampering | Token replay — redeeming the same link twice | high | mitigate | `Redeem` sets `RedeemedAt` and every later call returns `ErrAlreadyRedeemed`; tokens are also purpose-bound so an initial-link token cannot be replayed as the second confirmation. |
| T-01-06 | Information Disclosure | Consent record at rest containing parent PII | high | mitigate | Only the token's SHA-256 hash is persisted, never the plaintext secret, so store compromise yields no redeemable link. `Record` is capped at `ParentEmail` per MINOR-02 — no parent name, phone, or address field exists to leak. |
| T-01-07 | Information Disclosure | API key or parent email address leaking into logs | medium | mitigate | `ResendSender.Send` logs neither the Authorization header nor the request body; errors carry only the HTTP status code. |
| T-01-08 | Denial of Service | Email-client link prefetch consuming the single-use token before the parent clicks | medium | mitigate | 72-hour `DefaultInitialTTL` rather than a minutes-long window, plus the operator-facing re-send path built in plan 01-08, so a prefetch-consumed token does not permanently strand the parent. |
| T-01-09 | Repudiation | No record of which confirmation step occurred when | low | accept | `Record` carries `CreatedAt`/`UpdatedAt` and per-token `RedeemedAt`, which is sufficient to reconstruct the sequence for a LAUNCH-05 compliance review. A dedicated append-only audit log is not warranted at this volume and would enlarge the PII footprint MINOR-02 asks us to minimise. |
| T-01-SC | Tampering | package-manager installs | high | mitigate | SUPERSEDED by D-13. This service uses the Go standard library only — `go.mod` declares no third-party module, and an acceptance criterion enforces that. The `resend` and `@supabase/supabase-js` packages 01-RESEARCH.md's Package Legitimacy Audit flagged `[SUS]` belonged to the superseded Node design and are never installed; there is consequently no install event for a legitimacy checkpoint to gate. Resend is reached over its documented REST endpoint from `net/http`. |
</threat_model>
