<objective>
Persist the profile, condition tags, calibration baseline, and consent mirror in SwiftData, behind a
facade that enforces the consent gate at the data layer and a store file protected at rest.

Purpose: 01-RESEARCH.md's Security Domain makes two findings that shape this plan. First, under V4
Access Control, the under-13 lock and the teen partial gate must be enforced where screening data is
read and written, not only in navigation — otherwise a bug on any one screen bypasses a COPPA-grade
gate. Second, under V6, condition tags and eating-disorder-derived data are named explicitly as
sensitive in LAUNCH-04's GDPR and CCPA review scope, so the store needs an explicit file protection
class rather than the platform default.

It also resolves the storage question 01-RESEARCH.md flagged for the planner rather than deciding
silently: persist only the derived eating-disorder outcome, not the five individual answers. Decision
and rationale are recorded in Task 1.

Output: Four SwiftData models, a protected container, and a gated store facade with tests for expiry and
for the gate.
</objective>

    Create four `@Model` classes. Each stores enum values by their `String` raw value with a computed
    accessor returning the core type, because SwiftData persists primitives most predictably and the raw
    values are already the stable identifiers.

    `UserProfile`: `age`, `explanationRegisterRaw`, `dietaryPatternRaw`, `consentTierRaw`,
    `consentStateRaw`, `createdAt`, `updatedAt`. Add computed accessors for register, dietary pattern,
    tier, and state, plus `var consentGate: ConsentGate?`. Per DIET-01 the dietary pattern has no expiry
    and no re-screen, and per EXPLAIN-01 the register is changeable at any time — record both on their
    properties, and note that neither may ever be derived from age.

    `ConditionTagRecord`: `tagRaw`, `recordedAt`, `editedAt` (optional), and
    `professionalClearanceGrantedAt` (optional). Add `var tag: ConditionTag?` and
    `func validity(now:calendar:) -> TagValidity` and `func isReScreenDue(now:calendar:) -> Bool`, both
    delegating to `ConditionTagValidity` in core. Do not reimplement the date arithmetic here — the core
    rule is already tested against explicit boundary dates, and a second implementation would be able to
    drift from it. Add a comment recording D-08: expiry is a query-time check and never a deletion, so
    an overdue tag keeps applying its restriction rather than reverting to generic guidance.

    `CalibrationBaselineRecord`: `slowestSecondsPerKm`, `fastestSecondsPerKm`, `safeStartingWeightKg`,
    `sourceRaw`, `establishedAt`, with `var baseline: CalibrationBaseline?`. Per D-04 it exposes nothing
    that reads as a score, grade, level, or rating; per D-03 a skipped calibration is stored with the
    provisional source rather than left absent, so suggestions always have a floor.

    `ParentalConsentRecord`: `serviceRecordID`, `parentEmail`, `stateRaw`, `lastCheckedAt`, with
    `var state: ConsentState?`. Per MINOR-02 the only parent-identifying field is the email address —
    add no parent name, phone, postal address, or identity document field. Add a comment noting the Go
    service remains authoritative for consent state during the wait and this record mirrors it.

    Resolve the storage question 01-RESEARCH.md flagged rather than defaulting silently. On
    `UserProfile`, store the eating-disorder outcome as `edScreenOutcomeRaw` holding only the derived
    result — the resulting condition tag — and do not persist the five individual answers. Rationale,
    which must be recorded as a comment: §1.5 states the individual answers are never shown as a score or
    a label, and 01-RESEARCH.md recommends extending that framing to storage; the answers have no
    downstream consumer because gate resolution needs only the outcome; and not storing them removes
    them from the reach of any future data export, debug log, or feature. The cost is that editing this
    section later means re-answering all five questions, which D-09 already permits since an edit
    re-checks that section.

    Write `PersistenceTests` using an in-memory `ModelContainer` asserting: each model round-trips
    through save and fetch; `ConditionTagRecord.validity` returns `.active` before the twelve-month mark
    and `.expiredStillApplied` at and after it, and `isReScreenDue` matches; a record with `editedAt`
    measures the window from the edit; the computed enum accessors return nil rather than trapping for
    an unrecognised raw value, so a future schema change cannot crash on old data; and that
    `UserProfile` has no property holding an individual eating-disorder answer — assert by reflecting
    over the model's property names and checking none matches the pattern used for those five items.
  </action>

    Apply an explicit file protection class to the store file rather than relying on the platform
    default. 01-RESEARCH.md names condition tags and eating-disorder-derived data as sensitive within
    LAUNCH-04's review scope and records that no explicit protection class should not be the default
    here. Use `.completeUntilFirstUserAuthentication` as the baseline, applied to the store file and its
    sidecar files via `FileManager.setAttributes` with `FileAttributeKey.protectionKey` after the
    container is created. Record in a comment why the stronger `.complete` is not used: it makes the
    store unreadable whenever the device is locked, which would break any background work that touches
    the profile, and `.completeUntilFirstUserAuthentication` still protects against extraction from an
    unencrypted backup or a powered-off device. Note that if a later phase adds no background access,
    tightening to `.complete` is worth revisiting.

    Verify the attribute took effect rather than assuming it: read it back with
    `FileManager.attributesOfItem` and throw a descriptive error when it does not match, so a silent
    failure surfaces at startup instead of at a compliance review.

    Edit `RithamApp.swift` to attach the container with `.modelContainer(RithamModelContainer.shared)`.
    Keep the edit strictly additive and leave the header comment naming the three owners intact, since
    plan 01-19 edits this file next.

    Create `HealthDataStore`, the single facade through which every screening read and write passes. It
    holds a `ModelContext` and a `Calendar`, and derives the current `ConsentGate` from the stored
    `UserProfile` on each call rather than caching it, so a consent change takes effect immediately.

    Every accessor that touches screening data — the gate answers, the condition checklist, the severity
    follow-ups, the eating-disorder outcome, and the derived condition tags — first checks
    `gate.allows(.healthScreening)` and throws `HealthDataStoreError.consentRequired` when it is false.
    Define the error type with cases `consentRequired` and `profileMissing`. Add a header comment
    recording why this exists: navigation is not a security boundary, and enforcing here means a defect
    in any one screen's routing cannot read or write a minor's health data. Note that under-13 accounts
    are fully locked in every state before confirmed per D-06, which this check produces automatically
    because `ConsentGate` already returns an empty capability set for that case.

    Provide these operations:
    - `func loadProfile() throws -> UserProfile` and `func updateProfile(_:) throws`, ungated, since a
      profile must exist to evaluate the gate at all. Restrict the ungated surface to age, register,
      dietary pattern, tier, and consent state — never to screening answers.
    - `func saveScreeningResult(_ result: GateResolutionResult, answers: ScreeningAnswers, now: Date) throws`
      — gated. Persists one `ConditionTagRecord` per matched tag with `recordedAt` set to `now`, and
      stores only the derived eating-disorder outcome per Task 1.
    - `func activeConditionTags(now: Date) throws -> [ConditionTag]` — gated. Returns every stored tag
      whose validity is `.active` or `.expiredStillApplied`. Per D-08 an overdue tag is still returned,
      because the safer default is to over-restrict briefly rather than silently under-restrict; add a
      comment stating that filtering out expired tags here would be a safety defect.
    - `func isReScreenDue(now: Date) throws -> Bool` — gated. True when any stored tag is overdue. Per
      D-07 this drives a non-blocking banner only; add a comment stating no caller may use it to gate
      access.
    - `func invalidateSection(_ section: EditableSection, now: Date) throws` — gated for screening
      sections, ungated for the register and dietary pattern. Per D-09 it clears only that section's
      records and stamps `editedAt`, never the whole questionnaire.
    - `func recordProfessionalClearance(for tag: ConditionTag, at: Date) throws` and
      `func clearancesNeedingReConfirmation(now:) throws -> [ConditionTag]` — gated, delegating to
      `ProfessionalClearance.needsReConfirmation`. Per §1.6 this toggle is not a permanent unlock.
    - `func saveCalibrationBaseline(_:) throws` and `func loadCalibrationBaseline() throws -> CalibrationBaseline?`
      — ungated, since MINOR-01 lets a teen calibrate with no parental involvement. Return
      `CalibrationBaseline.provisional` when none is stored, so a skipped calibration is never a blank
      state.

    Write `HealthDataStoreGateTests` with an in-memory container asserting: for an under-13 profile in
    each of `.pending`, `.emailSent`, and `.linkClicked`, every gated operation throws `consentRequired`
    while `saveCalibrationBaseline` and `loadCalibrationBaseline` succeed — the latter proving the teen
    and calibration carve-outs are not accidentally gated shut; the same under-13 in `.confirmed`
    succeeds on the gated operations; a teen in `.pending` is refused screening writes but permitted
    calibration and profile updates; an adult in `.pending` is permitted everything; a stored tag past
    twelve months is still returned by `activeConditionTags` and also reported by `isReScreenDue`;
    `invalidateSection` for the condition checklist leaves the dietary pattern and register untouched;
    and `loadCalibrationBaseline` with nothing stored returns a provisional baseline rather than nil.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app code → health data at rest | Condition tags and eating-disorder-derived data are named as sensitive in LAUNCH-04's review scope |
| navigation layer → data layer | Reaching a screen must not by itself confer permission to read or write screening data |
| device filesystem → store file | Backups, other processes, and physical extraction are all paths to the store |
