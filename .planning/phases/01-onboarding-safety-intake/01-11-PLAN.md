<objective>
Persist the profile, condition tags, and calibration baseline in SwiftData, behind a facade with a store
file protected at rest.

Purpose: 01-RESEARCH.md's Security Domain V6 finding shapes this plan: condition tags and
eating-disorder-derived data are named explicitly as sensitive in LAUNCH-04's GDPR and CCPA review
scope, so the store needs an explicit file protection class rather than the platform default.

There is no consent gate to enforce at this layer. Per D-14 (01-CONTEXT.md), Ritham has a permanent
13+ age floor enforced at Q0, before any profile is ever created — the earlier tiered-consent design
that gated screening access by parent-confirmation state (D-05/D-06/D-13, superseded) is gone
entirely. A stored `UserProfile` therefore always belongs to a user who is already 13 or older, so
every screening accessor works the same way for every stored profile, full stop.

It also resolves the storage question 01-RESEARCH.md flagged for the planner rather than deciding
silently: persist only the derived eating-disorder outcome, not the five individual answers. Decision
and rationale are recorded in Task 1.

Output: Three SwiftData models, a protected container, and a store facade with tests for expiry.
</objective>

    computed accessors for register and dietary pattern. Per DIET-01 the dietary pattern has no expiry

    properties, and note that neither may ever be derived from age. `age` remains a plain stored field

    rule is already tested against explicit boundary dates, and a second implementation would be able to
    drift from it. Add a comment recording D-08: expiry is a query-time check and never a deletion, so
    an overdue tag keeps applying its restriction rather than reverting to generic guidance.

    `CalibrationBaselineRecord`: `slowestSecondsPerKm`, `fastestSecondsPerKm`, `safeStartingWeightKg`,

    that reads as a score, grade, level, or rating; per D-03 a skipped calibration is stored with the
    provisional source rather than left absent, so suggestions always have a floor.

    Resolve the storage question 01-RESEARCH.md flagged rather than defaulting silently. On
    `UserProfile`, store the eating-disorder outcome as `edScreenOutcomeRaw` holding only the derived
    result — the resulting condition tag — and do not persist the five individual answers. Rationale,

    downstream consumer because gate resolution needs only the outcome; and not storing them removes
    them from the reach of any future data export, debug log, or feature. The cost is that editing this
    section later means re-answering all five questions, which D-09 already permits since an edit
    re-checks that section.

  <name>Task 3: The health data store facade</name>
  <files>RithamApp/Ritham/Persistence/HealthDataStore.swift, RithamApp/RithamTests/HealthDataStoreTests.swift</files>

  <action>
    Create `HealthDataStore`, the single facade through which every screening read and write passes. It
    holds a `ModelContext` and a `Calendar`.

    Every accessor — the gate-section answers, the condition checklist, the severity follow-ups, the
    eating-disorder outcome, and the derived condition tags — reads and writes the stored `UserProfile`
    directly. There is no consent gate to check. Per D-14 (01-CONTEXT.md), Ritham has a permanent 13+
    age floor enforced at Q0, before a profile is ever created, so a stored profile always belongs to a
    user who is already 13 or older and gets full, identical access from the moment it exists. Add a
    header comment recording that this store deliberately has no gating concept: an earlier design
    (D-05/D-06/D-13, superseded by D-14) enforced a parental-consent gate at exactly this layer — a
    `ConsentGate` type, `.allows(_:)` checks on every accessor, and a `consentRequired` error — and none
    of that machinery exists any more or should be reintroduced, even as an always-true stub; there is
    genuinely nothing left to gate.

    Define `HealthDataStoreError` with two cases: `profileMissing`, thrown by any accessor that needs a
    stored profile and finds none, and `ageBelowFloor`, thrown by `updateProfile` per the rule below.

    Provide these operations, all operating directly against the stored profile:
    - `func loadProfile() throws -> UserProfile` and `func updateProfile(_:) throws`. Per MINOR-01, once a
      profile exists its owner already cleared the 13+ floor at onboarding; `updateProfile` enforces that
      this can never be undone later (e.g. a Settings edit). Before writing, compare the incoming
      `profile.age` against the currently stored age: if the incoming value is under 13, throw
      `ageBelowFloor` and write nothing at all — not the age field, not any other field passed in the
      same call — so the stored profile is left completely untouched and the previous age is kept. This
      is a whole-update rejection, not a per-field silent drop, so the caller always knows the edit did
      not take. When no profile is stored yet (the very first write, from onboarding's age step), this
      check does not apply — `updateProfile` creates the initial profile normally, and `AgeStepView`
      (plan 01-13) is what keeps an ineligible value from ever reaching this call in the first place, by
      construction. Add a comment recording that both mechanisms exist because they close different
      gaps: plan 01-13 stops an ineligible age from being submitted at all during onboarding, and this
      check stops a confirmed profile's age from being edited back down below the floor afterward.
    - `func saveScreeningResult(_ result: GateResolutionResult, answers: ScreeningAnswers, now: Date) throws`
      — persists one `ConditionTagRecord` per matched tag with `recordedAt` set to `now`, and stores only
      the derived eating-disorder outcome per Task 1.
    - `func activeConditionTags(now: Date) throws -> [ConditionTag]` — returns every stored tag whose
      validity is `.active` or `.expiredStillApplied`. Per D-08 an overdue tag is still returned, because
      the safer default is to over-restrict briefly rather than silently under-restrict; add a comment
      stating that filtering out expired tags here would be a safety defect.
    - `func isReScreenDue(now: Date) throws -> Bool` — true when any stored tag is overdue. Per D-07 this
      drives a non-blocking banner only; add a comment stating no caller may use it to gate access.
    - `func invalidateSection(_ section: EditableSection, now: Date) throws` — per D-09 clears only that
      section's records and stamps `editedAt`, never the whole questionnaire.
    - `func recordProfessionalClearance(for tag: ConditionTag, at: Date) throws` and
      `func clearancesNeedingReConfirmation(now:) throws -> [ConditionTag]` — delegating to
      `ProfessionalClearance.needsReConfirmation`. Per §1.6 this toggle is not a permanent unlock.
    - `func saveCalibrationBaseline(_:) throws` and `func loadCalibrationBaseline() throws -> CalibrationBaseline?`
      — return `CalibrationBaseline.provisional` when none is stored, so a skipped calibration is never a
      blank state.

    Write `HealthDataStoreTests` with an in-memory container asserting: every operation above succeeds
    against a stored profile regardless of the profile's age, since a stored profile is always 13 or
    older and there is no tier or state left to vary the result; a stored tag past twelve months is still
    returned by `activeConditionTags` and also reported by `isReScreenDue`; `invalidateSection` for the
    condition checklist leaves the dietary pattern and register untouched; `loadCalibrationBaseline` with
    nothing stored returns a provisional baseline rather than nil; calling a screening accessor with no
    stored profile throws `profileMissing`; creating the first-ever profile via `updateProfile` with age
    13 succeeds; and, given an existing stored profile aged 13 or older, calling `updateProfile` with an
    incoming age under 13 throws `ageBelowFloor`, leaves the stored age exactly as it was before the
    call, and leaves every other stored field unchanged too (a second field changed in the same rejected
    call must not have been applied either).
  </action>
