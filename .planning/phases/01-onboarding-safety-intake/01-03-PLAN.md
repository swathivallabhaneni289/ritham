<objective>
Model the screening questionnaire's vocabulary: every condition tag, the three clearance gate levels
with a most-restrictive ordering, every fixed-choice answer type, SCOFF scoring, the twelve-month tag
validity rule, and the dietary pattern.

Purpose: HEALTH-06's escalation engine (plan 01-06) is only as sound as the types it reasons over. If
gates cannot be ordered, "most restrictive wins" is unimplementable; if an answer type permits free
text, HEALTH-01's fixed-choice constraint is violated at the type level rather than merely by
convention. Landing the vocabulary first — with tests — means the engine plan is pure rule
transcription against a settled contract.

Output: The screening domain vocabulary in `RithamCore`, fully unit-tested on a machine with no Xcode.
</objective>

    every answer type here is a closed enum — no `String` payloads, no associated free-form values. The
    only numeric input in the entire questionnaire is Q0's age.

    In `ScreeningAnswers.swift` define:
    - `public enum YesNo: Sendable, CaseIterable { case yes, no }`
    - `public enum YesNoUnsure: Sendable, CaseIterable { case yes, no, notSure }` with
      `public var isCautiousBranch: Bool` returning true for both `.yes` and `.notSure`. HEALTH-06's
      governing principle is that "Not sure" always resolves to the more cautious branch; expressing it
      once here means plan 01-06 cannot forget it at an individual rule site.
    - `public enum BloodPressureControl: Sendable, CaseIterable { case wellControlled, notSureOrNotChecked, doctorSaysHigh }` (CV-2)
    - `public enum RhythmControl: Sendable, CaseIterable { case yes, notSure, no }` (CV-2b)
    - `public enum SurgicalClearance: Sendable, CaseIterable { case fullyCleared, stillInRecoveryNotCleared, notApplicable }` (MSK-2)
    - `public enum PostpartumWeeks: Sendable, CaseIterable { case underSix, sixToTwelve, overTwelve }` (PP-2)
    - `public enum ChecklistItem: String, CaseIterable, Sendable, Hashable` with one case per checkbox in
      §1.3's nine categories plus `noneOfTheAbove`, and a `public var category: ChecklistCategory`.
      Define `public enum ChecklistCategory: String, CaseIterable, Sendable` with the nine categories.
    - `public struct ChecklistSelection: Sendable, Equatable` wrapping a `Set<ChecklistItem>` whose only
      mutator is `public mutating func toggle(_ item: ChecklistItem)`. §1.3 states choosing "None of the
      above" clears any other selection, so implement that inside `toggle`: selecting `noneOfTheAbove`
      empties the set first, and selecting any other item removes `noneOfTheAbove`. Enforcing it in the
      type means no view can produce a contradictory selection.
    - `public struct ScreeningAnswers: Sendable, Equatable` holding: `age: Int?`; the seven gate answers
      as `YesNo?`; `med1: YesNoUnsure?` and `med2: YesNo?`; `checklist: ChecklistSelection`; every
      severity follow-up as an optional of its type above; `scoff: SCOFFResponses?`; and `u1: YesNo?`.
      All optional because the flow fills them progressively and branches skip inapplicable questions.

    In `SCOFF.swift` define `public struct SCOFFResponses: Sendable, Equatable` with five `YesNo`
    properties named `ed1` through `ed5`, a `public var yesCount: Int`, and
    `public var isPositiveScreen: Bool` returning `yesCount >= 2` — §1.4 names two as the established
    threshold. Add `public static func isTriggered(by selection: ChecklistSelection) -> Bool` returning
    true only when the checklist contains the eating-disorder-history item, per D-10: this screen is not
    shown to every user.

    §1.5 requires that the computed score never surfaces to the user as a number, a positive/negative
    result, or a label. Enforce that at the type level: give `SCOFFResponses` no
    `CustomStringConvertible` conformance and no display-name or summary property, and add a header
    comment stating that `yesCount` is for internal gate resolution only and must never be bound to a
    view. `isPositiveScreen` is the only value callers outside the engine should read.

    Write `ScreeningAnswersTests` asserting: `YesNoUnsure.notSure.isCautiousBranch` and
    `.yes.isCautiousBranch` are true while `.no` is false; a SCOFF response with exactly one yes is not a
    positive screen and with exactly two is; zero yeses is not; five yeses is; `isTriggered` is false for

    item is present; toggling `noneOfTheAbove` into a populated selection leaves a set containing only
    `noneOfTheAbove`; toggling any other item into a selection holding `noneOfTheAbove` removes it; and
    every `ChecklistItem` maps to a category.

  <name>Task 3: The twelve-month condition-tag validity rule</name>
  <files>RithamCore/Sources/RithamCore/Screening/ConditionTagValidity.swift, RithamCore/Tests/RithamCoreTests/ConditionTagExpiryTests.swift</files>

    - `.planning/phases/01-onboarding-safety-intake/01-CONTEXT.md` — D-07 (non-blocking reminder at expiry), D-08 (keep applying expired restrictions), D-09 (editing one answer re-checks only that section)

  </read_first>
  <action>
    HEALTH-02's twelve-month rule must be testable before Xcode exists, so the rule lives here as a pure
    function of dates and the SwiftData model in plan 01-11 calls into it rather than reimplementing it.

    Define `public enum TagValidity: Sendable, Equatable` with cases `active` and `expiredStillApplied`.
    There is deliberately no `expired` case that drops the restriction: D-08 requires that while a tag is
    overdue but not yet re-screened the app keeps applying the existing restriction rather than reverting
    to generic guidance — over-restrict briefly, never silently under-restrict. Record that reasoning as a
    comment on the case, since a future reader will otherwise be tempted to add the missing case.

    Define `public struct ConditionTagValidity: Sendable` with:
    - `public static let validityWindow: TimeInterval` — twelve months, computed via `Calendar` date
      arithmetic rather than a hardcoded seconds count, so leap years and DST do not shift the boundary.
      Prefer exposing `public static func expiry(from recordedAt: Date, calendar: Calendar) -> Date`
      that adds twelve months with `calendar.date(byAdding:)`, and derive everything else from it.
    - `public static func validity(recordedAt: Date, now: Date, calendar: Calendar) -> TagValidity` —
      `.active` while `now` is strictly before the computed expiry, `.expiredStillApplied` at or after it.
    - `public static func isReScreenDue(recordedAt: Date, now: Date, calendar: Calendar) -> Bool` —
      true exactly when validity is `.expiredStillApplied`. D-07 makes this a non-blocking banner
      signal, so its only job is to say "prompt", never "block": add a comment stating no caller may use
      this to gate access.
    - `public static func validity(recordedAt: Date, editedAt: Date?, now: Date, calendar: Calendar) -> TagValidity` —
      §1.6 says tags stay valid twelve months *or until the user edits an answer, whichever comes first*,
      and D-09 scopes an edit to its own section. When `editedAt` is non-nil, measure the window from
      `editedAt` instead of `recordedAt`.

    Add `public struct ProfessionalClearance: Sendable, Equatable` holding `grantedAt: Date` and
    `public func needsReConfirmation(now: Date, calendar: Calendar) -> Bool` using the same window.
    §1.6 states the "I've talked to a professional" toggle is not a permanent unlock and re-prompts at
    each re-screen point; model it as a dated grant, never a standing boolean.

    Write `ConditionTagExpiryTests` asserting, with a fixed `Calendar` and explicit `Date` values so the
    tests are deterministic: a tag recorded today is `.active`; one day before the twelve-month mark is
    `.active`; exactly at the twelve-month mark is `.expiredStillApplied`; one day after is
    `.expiredStillApplied`; `isReScreenDue` is false before and true at or after the mark; an edit six
    months in resets the window so the original twelve-month mark is still `.active`; and
    `ProfessionalClearance.needsReConfirmation` follows the same boundary. Add an explicit test named for
    D-08's guarantee asserting that no input to `validity` ever yields a value that drops the restriction
    — enumerate `TagValidity.allCases`-equivalent coverage by asserting the returned value is one of the
    two defined cases in every branch.
  </action>
