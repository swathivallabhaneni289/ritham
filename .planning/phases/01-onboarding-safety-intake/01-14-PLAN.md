<objective>
Build the consent screens and the client that talks to the Go consent service: the under-13 halt with
its waiting state, the parent email entry with a correction and re-send affordance, and the 13-to-17
partial-gate notice.

Purpose: MINOR-01 splits into two very different experiences that must not become two different apps.
An under-13 account is fully locked until a parent confirms, per D-06 — no preview, no partial
functionality. A 13-to-17 account is already using calibration, tracking, and Momentum, and only the
health questions wait; that user can decline to involve a parent indefinitely and keep everything they
already have. Both are ordinary steps in the same flow, reached by routing rather than by a fork.

MINOR-02 constrains the interaction sharply: the minor must never hold or enter a parent's credentials,
and no more parent-identifying information may be collected than the method strictly requires — which is
one email address.

Output: A typed service client, a status poller that mirrors rather than decides, and three registered
screens.
</objective>

  <action>
    Create `ConsentServiceClient` as a protocol with three async methods — `requestConsent`, `status`,
    and `resend` — plus a `URLSession`-backed implementation and a fake for tests. Only these three
    exist: the verify and confirm endpoints are opened by the parent from their email client and must
    never be callable from the app, because an app-callable confirm would let the minor's own device
    complete the parental consent step. Add a header comment recording that constraint.

    Decode the state field into `ConsentState` using its raw values, which plan 01-04 aligned with the
    server's strings. Treat an unrecognised state as an error rather than defaulting to any known value —
    defaulting to `confirmed` would be a privilege escalation, and defaulting to `pending` would silently
    lock out a confirmed account. Define `ConsentClientError` with cases for transport failure, an
    unexpected status code, a decoding failure, an unknown state, and rate-limited.

    Read the service base URL from the app's configuration rather than hardcoding it, and require HTTPS —
    reject a non-HTTPS base URL at construction, since the consent flow carries a parent's email address.

    Create `ConsentStatusPoller`, an `@Observable` object that polls `status` on an interval with backoff
    while `state.isAwaitingParent`, stops once `grantsAppAccess` is true or on an unrecoverable error, and
    writes the observed state into `ParentalConsentRecord` via `HealthDataStore`. Add a header comment
    stating the poller mirrors and never decides: it may only write a state it read from the server, and
    no code path may construct `.confirmed` locally. Stop polling when the app is backgrounded and resume
    on foreground so it does not drain battery during the multi-hour wait D-05's delayed second email
    implies.

    Write `ConsentServiceClientTests` against a stubbed `URLProtocol` asserting: `requestConsent` posts
    the profile reference and the email and decodes the returned identifier and state; `status` decodes
    each of the four states; an unrecognised state string produces `unknownState` rather than any valid
    value; a non-2xx response produces `unexpectedStatus`; a rate-limited response on resend surfaces as
    `rateLimited`; and constructing the client with an `http://` base URL fails.

    Write `ConsentPollerTests` with the fake client asserting: the poller stops once the observed state
    is `confirmed`; it keeps polling through `pending`, `emailSent`, and `linkClicked`; observing
    `linkClicked` does not set the local record to `confirmed`, which is the client-side expression of
    D-05's correction; and a transport error does not advance or clear the locally stored state.
  </action>
