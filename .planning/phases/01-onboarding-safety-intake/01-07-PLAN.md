<objective>
Implement the onboarding flow's branching as one pure routing function over a single shared step
vocabulary, and define EXPLAIN-01's register.

Purpose: CROSSGEN-05 forbids any age-based navigation fork — no separate under-18 app mode, no screen
labelled for one age group. MINOR-01 simultaneously requires age to change what happens next. Per D-14,
that requirement is now a single boolean: age under 13, or not. The only way to satisfy both is for
every user to traverse one step enum, with age changing *which case comes next* — at exactly one fork —
and never *which hierarchy they are in*. Making that a pure function rather than scattered per-view
conditionals is what makes the no-fork guarantee testable before any view exists — which is exactly what
01-VALIDATION.md's `OnboardingFlowStateTests` row asks for. This is a strictly stronger guarantee than
the superseded tiered design: that design had two branch points (a consent halt, and a post-calibration
capability gate) across three tiers; this one has one branch point, and every age 13 and up — not just
same-tier ages — takes the identical path with zero divergence.

Note on placement: 01-RESEARCH.md's Pattern 1 shows an `@Observable` flow-state object whose
`step.view(flow:)` returns a SwiftUI View. The View half cannot live in this Foundation-only target. The
split is deliberate — the routing decision and the answers live here where they are testable today, and
the app target's observable wrapper in plan 01-12 delegates to this function rather than reimplementing
it. No branching logic may exist on the app side.

Output: The step vocabulary, the answer aggregate, the routing function, and the register — tested with
no Xcode.
</objective>

  <action>
    Implement `public enum OnboardingRouter` with
    `public static func nextStep(after current: OnboardingStep, answers: OnboardingAnswers) -> OnboardingStep?`,
    returning `nil` only when the flow is finished. This is the single source of truth for branching —
    01-PATTERNS.md's shared rule is that no view computes its own next step.

    Sequence, per MINOR-01 and §1.1:
    - `welcome` → `explanationRegister` → `age`.
    - After `age`, read `answers.isAgeEligible` directly — no tier, no gate, just the one boolean. When
      it is `false` (age under 13), go to `ageIneligible`. Otherwise go to `dietaryPattern` — DIET-01
      requires Q0b directly after age, unconditionally, for every user who clears the floor, with no
      exception case to carve out anymore.
    - From `ageIneligible`, while `answers.isAgeEligible` is still `false`, return `ageIneligible` again
      so the flow stays on the block screen — nothing advances until the user goes back to `age` and
      enters a qualifying value. There is no separate "waiting" state and nothing is persisted for the
      rejected attempt; once `answers.isAgeEligible` becomes `true`, `nextStep(after: .age, ...)` routes
      straight to `dietaryPattern` like any other user.
    - `dietaryPattern` → `privacyExplainer` → `calibrationIntro` → `calibrationSession` →
      `calibrationComplete`. Calibration is skippable per D-03: when `calibrationOutcome` is `.skipped`,
      route from `calibrationIntro` straight past the session to the step after `calibrationComplete`,
      never blocking.
    - After calibration, go directly and unconditionally to `screeningOpeningDisclaimer` — per D-15
      there is no capability gate here at all anymore. Every user who cleared the 13+ floor gets the
      complete safety screening (gate section, condition checklist, SCOFF) with zero parental
      involvement, identically to every other user above the floor.
    - `screeningOpeningDisclaimer` → `gateSection`. After `gateSection`, go to `clearanceInterstitial`
      when any of G1 through G7 is yes, otherwise straight to `conditionChecklist`. §1.2 requires the
      user proceeds to the checklist after either interstitial, so `clearanceInterstitial` →
      `conditionChecklist` unconditionally.
    - `conditionChecklist` → `severityFollowUps` when any category needing follow-ups was selected,
      otherwise `universalFollowUp`. `severityFollowUps` → `scoffFollowUp` when
      `answers.isSCOFFTriggered`, otherwise `universalFollowUp`. Per D-10 the SCOFF step is not shown to
      every user. `scoffFollowUp` → `universalFollowUp` → `screeningComplete` → `home`.

    There is no capability-gate type to consult anywhere in this function — `answers.isAgeEligible` is
    read once, at exactly one fork, and nothing downstream of `dietaryPattern` branches on age at all.

    Add `public static func isReachable(_ step: OnboardingStep, answers: OnboardingAnswers) -> Bool` by
    walking from `welcome` — the views use this rather than re-deriving reachability.

    Write `OnboardingFlowStateTests` covering CROSSGEN-05's no-fork guarantee at the routing level:
    - For a representative set of ages (8, 15, 40, 70), walk the flow from `welcome` to termination
      collecting every visited step, and assert every visited step is a case of `OnboardingStep`. Assert
      the traversals for 15, 40, and 70 are byte-for-byte identical — same steps, same order, zero
      divergence — and that only age 8's traversal differs, stopping at `ageIneligible`. This is the
      strongest form of the no-fork guarantee: not just "no separate hierarchy," but "no divergence at
      all" above the floor.
    - Assert an age-8 answer never advances past `ageIneligible` across repeated `nextStep` calls with
      the age unchanged, and that correcting the age to 13 or older on a subsequent call routes straight
      to `dietaryPattern`, exactly like any other user.
    - Assert `dietaryPattern` immediately follows `age` for every eligible age tested (13, 15, 40, 70).
    - Assert every eligible age reaches `gateSection` and `conditionChecklist` — there is no terminal
      point above the floor that a user can be routed to short of `screeningComplete`/`home`.
    - Assert `scoffFollowUp` is skipped when the eating-disorder item is unselected and visited when it is.
    - Assert a skipped calibration still reaches the step after `calibrationComplete`.
    - Assert `nextStep` is deterministic: identical answers yield identical results across repeated calls.
  </action>
