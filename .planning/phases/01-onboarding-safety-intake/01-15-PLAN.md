<objective>
Build ONBOARD-01's calibration experience: the intro with its skip action, the live session in both walk
and lift modes, and the completion screen.

Purpose: ONBOARD-01 exists to replace a self-reported fitness-level dropdown with a real session, so the
screens must never reintroduce one. D-02 requires the session work without a blocking location prompt,
which is why CoreMotion's pedometer is the default source and location is at most enrichment; and it
requires a manual stopwatch to work standalone, which also covers devices with no step-counting
hardware and the simulator, where sensor data does not exist. D-03 makes the whole thing skippable
without blocking anything. D-04 constrains the output: the session sets a pace zone and a safe starting
weight, and none of it is ever shown as a score, grade, or level.

The completion rules themselves are already implemented and tested in core. These sources feed that
rule; none of them decides completion independently.

Output: Two sensor-facing sources, a lift recorder, an opportunistic GPS enricher, three registered screens.
</objective>

    Create `PedometerSession` as an `@Observable` class conforming to `CalibrationSessionSource` with
    `mode` of `.walk`. It wraps `CMPedometer`, guarding every start with
    `CMPedometer.isStepCountingAvailable()` and reporting unavailability through a published property
    rather than failing silently — 01-RESEARCH.md's Pitfall 4 records that the hardware is absent on some
    devices and that the simulator produces no motion data at all, so this path cannot be exercised there.

    Use `startUpdates(from:withHandler:)` and accumulate elapsed time into a `WalkProgress`. Continuity
    matters: D-01 requires ten or more *continuous* minutes, so call `recordInterruption()` when updates
    stop arriving for longer than a short tolerance, or when the user pauses, which zeroes the
    accumulated duration and sets the interruption flag. Surface that flag to the view so a restart is
    explained rather than appearing as silently lost progress.

    This class requires only the motion usage description and must not touch CoreLocation. D-02 forbids a
    blocking location prompt in the critical path, and per Assumption A1 location is enrichment only:
    when the user has *already* granted location access, pace and distance may be displayed more
    precisely, but completion is decided solely from `CalibrationCompletion.evaluate`. Add a header
    comment recording that requesting location authorisation from this class would breach D-02, and do
    not call any authorisation request here.

    Create `StopwatchSession`, also `@Observable` and conforming to `CalibrationSessionSource` with
    `.walk`, driven by a timer with explicit start, pause, and resume. Pausing calls
    `recordInterruption()` for the same continuity reason. It must work standalone with no sensor and no
    permission of any kind, which is what makes it a genuine fallback rather than a degraded mode — this
    is also the only path exercisable in the simulator.

    Create `LiftSessionRecorder`, `@Observable`, conforming with `.lift`. It lets the user name or pick an
    exercise and record a working set, maintaining a `LiftProgress`. Record only working sets, not warm-up
    sets. Show live counts of total working sets and distinct exercises using `RithamType.numerals` so
    the values do not cause layout jitter as they tick.

    Create `LocationEnrichment`, `@Observable`, delivering the other half of D-02: the session is
    "measured via GPS/motion sensors when the user grants location access", with GPS layered on as
    enrichment per Assumption A1. It reads `CLLocationManager.authorizationStatus` and starts location
    updates ONLY when that status is already `.authorizedWhenInUse` or `.authorizedAlways`. When the
    status is `.notDetermined`, `.denied`, or `.restricted` it stays inert and publishes nothing.

    It must never call `requestWhenInUseAuthorization` or `requestAlwaysAuthorization`. This is the
    distinction that makes D-02 satisfiable in both directions: a user who has already granted location
    for some other reason gets more precise pace and distance, and a user who has not is never prompted
    and never blocked. Add a header comment stating that adding an authorisation request here would
    breach D-02's no-blocking-prompt rule, and that this type contributes display precision only —
    `CalibrationCompletion.evaluate` decides completion from `CalibrationProgress` alone, so a GPS
    dropout or a denied permission can never prevent a session from completing.

    Expose `isEnriching: Bool` and the derived pace and distance as optionals, so the session view can
    show the more precise values when present and the motion-derived values otherwise, without branching
    on permission state itself.

    None of the four may decide completion. Each source exposes `progress`, and the view asks
    `CalibrationCompletion.evaluate`. Add that as a header comment on each, noting the rule is already
    tested in core against both thresholds and a second judgement here could drift from it.

    Write `CalibrationSourceTests` asserting, without real sensors: `StopwatchSession` accumulates elapsed
    time from an injected clock and reaches completion at exactly six hundred seconds; pausing it records
    an interruption and zeroes the accumulation so it is no longer complete; `LiftSessionRecorder`
    reaches completion at exactly three working sets across two exercises and not at three across one;
    each source reports the mode it claims; and `PedometerSession` reports unavailable rather than
    crashing when step counting is unavailable. Also assert, with an injected authorisation-status
    provider: `LocationEnrichment` stays inert and publishes nothing for `.notDetermined`, `.denied`, and
    `.restricted`; it begins enriching for `.authorizedWhenInUse` and `.authorizedAlways`; and a walk
    session reaches completion identically whether enrichment is active or inert, which is the assertion
    that GPS is enrichment and not a gate. Inject the clock, the availability check, and the
    authorisation-status provider so all of this runs in the simulator.
  </action>
