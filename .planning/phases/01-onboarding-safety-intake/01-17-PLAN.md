<objective>
Build the remaining HEALTH-05 disclaimer surfaces, the health profile screen that gives them a home in
this phase, and the Settings surfaces for editing answers and handling the twelve-month re-screen.

Purpose: HEALTH-05 requires seven copy blocks at their defined touchpoints. Four are already rendered by
the screening flow. The remaining three — the persistent compact tag, its expanded form, and the
required-blocking message — attach to *adjusted suggestions*, which are HEALTH-03 and HEALTH-04 work in
Phase 2. They still belong in this phase as working components with a real surface, and 01-UI-SPEC.md
supplies that surface: its empty-state copy, "No health profile yet" with an invitation to complete the
screening to see condition tags and adjusted guidance, describes a health profile screen. That screen is
where D-11's transparency and D-12's list-every-matched-condition rule become visible to the user.

Settings closes HEALTH-02 and the editing decisions: D-09 scopes an edit to its own section, D-07 makes
the expiry reminder non-blocking, and D-08 keeps expired restrictions applying until the re-screen
actually happens.

Output: Three disclaimer components, the health profile screen, and the Settings surfaces.
</objective>

    Create `ConditionDisclaimerTag`, a view taking a `GateResolutionResult`. It renders
    `ScreeningCopy.compactDisclaimerTag(conditions:)` fed from `result.disclaimerConditionNames`.

    Per D-12 that list is every matched condition, not only the one whose gate currently binds. When two
    or more tags apply and a single most restrictive gate governs, the tag still names them all, because
    a user seeing only one condition would reasonably conclude the others are not affecting them. The
    result type already returns the full list; do not filter it down to the governing tag here.

    The tag is persistent and always visible on any adjusted suggestion, so it must not be collapsible to
    nothing, auto-dismissing, or hidden behind a scroll. Render its leading accent mark in coral, which
    01-UI-SPEC.md reserves for exactly this among other uses, with charcoal labels on any coral fill.

    Tapping expands `ScreeningCopy.expandedDisclaimer(conditions:)` in place. The expand affordance must
    be at least `RithamSpacing.minimumTapTarget` in both dimensions even though the tag is visually
    compact — 01-UI-SPEC.md lists this among its non-negotiable spacing exceptions. Give it an
    accessibility hint describing what expanding reveals.

    Render the tag at the `label` role and never below it. 01-UI-SPEC.md's floor rule names this element
    specifically: where it should read as fine print, use `RithamType.fineprint()` — reduced opacity at
    the label size — never a smaller point size. That rule is tied to the cross-generational mandate, not
    to taste.

    Create `RequiredBlockingMessageView` rendering `ScreeningCopy.requiredBlockingMessage` on an off-white
    card over flat charcoal, per the inventory. It replaces a suggestion within one domain and must never
    present as an app-level block: it may not cover the screen, prevent navigation, or offer only a dead
    end. §5's third governing principle keeps manual logging and generic information available
    throughout, and the copy itself tells the user they can still track manually — so the surface hosting
    it stays usable.

    Create `StandingFooterDisclaimer` rendering `ScreeningCopy.standingFooterDisclaimer` at the `label`
    role, to be placed wherever adjusted content appears. Do not shrink it; 01-UI-SPEC.md rules out the
    smaller text styles for this element by name.

    Write `DisclaimerTagTests` asserting against the copy and the result type rather than by rendering: a
    result with two matched tags where only one gate binds produces a tag string containing both display
    names; a result with one tag contains that one; `disclaimerConditionNames` is stable across repeated
    calls so the tag does not reorder between renders; the expanded string contains the condition names
    and the not-a-diagnosis phrasing; and `blocksPersonalization` is true for a blocked domain while
    `blocksAppAccess` remains false, which is the invariant the blocking view's non-covering presentation
    depends on.
