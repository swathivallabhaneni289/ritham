# Phase 1 — UI Design Contract

> Visual and interaction contract for Onboarding & Safety Intake. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Platform:** Native iOS (SwiftUI), iPhone only for v1. Must support both Dynamic-Island and non-Dynamic-Island devices, and full Dynamic Type scaling. No CONTEXT.md or RESEARCH.md existed for this phase at spec time — everything below is sourced from `.planning/REQUIREMENTS.md`, `.planning/sketches/` (rounds 002/003), `docs/mascot.md`, and `docs/health-screening.md`, or is an explicit default called out as such.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — native SwiftUI, no npm/shadcn/component-registry tooling applies to this platform |
| Preset | not applicable |
| Component library | SwiftUI native controls only (`Button`, `TextField`, `Picker`, `List`, etc.) — no third-party Swift UI package targeted for Phase 1 |
| Icon library | SF Symbols |
| Font | SF Pro (system default) via Dynamic Type — no custom typeface |

**Theme mode:** Phase 1 ships as a single fixed dark (charcoal-dominant) theme, not driven by the system's light/dark appearance setting. This is a default, not an upstream-locked decision — it follows directly from sketch 003's confirmed charcoal-dominant palette (the same "dark-first" choice WHOOP/Peloton made). Flag for future confirmation: sketch 002's research noted Peloton shipped dark-only in Oct 2025 and reversed within 4 weeks after backlash — a true system-light-mode variant is an open item for a later phase, not required for Phase 1's screening/onboarding flow.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding |
| sm | 8px | Compact element spacing (e.g. between a checklist row's label and its checkbox) |
| md | 16px | Default element spacing, standard screen margin |
| lg | 24px | Section padding (e.g. between the gate-question framing line and Q1) |
| xl | 32px | Layout gaps (e.g. between the disclaimer block and the first question) |
| 2xl | 48px | Major section breaks (e.g. above/below a clearance interstitial's CTA) |
| 3xl | 64px | Page-level spacing (e.g. top inset on the welcome/hero screen) |

Exceptions:
- **44×44pt minimum tap target** for every icon-only control (the compact disclaimer tag's expand affordance, back/close buttons, Yes/No toggle chips) — Apple HIG floor, non-negotiable given the cross-generational requirement (teens through grandparents on identical controls).
- No other exceptions.

## Typography

Mapped to SwiftUI semantic Dynamic Type styles at the default (Large) size class. Exactly 4 sizes, 2 weights, per the design-contract limit.

| Role | SwiftUI Style | Size (pt, @Large) | Weight | Line Height |
|------|---------------|--------------------|--------|-------------|
| Display | `.title` | 28 | Semibold | 1.2× |
| Heading | `.title2` | 22 | Semibold | 1.2× |
| Body | `.body` | 17 | Regular | 1.5× |
| Label | `.callout` | 16 | Regular | 1.5× |

**Floor rule:** nothing renders below `.callout` (16pt default). This explicitly rules out `.footnote` (13pt) and `.caption`/`.caption2` for **any** Phase 1 element — including the standing footer disclaimer (§Copywriting, 4.7) and the persistent compact disclaimer tag (4.4). If either needs to visually read as "fine print," achieve that with color/weight (e.g. Label-role at reduced opacity on off-white), never with a smaller point size. This is a direct requirement of the cross-generational mandate — no age-segmented "senior mode" also means no separate small-type track that only younger users are assumed to read comfortably.

**Numerals:** SF Pro's default (non-rounded) numeral style only. Locked from sketch 002 round-2 research: no `ui-rounded`/SF Rounded numerals anywhere in the app — that reads gamer/toy-coded, which is exactly what round 1 (Duolingo-adjacent) was rejected for. Any ticking/counting value (e.g., a future session timer) uses `.monospacedDigit()` to prevent layout jitter, not a rounded typeface.

**Reflow rule:** at accessibility text sizes (AX1–AX5), no text may be composited on top of a diagonal band or the halftone texture (see Decorative Surface Inventory below) — the header/hero region housing the band motif must be independently sized via `GeometryReader` and allowed to compress or drop out of layout, with text content reflowing onto the flat charcoal/off-white field beneath it. Test at AX3 minimum before considering a screen done.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0E100D` (charcoal) | Base background field for every screen in this phase |
| Secondary (30%) | `#F5F3EC` (off-white) | Elevated surfaces (interstitial cards, checklist rows, sheet backgrounds), and the primary text color for content sitting on charcoal |
| Accent — Coral (10%) | `#FF5C39` | Reserved for: primary CTA button fill ("Continue," "Start calibration session," "I understand — continue"), the selected/active state of a Yes/No or checklist chip, the compact disclaimer tag's leading accent mark |
| Accent — Lime | `#C6F24E` | Reserved for: the static ring-and-dot brand ornament only (never a progress/completion indicator — see decision below), and a one-off affirmation micro-accent on the "Good to know — you're clear to move on" gate-pass moment |
| Destructive | `#FF3B30` (iOS system red) | Reserved for future phases — **not used on any Phase 1 screen.** Phase 1 has no destructive action (editing an answer is a normal edit, not a delete/irreversible action). Record here so a later phase doesn't improvise a different red. |

**Accent discipline:** Coral and lime are each reserved for the specific elements listed above — never used interchangeably, never as a decorative wash, never covering more than a thin diagonal band or a small ornament at any given time (carrying forward sketch 002's hard rule: "amber [replaced by coral/lime] is a signal, never a decorative surface").

### Contrast Verification

Computed WCAG 2.1 relative-luminance contrast ratios for every color pair actually used for text/icons in this phase:

| Pair | Ratio | AA (4.5:1 normal / 3:1 large) | AAA (7:1 normal / 4.5:1 large) |
|------|-------|-------------------------------|----------------------------------|
| Off-white `#F5F3EC` text on charcoal `#0E100D` | 17.2:1 | Pass | Pass |
| Acid lime `#C6F24E` text/icon on charcoal `#0E100D` | 14.8:1 | Pass | Pass |
| Coral `#FF5C39` text/icon on charcoal `#0E100D` | 6.2:1 | Pass | Pass (large text only) |
| Charcoal `#0E100D` text/icon **on** coral `#FF5C39` fill | 6.2:1 | Pass | Pass (large text only) |
| Charcoal `#0E100D` text/icon **on** lime `#C6F24E` fill | 14.8:1 | Pass | Pass |
| **Off-white `#F5F3EC` text/icon on coral `#FF5C39` fill** | **2.8:1** | **Fail** | Fail |
| **Off-white `#F5F3EC` text/icon on lime `#C6F24E` fill** | **1.2:1** | **Fail** | Fail |

**Binding rule:** coral and lime are both light-luminance colors relative to charcoal. Any filled surface using coral or lime (a coral CTA button, a lime-accented chip) must use **charcoal** text/icon labels — never off-white, which is the intuitive-but-wrong default and fails contrast badly on both. Off-white is only for text/icons placed directly on the charcoal field, never on a coral or lime fill.

## Visual Motif — SwiftUI Re-Expression

Sketch 003's `background.svg`/`theme.css` (charcoal/coral/lime/off-white bands at ~57°, halftone corner, concentric arcs, ring-and-dot) is a **design spec, not a drop-in asset**. It was authored as a 1440×720 landscape SVG with CSS custom-property theming (`:root { --band-hot: ... }` + `.band-hot { fill: var(...) }`). Neither the coordinate space nor the CSS mechanism ports directly to a native iPhone portrait screen. Two concrete translation requirements:

1. **Replace CSS custom properties with a Swift theme object**, not per-view hardcoded hex values:

```swift
enum RithamColor {
    static let ink   = Color(hex: 0x0E100D) // charcoal — dominant
    static let hot   = Color(hex: 0xFF5C39) // coral — primary accent/signal
    static let volt  = Color(hex: 0xC6F24E) // acid lime — secondary accent/ornament
    static let paper = Color(hex: 0xF5F3EC) // off-white — secondary surface/text-on-dark
}
```

2. **Recompute the flat-margin geometry for the actual render target — do not port sketch 003's polygon coordinates verbatim.** Sketch 003 verified computationally (not just visually) that its 1440×720 canvas leaves ~25% flat charcoal on the left and ~20% on the right at every visible row, using `xMidYMid slice` to crop for different aspect ratios. Slice-cropping that same coordinate space to a ~390×844 portrait viewport keeps the *middle* of the composition and discards both flat margins — producing a screen that's mostly diagonal band with no clear space for text. That is a real bug, not a hypothetical one, if the polygon points are copied as-is.

   The correct approach: bound the band motif to a **fixed-height header/hero region** (recommend 220–280pt tall) at the top of applicable screens, not a full-screen bleed. Draw it as a custom `Shape` that recomputes its own polygon points from the header rect's actual width/height at render time:

```swift
struct BandMotif: Shape {
    let angleDegrees: Double = 57 // fixed, matches sketch 003 — "steep," not a literal 45°

    func path(in rect: CGRect) -> Path {
        // Re-derive left/right flat-margin fractions for THIS rect's own
        // aspect ratio — sketch 003's ~25%/~20% figures were solved for a
        // 1440×720 canvas and do not transfer as-is. Re-run the same
        // edge-crossing computation described in sketch 003's README
        // ("Geometry note") against the header rect's real dimensions
        // before shipping, and verify computationally, not by eye.
        ...
    }
}
```

   Below the header region, the rest of the screen is flat charcoal (or an off-white card) — the guaranteed content-safe area for headline, body copy, and CTAs. This is the mechanism that prevents the portrait-crop bug: text never depends on the band composition leaving room for it, because text lives outside the bounded header entirely.

## Decorative Surface Inventory

Locked decision #3 (screening screen stays "flat/restrained/no-illustration") is about more than Momo — it governs the band motif too. Per-surface decision:

| Screen | Band motif (header) | Halftone | Arcs | Ring-and-dot | Momo |
|--------|:---:|:---:|:---:|:---:|:---:|
| Welcome / hero | Yes | Yes (corner) | Yes | Yes | Yes (hero art) |
| Explanation-register picker | Yes (bounded header only) | No | No | Optional (small, corner) | No |
| Age (Q0) / dietary pattern (Q0b) | No — flat charcoal only | No | No | No | No |
| Privacy explainer | Yes (bounded header only) | No | No | Optional | No |
| Under-13 halt / parent-consent step | No — flat charcoal only | No | No | No | No |
| 13–17 partial-gate notice | No — flat charcoal only | No | No | No | No |
| Calibration start / complete | Yes | No | No | Yes | Yes (functional glyph or hero, per §Momo below) |
| Gate section (G1–G7) | No — flat charcoal only | No | No | No | No |
| Routine / urgent clearance interstitial | No — flat charcoal + off-white card only | No | No | No | No |
| Condition checklist | No — flat charcoal only | No | No | No | No |
| SCOFF follow-up (ED-1–ED-5) | No — flat charcoal only | No | No | No | No |

**Rule:** any screen that collects, confirms, or blocks on health/consent data stays flat charcoal — no bands, no halftone, no arcs, no Momo. Decorative surface is reserved for welcome, explanation/register choice, privacy explainer, and the calibration flow, matching locked decision #3's intent applied consistently across the whole motif system, not just the mascot.

## Ring-and-Dot vs. Apple Activity Rings — Decision

Locked decision #2 requires an explicit call, not an open item. **Decision: differentiate by function, not by form.**

- Sketch 002's carried-forward hard rule already forbids using a ring/badge/bloom shape as a *progress or completion indicator* anywhere in the app (data forms — bar strips, block grids — are used for Momentum instead, per that research).
- Sketch 003's ring-and-dot is a single thin lime stroke ring with one solid center dot, rendered as a **static brand ornament** in a flat safe zone — it never fills, animates, or represents a fraction of anything.
- Combined, these two facts mean the ring-and-dot never appears in a context (progress ring, streak ring, loading indicator) where a user could plausibly read it as "3 concentric Activity-Rings-style rings tracking daily goals." It is decorative typography, not a data widget, and Apple's rings are always three, always closing/filling, always representing move/exercise/stand.
- **Binding rule:** the ring-and-dot motif may only appear as a static, non-data-bearing ornament (per the Decorative Surface Inventory above). It must never gain a second concentric ring, must never visually fill/progress, and must never sit adjacent to or represent Momentum/streak data. If a future phase needs a genuine progress ring for some other purpose, that is a new design decision requiring its own vetting — this ornament does not become one by extension.

## Momo Placement & Style

MANIFEST.md flags Momo's placement against the sketch-003 palette as untested since round 2. Recommendation, drawing on sketch 002's closest analog (Afterburn — near-black instrument-panel dark mode, where Momo needed "a bounded, warm-lit portrait card, not floated over live data"):

- **Momo sits in a bounded inset card** (rounded rect, off-white or subtly warm-lit charcoal card) on the flat charcoal field — never floated directly over a diagonal band, the halftone texture, or the concentric arcs. The reasoning carries forward directly: semi-realistic painted illustration and hard-edged flat neo-brutalist vector are a genuine style collision when overlapped; bounding Momo in his own card resolves it the same way it did in round 2.
- Applies at: welcome/hero screen (full hero art, largest card) and calibration start/complete (functional glyph or a smaller hero card, per the two-tier asset system in `docs/mascot.md` §1).
- Momo never appears on any screen in the flat-charcoal-only row of the Decorative Surface Inventory above (per locked decision #3).
- **Correction needed before art handoff:** `docs/mascot.md` §1a still justifies Momo's ginger coat by tying it to "the warm amber/ember used throughout the app" — that rationale is superseded by locked decision #4 (Momo's coat color is independent of whichever functional accent color the app uses; the app's accent is now coral/lime, not amber). The illustrator brief should be corrected to drop that sentence before art is commissioned; the coat stays ginger for its own sake, not as an accent-matching choice.
