# Phase 4 — UI Design Contract

> Visual and interaction contract for `HomeHubView`'s replacement: a real, sectioned dashboard
> (CROSSGEN-01), not a vertical button list. Generated by gsd-ui-researcher, verified by
> gsd-ui-checker. Scope is the visual/interaction contract only — refactor mechanics
> (content-extraction, file placement, xcodegen regeneration, test-file coupling) belong to
> `04-RESEARCH.md` and the planner; this document states the resulting *look and behavior* those
> mechanics must produce.
>
> **Checkpoint revision (2026-09-08):** Task 3's human-verification checkpoint produced direct
> layout/interaction feedback that changes three things this document originally locked:
> (1) Momentum and sleep now sit in a two-column grid row instead of two full-width stacked
> cards — "rather than keeping them all stacked one after the other." (2) The workout-plan and
> diet-plan sections are compact tap-to-open summary cards (a `Button`-wrapped card presenting a
> sheet on tap) rather than always-inline embeds — "the details... should only open when I click
> the [option]." (3) The exercise section gained a small leading SF Symbol per session row,
> matching Apple Fitness's icon-plus-row list shape — the Ring Collision rule below still forbids
> a data-bearing ring/arc anywhere on this screen, so the icon is a static glyph, not a progress
> indicator. See 04-CONTEXT.md's dated D-04/D-05 revisions for the full decision record. The
> original locked contract below is retained for context; the Layout & Section Contract and
> Copywriting Contract sections carry inline notes marking exactly what each revision supersedes.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — native SwiftUI/iOS project (Swift 6.3.3, iOS 17.0 floor). The shadcn initialization gate applies only to React/Next.js/Vite projects and is not applicable here. |
| Preset | not applicable |
| Component library | First-party only, locked since Phase 1: `RithamScreen` (screen scaffold), `PrimaryCTAButton`/`SecondaryCTAButton`, `ChoiceQuestionView`, `MomentumProgressBlocks`, `ShieldRow`. No `List`/`Form` exists anywhere in the codebase and none is introduced this phase (04-RESEARCH.md Alternatives Considered). |
| Icon library | SF Symbols only (e.g. `shield.fill`/`shield` in `ShieldRow`). No custom icon asset system exists. |
| Font | SF Pro system font via `RithamType`'s four-role scale. Non-rounded numeral style only — `RithamType.numerals()` (`.monospacedDigit()`) on every ticking/counting value, never a rounded typeface. |

This phase introduces **zero new design-system primitives**. Every token, color, and type role
below already exists in `RithamColor.swift`/`RithamType.swift`/`RithamSpacing.swift`
(Phase 1, `01-UI-SPEC.md`) and is transcribed here, not reinvented. The one new visual pattern this
phase adds is the **section-card wrapper** (see Color, "Dashboard Section Card" below) — a
composition of existing tokens, not a new primitive.

## Spacing Scale

Declared values (existing `RithamSpacing` tokens — multiples of 4, unchanged):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4pt | Icon gaps, inline padding |
| sm | 8pt | Compact element spacing; section-card corner radius |
| md | 16pt | Default element spacing; screen margin; section-card internal padding; inter-section gap |
| lg | 24pt | Section-internal padding (e.g. within a card, above a sub-heading) |
| xl | 32pt | Layout gaps (not expected on the dashboard itself) |
| 2xl (xxl) | 48pt | Major section breaks (not expected on the dashboard itself) |
| 3xl (xxxl) | 64pt | Page-level spacing (not expected on the dashboard itself) |
| minimumTapTarget | 44pt | Every tappable control on the dashboard (cards' inline actions, "see all"/CTA affordances) — non-negotiable per the cross-generational mandate |

**Dashboard-specific rule:** the vertical gap between sibling section cards is `RithamSpacing.md`
(16pt) — the same value `HomeHubView`'s existing outer `VStack(spacing: RithamSpacing.md)` already
uses. Do not tighten it to `sm` to fit more sections above the fold; density is not a stated goal
and would work against the "scannable at a glance" requirement (04-CONTEXT.md specifics).

Exceptions: none.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Display | 28pt (`.title`) | Semibold | System default for `.title` |
| Heading | 22pt (`.title2`) | Semibold | System default for `.title2` |
| Body | 17pt (`.body`) | Regular | System default for `.body` |
| Label | 16pt (`.callout`) | Regular | System default for `.callout` — **the floor**; nothing on this screen may render smaller |

**Dashboard-specific rules (extending the existing, locked type-scale contract):**

- **Section headings** (e.g. "This week's activity," "Sleep," "Your workout plan," "Diet plan")
  use `RithamType.heading` (22pt Semibold) — one level below the screen's own `RithamType.display`
  headline, so the visual hierarchy reads screen title → section heading → body content, never
  four section headings competing with the screen headline at the same size.
- **No `.caption`/`.caption2`/`.footnote` anywhere in any new dashboard code**, including session
  timestamps in the exercise section and the verification label ("Sensor-verified"/"Manually
  entered"). This is a hard carry-forward of `RithamType`'s own file-header rule, and it directly
  forecloses the most natural-looking mistake on a dense dashboard: a small grey timestamp under
  each session row. Use `RithamType.label` (16pt) for any secondary/metadata text; if it needs to
  read as de-emphasized, apply `RithamType.fineprint()` (opacity reduction on the same 16pt floor)
  — never a smaller point size.
- Every ticking/counting numeral (streak count, weekly progress count, shield count, any future
  step/calorie count) uses `RithamType.numerals()`, unchanged from existing Momentum components.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `RithamColor.ink` (#0E100D, charcoal) | Screen background (`RithamScreen`'s own `ZStack` base) — unchanged |
| Secondary (30%) | `RithamColor.paper` (#F5F3EC, off-white) | Primary text/label color on charcoal; secondary surface tint inside section cards (see below) |
| Accent (10%) | `RithamColor.hot` (#FF5C39, coral) | Reserved for: the primary CTA fill (`PrimaryCTAButton`), the weekly progress blocks' filled state (`MomentumProgressBlocks`), the shield-earned glyph fill (`ShieldRow`) |
| Destructive | `RithamColor.destructive` (#FF3B30, iOS system red) | Not used this phase — the dashboard has no destructive action (per 01-UI-SPEC.md precedent, recorded so a later phase does not improvise a different red) |

**Locked rules this phase must not violate (already structural in `RithamColor.swift`):**

- `RithamColor.volt` (#C6F24E, acid lime) is reserved for the static ring-and-dot ornament only —
  **never** a data-bearing progress indicator anywhere on the dashboard. This forecloses the most
  likely "Apple Health" instinct: a lime activity ring. No section on this dashboard renders a
  ring, arc, or radial progress form of any kind (see also the Ring Collision rule below).
- Label color on any coral (`hot`) or lime (`volt`) fill must go through `RithamColor.label(on:)`
  — never a hardcoded `paper` label on those two fills (paper-on-hot measures 2.8:1, paper-on-volt
  1.2:1, both AA failures per `RithamColor.swift`'s own measured contrast table).

**Dashboard Section Card** (new composition pattern, extending — not matching — the
`ReScreenBanner.swift` precedent):

| Property | Value |
|----------|-------|
| Fill | `RithamColor.paper.opacity(0.06)` |
| Corner radius | `RithamSpacing.sm` (8pt), via `.clipShape(RoundedRectangle(cornerRadius:))` — matches the existing rounded-rect convention used by `PrimaryCTAButton`/`SecondaryCTAButton`/`ReScreenBanner` |
| Internal padding | `RithamSpacing.md` (16pt) |
| Label color inside the card | `RithamColor.paper` (full opacity, unchanged from the rest of the screen) — the card fill is a subtle tint on charcoal, not an inverted-to-paper surface |

This is a deliberate departure from `ReScreenBanner`'s own treatment (solid `RithamColor.paper`
fill with `RithamColor.ink` labels): `ReScreenBanner` is a single, occasional, attention-getting
banner; a dashboard with four-plus always-visible sections rendered as solid off-white slabs would
invert the 60/30/10 split (four large paper fields competing with the charcoal background) and
clash with every other screen in the app. A low-opacity paper tint on ink preserves `paper`-on-`ink`
text contrast (17.2:1, unchanged from the base screen) while giving each section a barely-visible
seam — enough to read as a grouped region, not enough to read as a colored card.

**Accent reserved for:** the primary CTA fill (log/track/plan-request actions), `MomentumProgressBlocks`' filled-week blocks, and `ShieldRow`'s earned-shield glyphs. Never a section-card fill, never a section heading, never a badge/dot/status indicator anywhere on this screen.

## Layout & Section Contract

The screen keeps `RithamScreen(surface: DecorativeSurface.boundedHeaderOnly, ...)` — the same
surface `HomeHubView` uses today. `.boundedHeaderOnly` sets `ringAndDot: true` (a small static
lime ring-and-dot ornament in the header corner); no section body may introduce a second ring, arc,
or radial motif anywhere in the scrollable content below it, per `MomentumProgressBlocks`' own
documented "two circular motifs in one viewport" collision rule.

**Screen headline/body copy:** delete `HomeHubView`'s existing "Your interim home" headline and
"This is a temporary hub..." body text entirely (04-RESEARCH.md's State of the Art table marks
this copy explicitly deprecated; D-01 requires the interim-hub framing gone "in shape or in
spirit," not just its button list). Replace with a headline that reads as a real home screen, not
an apology for a placeholder — e.g. a plain "Home" or a time-of-day-neutral greeting. Exact
wording is Claude's Discretion at plan time; the constraint is that no user-facing copy anywhere
on this screen may describe it as temporary, interim, or a placeholder.

**Section order (top to bottom), fixed by the adjacency rules below — this is not open
arrangement discretion:**

1. **Momentum summary section** — carried forward from `HomeHubView`'s existing `momentumSection`
   (progress blocks, streak line, shield row), re-parented per D-06/04-RESEARCH.md Pitfall 2 into
   its own component file. Visually: one Dashboard Section Card containing
   `MomentumProgressBlocks`, the streak-line text (`RithamType.heading` + `numerals()`), and
   `ShieldRow`, in that vertical order — unchanged internal layout from today's `momentumSection`.
2. **Sleep check-in section** — a Dashboard Section Card whose only content is
   `MomentumCopy.Sleep.headline` ("How did you sleep?") as the card's own heading-weight text and
   a single tap affordance opening `.sleepCheckIn`. **No completed/skipped indicator of any kind**
   — see RECOVERY-01 Invariant row below.
3. **Exercise / logged-activity section** — a Dashboard Section Card listing `MomentumSummary
   .recentSessions` (`MomentumSessionEntry`: title, `startedAt`, `verificationLabel`, `qualifies`),
   read through `MomentumSummaryReader` exactly as today, never re-derived. Each row shows the
   session title and, when present, the verification label
   (`MomentumCopy.Verification.sensorVerified`/`.manuallyEntered`) at `RithamType.label` — not
   `.caption`. Below the list (or in place of it, when `recentSessions.isEmpty`), the section
   carries the log-entry actions currently on `HomeHubView` as bare buttons: "Track cardio," "Log
   strength," their history entry points, and the Daily Movement Snapshot opt-in-gated entry
   (`HomeHubView.showsMovementSnapshotEntry`) — placed here, adjacent to exercise logging, per
   04-RESEARCH.md Pitfall 6's locked adjacency rule (the Movement Snapshot entry must never be the
   Momentum section's visual neighbor; this section boundary is what keeps it non-adjacent).
4. **Workout-plan section** — a Dashboard Section Card embedding `RecommendationsSectionContent`
   (the extracted `RecommendationsView` body) directly, per D-04. Idle/loading/plan/error states
   render inline inside the card exactly as `RecommendationsView` renders them today (see States
   table below) — no navigation away.
5. **Diet-plan section** — a Dashboard Section Card embedding the DIET-01-isolated subset of
   `DietPlanView` (dietary-pattern picker, optionally the allergen multi-select) per D-05's
   narrowed scope. The food-allergy screening checkbox and its severity follow-up stay off this
   card entirely (Pitfall 3) — this section never calls `GateResolution.resolve`.
6. **Guidance and Settings entry points** — remain reachable, but as a single small overflow-style
   affordance (existing gear/overflow pattern for Settings, a plain secondary action for Guidance),
   not as full-width `PrimaryCTAButton`/`SecondaryCTAButton` rows appended below the sections. This
   is what keeps D-01's "not a vertical list, in shape or in spirit" true at the bottom of the
   screen as well as the top — a leftover button stack under real sections is the same rejected
   pattern with extra steps.

**Forward-compatibility note (D-08):** the section list above is an ordered, uniform stack of
Dashboard Section Cards specifically so a future steps/calories card can slot in (most naturally
after section 3) without a layout redesign. Do not build a placeholder, "coming soon," or
empty-state card for steps/calories now — leave room structurally, show nothing.

**Card-vs-button-list discriminator (the actual test of D-01 compliance):** every section must
render real content above any action control — progress blocks, session rows, plan session rows,
or a diet-pattern selector — never a card whose only content is a heading and a
`PrimaryCTAButton`. A dashboard of four coral-topped buttons in rounded boxes is the same rejected
screen with corners softened. Cap primary-fill buttons (`PrimaryCTAButton`) to the genuine
data-entry actions from D-07 (Track cardio, Log strength, and the plan/diet sections' own
request/retry actions) — do not give every section its own primary-fill "open" button when the
section already shows its content inline.

## Interaction / State Contract

Per 04-CONTEXT.md D-08's "no dashboard-specific aggregate view model" rule, each section loads and
fails independently — there is no single "dashboard loading" or "dashboard error" state. Per-section
states:

| Section | Idle/empty | Loading | Error |
|---------|-----------|---------|-------|
| Momentum summary | n/a (always has a value once loaded) | brief blank card until `onAppear` resolves — no spinner needed for a synchronous local read | `OnboardingCopy.Errors.savingFailed`, `RithamType.body`, `paper` — unchanged from today's `momentumLoadFailed` branch |
| Sleep check-in | n/a — this section is a static entry point, never reflects check-in state (see RECOVERY-01 row below) | n/a | n/a |
| Exercise/logged-activity | `MomentumCopy.Empty.noSessionsHeadline` / `.noSessionsBody`, unchanged | n/a (reads from the same already-loaded `MomentumSummary`) | shares the Momentum summary's error state above (same read call) |
| Workout-plan | `RecommendationsSectionContent`'s existing idle copy ("Get a plan built around your stored weekly frequency and starting point." + "Get my plan" CTA) | `ProgressView("Building your plan...")`, `paper` | "We couldn't reach the plan service. Check your connection and try again." + "Retry" CTA — unchanged, all existing strings |
| Diet-plan | n/a — a picker always has a selection (defaults to `DietaryPattern.none`) | n/a | `OnboardingCopy.Errors.savingFailed` on a failed persist, matching `DietPlanView`'s existing `showSaveError` pattern |

**RECOVERY-01 Invariant 3 as a screen-wide visual rule:** no badge, dot, checkmark, count, or any
other completed/incomplete visual state may ever appear on the sleep section, or be derived from
sleep check-in history anywhere else on this screen. A skipped check-in must remain indistinguishable
from a day the prompt was never shown. This rule extends past the sleep card itself: do not add a
"logged today" indicator to any other card as a side effect of dashboard-izing the layout (e.g. no
green dot on the exercise card implying "sleep also logged").

**MOMENTUM-06 no-sharing rule (screen-wide):** no `ShareLink`, `UIActivityViewController`,
`UIPasteboard`, invite affordance, or copy-link control anywhere on this screen, in any section —
not just the Momentum card. This is asserted structurally by `Phase3CoverageTests`' directory-walk
gate once the Momentum section is relocated per Pitfall 2; the visual contract restates it here so
no section (e.g. a future "cheer" affordance from a later Household round) is designed against this
screen without the constraint in view.
