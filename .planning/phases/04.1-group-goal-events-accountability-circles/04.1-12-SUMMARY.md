# Phase 04.1 Plan 12: Group Feed, Cheers, and Export Consent Summary

**A Go `internal/feed` package (membership-JOIN-scoped, cursor-paginated group/event feed with no aggregate field; a fixed two-value count-free cheer mechanic; a per-visible-person export-consent gate over the existing `photo_export_consents` table), migration `0006_feed`, and seven authenticated routes, all guarded by a JSON key-set pin plus a structural no-denominator source gate.**

## Accomplishments

- `internal/feed.Service`: `GroupFeed`/`EventFeed` join `group_members` on the *viewer's* own id as part of the feed SQL itself (never the completion author's, so a keep-posts leaver's past completions still appear); a same-package test (`TestGroupFeedRows_NonMemberQueryItselfReturnsZeroRows`) calls the raw, unexported query directly and proves it returns zero rows for a non-member against a group holding real completions -- the membership condition can't silently migrate out of the SQL without this test catching it.
- Keyset cursor pagination on `(posted_at, id)` descending, opaque base64-encoded, fetching `limit+1` rows to detect a next page with no separate count query. `TestGroupFeed_CursorPaginationIsDisjointAndTerminates` pages through five completions two at a time and asserts every completion is seen exactly once and the final page's cursor is empty.
- `Page`/`Item` structs carry no total, remaining count, member count, or completion fraction -- reflection-asserted (`TestPage_HasNoTotalOrCountField`) and JSON-key-set-pinned (`nodenominator_test.go#TestPageJSONKeySet`, which lives in package `feed` since `httpapi` imports `feed` and the reverse import doesn't exist).
- Cheers (`cheers.go`) are Ritham's first cheer implementation: exactly two accepted values (`niceWork`/`keepGoing`, matching `RithamCore.Cheer`'s own raw values byte-for-byte), idempotent by `completion_cheers`' own composite primary key (`ON CONFLICT DO NOTHING`, not a pre-check), and authorized through the identical `requireVisibleCompletion` visibility test the feed itself uses. `TestViewerCheers_OneUsersCheerChangesNothingObservableForAnother` proves one user's cheer never leaks into another's own `ViewerCheers` view.
- Export consent (`exportconsent.go`) builds entirely on the `photo_export_consents` table migration `0002_photos` already shipped -- no new schema. `RequestExportConsent` is owner-only and records one pending (`granted_at IS NULL`) row per subject; `GrantExportConsent` is subject-only and requires a pending row to exist (`ErrExportConsentMissing` otherwise, so nobody can pre-emptively grant consent for a photo they were never asked about); `ExportAllowed` opens only when every recorded subject has granted, and is allowed immediately when none were ever recorded.
- `internal/httpapi/feed_handler.go`: seven routes encoding `feed.Page`/`feed.Item` directly as the wire response (no second translation struct -- one struct definition is the whole wire-shape promise). `statusForFeedError` maps not-a-member->404, unknown cheer->400, consent-missing->409, not-photo-owner->403 (see Deviations for the deliberate divergence from `statusForEventsError`'s own not-photo-owned->404 precedent).
- `internal/feed/nodenominator_test.go`: Half 1 pins the exact JSON key set of a fully populated `Page` (including nested `Item`/`Person`/`ViewerCheers`); Half 2 walks `internal/feed` and `internal/httpapi` (10 files scanned, above the 6-file floor) and fails on denominator/ranking-shaped identifiers (`total`, `denominator`, `fraction`, `percent`, plus `rank`/`score`/`leaderboard`/`position`/`winner` reused from `internal/events`' own gate) and SQL aggregate functions -- deliberately excluding bare `count` and `memberCount`, which are already-shipped, legitimate figures elsewhere in `internal/httpapi`.

## Decisions Made

- **`ErrNotAMember` is a true alias of `groups.ErrNotAMember`, not a fresh sentinel.** `var ErrNotAMember = groups.ErrNotAMember` keeps `errors.Is(err, groups.ErrNotAMember)` working everywhere else in the codebase that checks the original, matching `internal/events`' own precedent of surfacing the membership gate's sentinel unchanged rather than restating it.
- **Query-first, gate-on-zero-rows ordering.** `GroupFeed`/`EventFeed` run their membership-joined SQL first and only consult a direct `isGroupMember`/`groupIDForEvent` lookup when zero rows come back, to disambiguate "member with an empty feed" from "not a member." This keeps the JOIN the actual, load-bearing authorization mechanism a test can assert directly (`TestGroupFeedRows_NonMemberQueryItselfReturnsZeroRows`), rather than dead code behind a preceding gate call that a later refactor could make unreachable without any test noticing.
- **Photo URL resolution never goes through `photo.Service.Asset`.** That method is deliberately scoped to the requester's own uploads (`WHERE id = $1 AND owner_user_id = $2`) and would reject every other group member's photo. The feed query instead `LEFT JOIN`s `photo_assets` directly for `shared_object_key`, and `main.go` wires `feed.Service` from the object store (which already satisfies `PhotoURLSource`), not from the photo service.
- **`GrantExportConsent` requires a pre-existing pending row.** Rather than upserting unconditionally, granting for a `(photoAssetID, subjectUserID)` pair with no matching pending `photo_export_consents` row returns `ErrExportConsentMissing` -- a subject cannot pre-emptively grant consent for a photo nobody has asked them about yet.
- **`nodenominator_test.go`'s forbidden-word list excludes `memberCount`/`member_count` and bare `count`.** An initial version of this gate (matching the advisor's suggested word list literally) failed against `internal/httpapi/groups_handler.go`'s already-shipped, legitimate `GroupDetailResponse.MemberCount` (plan 04.1-08, a group roster size, not a completion-based denominator) and `RSVPStateResponse.Count` (plan 04.1-10, an already-permitted pre-event headcount). The gate now forbids only `completionCount`/`completion_count` and `cheerCount`/`cheer_count` -- the two compound forms that would actually be new aggregate figures this plan is about -- plus the ranking/denominator bare words (`rank`, `score`, `leaderboard`, `position`, `winner`, `total`, `denominator`, `fraction`, `percent`).
- **`ExportAllowed`'s `exporterUserID` parameter is currently unused inside the method body.** It matches this plan's own artifact signature and every route sits behind `RequireSession` regardless, so no unauthenticated caller can reach it; the parameter is kept for a future caller-scoped restriction without an API break, documented inline rather than silently dropped.
- **GROUPEVENTS-05 is NOT marked complete.** The plan's own frontmatter lists both `GROUPEVENTS-04` and `GROUPEVENTS-05` as requirements, but this plan's objective text is explicit that the digital finisher certificate (the actual GROUPEVENTS-05 deliverable) is a separate future surface built on top of `Completion`'s existing fields and this plan's export-consent gate -- 04.1-10-SUMMARY.md already flagged the certificate itself as out of scope. Marking GROUPEVENTS-05 complete here would misrepresent what shipped; only `GROUPEVENTS-04` is marked complete (idempotently -- it was already marked complete in `REQUIREMENTS.md` from an earlier plan, apparently prematurely relative to this plan's own delivery; not investigated further as out of this plan's scope).

## Next Phase Readiness

- `internal/feed.Service` is ready for a future plan building the digital finisher certificate (GROUPEVENTS-05): `ExportAllowed`/`RequestExportConsent`/`GrantExportConsent` are the complete export-consent gate that certificate generation will call before letting an image leave Ritham, and `events.Completion`'s existing fields (`EventID`, `User`, `CompletedAt`, `OwnTimeSeconds`) already carry everything the certificate's "what's on it" list requires (per 04.1-10-SUMMARY.md's own note).
- The `event_completions(event_id, posted_at)` index (this plan's migration) fully covers `EventFeed`'s query path but not `GroupFeed`'s -- `GroupFeed` pages across every event in a group via a join through `goal_events`, which this single-table index does not cover end-to-end. Functionally correct today (verified against a live database with realistic small test fixtures), but a group with many events and a long completion history should get a dedicated composite index (likely on `goal_events(group_id)` joined with a covering index on `event_completions(posted_at, id)`) before this becomes a real production feed at scale. Not built here since it's a performance concern with no plan-stated behavior test to drive it, and out of this plan's own migration scope beyond the one index it explicitly named.
- Docker Desktop remains unavailable in this environment (carried forward from 04.1-01/04.1-04's own documented gap); this plan's own tests never needed MinIO directly -- `PhotoURLSource` is an interface, and `feed_test.go` uses a stub double, so photo URL resolution's own logic is fully unit-tested without a running S3-compatible backend. The one real gap this plan doesn't close is a live round-trip against the actual MinIO `SharedURL` presigning implementation, matching every prior phase-4.1 plan's own documented MinIO gap.
