**A Go `internal/groups` package (creation, friend-gated invite, join with an atomic 12-member cap, leave with an explicit completion-visibility disposition, policy-gated removal) plus its `RequireMember` authorization gate, migration `0004_groups`, and nine authenticated `/v1/groups...` routes.**

## Accomplishments
- `internal/groups` package with a closed-by-construction schema: groups have no visibility, discoverability, or public-slug column at all — the absence of the column is docs/group-events.md §1's "no public tier exists" rule made structural, not a setting defaulted to private.
- `Invite` consults `internal/friends.Service`'s own `AreFriends` method through an injected `FriendPredicate` interface, never a second copy of the friendship query (T-04.1-46). It also requires the inviter to already be a group member before they can extend an invitation.
- `Join` enforces the 12-member cap and the membership insert inside one transaction with the group row locked (`SELECT ... FOR UPDATE`), so two concurrent joins cannot both pass a pre-check and overshoot the cap (T-04.1-48).
- `Get`/`ListForUser`/`RequireMember` are membership-scoped queries (a JOIN on the caller's user id), not a fetch followed by a separate check — a non-member fetch of a real group and a fetch of a random UUID return the byte-identical `ErrNotAMember` sentinel end to end, verified at both the service and HTTP layers (T-04.1-45).
- `Leave` is unconditional for any member, including the organizer and including a group's last member; nobody is elevated into the organizer role when it's vacated, and the group's `organizer_user_id` column is left pointing at whoever created it, matching docs/group-events.md §1's "nothing to transfer" design.
- `Leave`'s explicit `keepPosts`/`removePosts` disposition drives a `CompletionVisibility` seam (defaulting to a no-op) that plan 04.1-10 will wire a real implementation into once the completions table exists.
- `RemoveMember` follows the group's own `removal_policy` (any-member or organizer-only) and rejects self-removal — leaving is the dedicated route for that.
- Nine authenticated HTTP routes wired behind `RequireSession`, with a `statusForGroupsError` mapping that keeps not-a-member/no-invitation at 404 (never 403, which would itself confirm a group exists).

## Decisions Made
- **Invite requires membership, not just friendship.** The plan's must_haves listed `ErrNotAMember` as one of `groups.go`'s required exports, and only a current member has standing to extend an invitation into a closed group — an outsider who happens to be friends with someone inside shouldn't be able to invite them in. This is additive to the plan's literal behavior list (which only specified the friend-gate), applied as a Rule 2 (missing critical functionality) fix since the alternative would let anyone who knows a group id and is friends with a target invite them in regardless of their own membership.
- **SetCompletionVisibility as a setter, not a New() parameter.** The plan's own `<artifacts_produced>` locks `New(st *store.Store, fr FriendPredicate, now func() time.Time) *Service`'s signature. Since `CompletionVisibility` is explicitly described as construction-time-optional ("when plan 04.1-10 has not yet landed, the interface is satisfied by a no-op implementation"), a post-construction setter keeps the documented signature intact while still giving 04.1-10 a clean injection point.
- **Invitation upsert, not append-only history.** `group_invitations` has one row per (group, invitee) pair; `Invite` upserts onto it (`ON CONFLICT ... DO UPDATE ... WHERE state != 'pending'`) so a former member can be re-invited, or a decline can be followed by a fresh invite, without a growing history table nobody reads.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical] Invite requires the inviter to already be a member**
- **Found during:** Task 1 (Invite implementation)
- **Issue:** The plan's behavior list only specified the friend-gate for Invite ("Inviting someone the inviter is not friends with fails"); it never states that a non-member who happens to be friends with a target should also be blocked. Left as written, anyone who is friends with a group member's contact and knows the group's UUID (leaked out-of-band, e.g. via a screenshot) could invite people into a group they have no standing in.
- **Fix:** `Invite` now checks `isMember(inviterUserID)` first and returns the plan's own `ErrNotAMember` sentinel (already required as a `groups.go` export by must_haves) before reaching the friend check.
- **Files modified:** `RithamService/internal/groups/groups.go` (no test file change needed — covered implicitly by every existing Invite test, which all invite from a genuine organizer/member)
- **Verification:** `go test ./internal/groups/...` — all Invite-path tests still pass with the added check in place.
- **Committed in:** `7499019` (Task 1 commit)

**2. [Rule 3 - Blocking] NewMux signature change required updating handler.go, handler_test.go, and main.go**
- **Found during:** Task 3 (Authenticated group routes)
- **Issue:** `groups_handler.go`'s nine handlers need a `groupsService` to be wired into `NewMux`, but `NewMux`'s existing signature (four parameters) has no slot for it. Every pre-existing call site (`handler_test.go`'s twelve `NewMux(...)` calls, `main.go`'s server construction) would fail to compile once the signature changed.
- **Fix:** Added a fifth `groupssvc *groups.Service` parameter to `NewMux`, a `buildGroupsService(st, friendssvc)` constructor in `main.go` (returns nil, degrading gracefully, when either dependency is nil — matching every other route group's precedent), and updated all twelve `NewMux(...)` call sites in `handler_test.go` to pass the new parameter (`nil` where the pre-existing tests don't exercise group routes).
- **Files modified:** `RithamService/internal/httpapi/handler.go`, `RithamService/internal/httpapi/handler_test.go`, `RithamService/cmd/ritham-service/main.go`
- **Verification:** `go build ./... && go vet ./... && go test ./...` all exit 0; `TestWorkoutPlanRequest_*` reflection assertions in `handler_test.go` still pass unchanged.
- **Committed in:** `97294ae` (Task 3 commit)
