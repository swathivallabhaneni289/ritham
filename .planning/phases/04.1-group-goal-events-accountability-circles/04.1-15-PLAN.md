<objective>
Build the group-only feed and its completion card — the surface where every non-comparative rule in
this phase becomes something a person actually looks at.

Purpose: GROUPEVENTS-04 enumerates what this screen must never show, and the UI-SPEC translates
each into a concrete visual rule: no ordinal badge, no medal, no sort control, no progress ring,
no denominator, and no greyed-out row for someone who has not finished. The card with a time and
the card without one must differ only in the words themselves — no badge, no color, no icon
marking who chose to share a number, because a marker distinguishing them would itself be the
comparison signal the whole feature exists to remove.

This plan builds `CheerReactionRow`, Ritham's first cheer control. It deliberately does not reuse
the selected-state treatment the app's existing chip control uses. A chip's selected state marks a
data answer, where showing which option is chosen is the entire point; a cheer is a social action
on a feed several people see, and the accent fill would read as the important one to tap. The
UI-SPEC rules on this explicitly and the component records the reasoning inline so a later editor
does not "fix" it back.

Output: the `Social/Feed/` directory, the first cheer component, and two new steps.
</objective>

  <behavior>
    - The decoded page and item types accept exactly the key set the server sends and reject an
      unexpected key, so a field added server-side without a client change fails loudly.
    - The model appends pages in the order received and never sorts, reverses, or re-keys the
      items — asserted by feeding a page whose items are deliberately not in any numeric order of
      their own and checking the rendered order equals the received order.
    - Pull-to-refresh replaces the first page and resets the cursor.
    - The poll timer calls the same load path as pull-to-refresh, and stops when the view goes away.
    - A transport failure moves the model to failed and leaves existing items on screen, so a
      dropped connection never blanks a feed a person was reading.
    - A first load that fails renders as an error rather than as an empty feed.
    - Toggling a cheer updates only the viewer's own flag for that item and changes no other item.
    - The item type has no property carrying a total, a position, a fraction, or a cheer count,
      asserted by reflection over its stored properties.
  </behavior>
  <action>
    Write `GroupFeedTests.swift` first for every behavior above.

    Create `FeedClient.swift` over the shared social client, mirroring the server's page and item
    shapes exactly. Configure the decoder to reject unknown keys where the platform allows it, or
    assert the key set explicitly in the test, so a server-side field addition surfaces immediately
    rather than being silently dropped — that matters here more than elsewhere, because the field
    most likely to be added by mistake is a count.

    Create `GroupFeedModel.swift`. It appends and never orders. The doc comment states why the
    absence of any client-side sort is load-bearing: the server returns post order, that order is
    safe specifically because there is no synchronized start, and any client-side re-ordering would
    reintroduce exactly the ranking the server refuses to do.

    The poll interval and pull-to-refresh share one load path. Polling is this phase's delivery
    mechanism because no push infrastructure or entitlement exists in this project, which
    04.1-RESEARCH.md settles rather than leaves open; record that in the model's doc comment so the
    choice reads as decided rather than as a gap.

    A failure never clears loaded items. An empty feed and a failed feed are different states and
    the view must render them differently.
  </action>
