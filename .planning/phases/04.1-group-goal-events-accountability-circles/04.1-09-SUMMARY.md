See `key-decisions` in frontmatter for the full list. Highlights:

- **Backend fix was required, not optional.** `Incoming`'s response carried no name for the requester at all — a genuine gap between the plan's own stated behavior and what the shipped Go API returned, found before writing any client code by reading `friends_handler.go` directly (matching 04.1-05's and 04.1-06's own precedent of verifying the Go source before trusting the plan's prose).

- **Row 2 and row 3 of AddFriendView are one mechanism.** Confirmed against Task 3's own action text (which ties "the system share sheet" to "the direct-share path" in one sentence) that both invite-shaped rows should create the identical kind of invite and present the identical screen, rather than inventing a second, undocumented server-side "direct share" primitive with no target-selection UI to drive it.

## Known Stubs

- **Contact matching cannot yet make a user discoverable, and cannot yet find matches.** `contact_match_digests` (the table `MatchContacts` searches) is written only by a user submitting their own identifier via `SetContactMatchOptIn`'s `identifierDigests` field — and this app has no source for a user's own phone/email today (`SessionStore` holds a display name only). `AddFriendView`'s opt-in genuinely records the flag server-side (sufficient to satisfy `MatchContacts`'s own opted-in gate for a *future* caller), but no screen in this plan collects a phone/email to submit, and no screen calls `MatchContacts` to search — both are structurally guaranteed to be no-ops today. A future plan needs to: (1) add a phone/email collection step (its own new privacy-review surface), (2) submit its digest via `setContactMatchOptIn`, and (3) call `matchContacts(digests:)` against the device's address book, with a results UI. `FriendsClient.matchContacts(digests:)` already exists and is fully wire-correct; nothing server-side needs to change.
- **`FriendConnectionPath.directShare`/`FriendsClient.send(toUserID:path:)` are unwired by any UI.** A genuine device-to-device "in-person" connection path (distinct from the invite-token mechanism `AddFriendView`'s rows 2/3 both use) would need URL-scheme or universal-link handling this app has never built. The client method is fully wire-correct and ready for whenever that mechanism is designed.
- **No invite created by this plan can be redeemed by anyone yet — all three connection paths are write-only today, not just contact matching.** Verified by grep: zero call sites of `FriendsModel.redeem(token:)` outside its own declaration, and no `CFBundleURLTypes` registered in `Info.plist`/`project.yml`. Row 2's QR code encodes the bare token; row 3's share sheet sends `"Join me on Ritham: <token>"` as plain text — neither is a link anything can open, and `AddFriendView` has no field to type a token into by design (no search/text-entry anywhere on this screen). `FriendsModel.redeem(token:)` itself is fully correct and already covered end-to-end by `FriendsUITests` at the model layer; what's missing is any entry point that calls it — either a QR scanner or real URL-scheme/universal-link handling, neither of which exists anywhere in this app yet. A future plan needs to add one before an invite this screen creates can ever become a friendship.
- **`AddFriendView`'s contact-match chip never loads the server's actual current opt-in state.** `contactMatchSelection` initializes unconditionally to "Off" every time the screen appears, regardless of what the user chose last time — a user who opts in, leaves, and returns sees "Off" while the server still has them opted in. This is not fixable by this screen alone: the ten friends routes include `PUT /v1/friends/contact-match` and `POST /v1/friends/contact-match/query`, but no `GET` to read the stored flag back. `FriendsModel.contactMatchOptedIn` only reflects a write made in the current session, never a value loaded from the server. A future plan needs a read route before this can display truthfully.
