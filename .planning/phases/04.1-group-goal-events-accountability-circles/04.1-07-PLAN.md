<objective>
Build Privacy Zones and the single on-device function that decides what, if anything, a shared
location says.

Purpose: GROUPEVENTS-03's two location guarantees are sequentially dependent, not independent.
Evaluating "is this inside a Privacy Zone" requires the precise coordinate, but "never store
precise coordinates" says that coordinate must not survive. Both are only true if one exact order
is followed: capture a transient fix, check zones, and either stop there or reverse-geocode and
send only the resulting name — then let the coordinate fall out of scope. 04.1-RESEARCH.md
Pitfall 3 names the specific failure this plan is shaped to avoid: a zone model and a geocoding
call landing in separate plans with no ordering test between them. So the geocoding call itself
lives here, inside that one function, with the ordering asserted; plan 04.1-14 only calls it.

`docs/group-events.md` §3 sets the display rule this implements: a coarse named place, never
coordinates, a pin, an address, or any numeric radius or distance — because Strava's own
documentation concedes a fixed radius is defeatable by correlation, and Tinder's 2016 vulnerability
showed a displayed distance figure is enough to reconstruct a point. A named place has no
geometric edge and no numeric handle.

Output: the `Social/PrivacyZones/` directory, a file-protected zone record, one new step, and a
Settings entry.
</objective>
