## Accomplishments
- `PrivacyZone`/`PrivacyZoneEffect`/`PrivacyZoneStore`/`PrivacyZoneRecord`: a pure value type with great-circle (`CLLocation.distance(from:)`) containment, stored on-device only in the same file-protection-backed SwiftData container as health screening data, with a nil-safe raw-value effect accessor and no user/event/completion identifier field.
- `LocationAttachment.resolveSharedPlaceName`: the single function implementing 04.1-RESEARCH.md Pattern 3's five-step capture/zone-check/geocode/discard sequence, with the zone check running before the geocoder is ever constructed -- proven, not merely conventioned, by a call-counting spy asserting exactly zero resolver invocations on every zone match.
- `SystemGeocoder`: the only `CLGeocoder` call site in the codebase, gated behind a `PlaceNameResolving` seam, using a hard four-field placemark allowlist (area of interest, sub-locality, locality, administrative area) with street-level fields excluded by construction.
- `PrivacyZonesView`/`AddPrivacyZoneView`: a Settings-reachable zone list showing each zone by its own user-given label only (never a point, coordinate, or map thumbnail), and a zone-creation screen using a native map picker plus the existing two-option chip control for the generalize/suppress choice.
- `OnboardingStep.privacyZones`: registered with `StepRegistry` so `unregisteredSteps` stays empty, but reached only from `SettingsView`'s sheet, never the router -- matching `.signInWithApple`'s precedent exactly.

## Decisions Made
- **`PrivacyZoneRecord` registered in `RithamModelContainer.swift`, not `HealthDataStore.swift`** (a real deviation from the plan's `files_modified` list, made by the prior executor's Task 1 work and confirmed correct here): `RithamModelContainer.swift` is where every other model's schema membership is declared app-wide; `HealthDataStore.swift` is where accessors live. Registering the schema entry in `HealthDataStore.swift` instead would have been inconsistent with every other model in the container.
- **`PrivacyZonesView` conforms to `OnboardingStepPresenting`/registers under `.privacyZones` purely for `StepRegistry.unregisteredSteps`'s sake**, while being reached only from `SettingsView`'s sheet -- reusing `SignInWithAppleView`'s already-established "registered for the registry, reached by a different path" shape rather than inventing a new one.
- **Delete uses a native `confirmationDialog` with a `role: .destructive` action**, plus a `RithamColor.destructive`-outlined row button -- the first live activation of that token, reserved since Phase 1 specifically for this kind of irreversible action.
- **Zone radius is a fixed internal constant (150m)**, never surfaced as a user-facing control, per `PrivacyZone`'s own doc comment: the radius is an internal evaluation input only, never displayed or collected as a number anywhere in the UI.
- **Rename is inline** (tap "Rename" -> row becomes a `TextField` + Save/Cancel) rather than a separate sheet -- there is no existing rename-flow precedent elsewhere in the codebase to match, and this is the simplest shape consistent with "no coordinate ever re-displayed."
