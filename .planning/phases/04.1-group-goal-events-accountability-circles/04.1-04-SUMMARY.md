# Phase 04.1 Plan 04: Server-Side Photo Pipeline and EXIF-Strip Guarantee Summary

**Structural, type-enforced EXIF/GPS stripping (decode-then-reencode through only the Go standard library, with the shared storage tier's writer accepting nothing but the opaque pipeline output) plus a real iPhone-shaped HEIC rejection path and an authenticated multipart upload route -- all fully unit/integration-tested against a native Postgres, with the MinIO wire behavior itself left as this environment's one documented, carried-forward gap**

- **Duration:** ~100 min
- **Tasks:** 3 (2 TDD tasks with RED/GREEN commit pairs, 1 auto task)
- **Files created/modified:** 22

## Accomplishments

- `internal/photo.StripAndReencode` is the sole producer of the opaque `StrippedImage` type (unexported fields, no exported constructor) -- verified by `grep -c 'func StrippedImage'` returning 0 and by a compile-time assertion in `service_test.go` that `ObjectStore.PutShared`'s parameter type is exactly `StrippedImage`, never `[]byte`
- The metadata-removal guarantee is structural, not filter-based: `image.Decode`/`image/jpeg`-`Encode` through only the Go standard library cannot carry an EXIF/XMP segment or PNG text chunk, proven by `TestStripAndReencode_NoMetadataSegments`'s structural JPEG-marker walk and PNG-marker-absence check, with positive-control tests confirming the input fixtures genuinely carried that metadata first
- HEIC is rejected with a specific sentinel (`ErrUnsupportedFormat`), never a passthrough -- asserted against a genuine ISO-BMFF HEIF container, not a renamed JPEG. Solved the tricky failure-mode-collapse where Go's `image.Decode` returns the identical `image.ErrFormat` for both real HEIC and arbitrary garbage bytes, by sniffing the `ftyp` box's major brand explicitly before decode
- Orientation is read (via a narrow, read-only `rwcarlsen/goexif` use, T-04.1-22) before metadata is discarded, and the hand-rolled 8-case pixel transform is independently derived two ways, cross-checked against exiftool's documented descriptions, and pinned once in `orientation.go`'s doc comment so no other file re-derives it from memory
- Layered DoS bounds: byte-size cap, then a header-only pixel-count cap via `image.DecodeConfig` -- verified to actually run before the full decode using a PNG with a huge declared `IHDR` and deliberately invalid `IDAT`
- `ObjectStore.PutShared` takes only `StrippedImage`; `Service.Ingest` runs the strip pipeline first and writes nothing (no object, no row) on any failure -- verified with a stub `objectWriter` against a live Postgres, since this environment has no working Docker/MinIO
- `photo_assets` structurally cannot hold a GPS position, capture location, or address -- verified at both the migration-file-text level (`grep`) and the live-database-catalog level (`information_schema` query)
- `Asset()` selects by id **and** owner together, so an asset id alone is never sufficient to read someone else's photo
- Two authenticated routes (`POST /v1/photos`, `GET /v1/photos/{id}`) exist, routing every upload through `Ingest` only -- the handler never touches object storage directly. All five required response branches (401/200/415/413/404) are tested by name against `httptest` with stubs
