**Group creation, friend-gated invitation, member roster with policy-derived removal, and an explicit no-preselected-default leave disposition choice, built entirely against groups_handler.go's nine shipped routes with no backend changes.**

## Accomplishments

- `GroupsClient.swift` — nine operations mirroring `groups_handler.go`'s wire contract character for character (`CreateGroupRequest`/`GroupResponse`/`GroupDetailResponse`/`InviteToGroupRequest`/`LeaveGroupRequest`/`SetRemovalPolicyRequest` and their response types), no request struct naming the acting user.
- `GroupsModel.swift` — the four-case load state; `viewerIsOrganizer`/`viewerCanRemoveMembers` derived purely from the loaded group's own stated `memberRemovalPolicy` and the viewer's own id, never a client-side "organizer can always remove" shortcut (T-04.1-64); a failed list load or a 404 group-detail fetch never mutates `groups`/`selectedGroup` with an empty or default value.
- `GroupListView.swift` — a flat card list of the viewer's groups (rounded-square `SectionIconBadge`, distinguishing group identity from a person's circular `AvatarView`), a "Create a group" primary CTA, no search field and no browse affordance of any kind.
- `GroupDetailView.swift` — member roster (circular avatars + names), an invite entry point offering the viewer's own friends, a removal affordance gated on `viewerCanRemoveMembers` and withheld from the viewer's own row, a leave entry point. The organizer's row is rendered by the exact same code path as every other row — no marker of any kind — with the removal policy explained, when relevant, as plain body text.
- `LeaveGroupSheet.swift` — the required explicit keep/remove-past-posts choice: neither option is preselected (`selection` starts as an empty `Set`), and the confirm action stays disabled until one is chosen.
- `CreateGroupSheet.swift` — the group-naming form, built as its own file (Rule 2 addition — see Deviations) following `AddPrivacyZoneView.swift`'s precedent.
- `DestructiveCTAButton.swift` — the first live consumer of `RithamColor.destructive`, reserved unused since Phase 1; used by the Leave Group and Remove Member confirmations only.
- `HomeHubView.swift`'s signed-in social section now offers two destinations (Friends, Groups), closing `04.1-09-SUMMARY.md`'s own forward handoff.
- Backend fix: none needed — this plan builds entirely against the nine routes `04.1-08` already shipped.
- Core fix: `RithamCore.GroupLeaveDisposition`'s raw values corrected to match the Go wire contract exactly (see Deviations).

## Decisions Made

See `key-decisions` in frontmatter for the full list. Highlights:

- **No pending-invitations UI, and no `declineInvitation` client method.** Verified directly against `groups_handler.go` (nine routes, all mirrored) and `groups.Service` (no `ListInvitationsForUser`-shaped method at all) before writing any client code. Building an "Invitations" section that can never populate would be exactly the kind of hardcoded-empty-value stub this project's own convention flags — omitted instead, and recorded as a Known Stub below for whichever future plan adds the missing route(s).
- **`GroupLeaveDisposition`'s raw values were a real, verified bug**, not a hypothetical one: `membership.go`'s `knownLeaveDispositions` map only accepts the literal strings `"keepPosts"`/`"removePosts"`; the domain enum's implicit case-name-derived raw values (`"keepPastPosts"`/`"removePastPosts"`) would have caused every leave call to 400. Fixed at the source (`GroupModels.swift`) rather than adding a translation layer in `GroupsModel.swift`, since the enum's whole reason for existing is to be the one true representation of this choice.
- **`CreateGroupSheet.swift` exists because a group fundamentally needs a name**, and `GroupListView.swift`'s own acceptance gate (`grep -c 'TextField'` == 0) rules out collecting it inline on the list screen. Rather than silently auto-naming every new group, this plan follows the exact separate-sheet-file shape `AddPrivacyZoneView.swift` already established for the identical constraint.

**1. [Rule 1 - Bug] `GroupLeaveDisposition`'s raw values corrected to match the Go wire contract**
- **Found during:** Task 1 (writing `GroupsModel.leave(groupID:disposition:)`)

- **Fix:** Set explicit raw values (`case keepPastPosts = "keepPosts"`, `case removePastPosts = "removePosts"`), documented in the type's own header comment. Case names stay descriptive; only the wire-facing raw value changed.

**2. [Rule 2 - Missing Critical] Omitted `declineInvitation` and any pending-invitations list**
- **Found during:** Task 1 (before writing `GroupsClient.swift`, verified against `groups_handler.go` directly)

**5. [Rule 3 - Blocking] Cross-suite Keychain race, deterministically breaking full-target verification**
- **Found during:** Post-Task-3, running this plan's own full-target `xcodebuild test` verification (required by `04.1-11-PLAN.md`'s `<verification>` section)
- **Issue:** `SocialIdentityTests.requestCarriesBearerHeaderWhenTokenStored()` failed deterministically in every full-target run (two consecutive runs, both failing the same way) while passing every `-only-testing:` scoped run, including that same test in isolation. Root cause: `SessionStore` (plan 04.1-05) is backed by the real, process-shared iOS/macOS Keychain, not a test-isolated store. `SocialIdentityTests`/`FriendsUITests` each call `SessionStore().clear()` in their own `init()` plus `.store(...)` per test; `GroupsUITests` (this plan) added a third suite performing `.store(...)` writes. Each suite's own `.serialized` trait only orders tests *within* that suite — Swift Testing runs unrelated suites concurrently by default — so one suite's Keychain write can land between another suite's own store-then-assert pair. `04.1-09-SUMMARY.md` recorded a green 454/454 full-target run with `FriendsUITests` already present, so this exposure was latent (present but not manifesting) until a third writer suite tipped the scheduling.
- **Fix:** (a) Removed `GroupsUITests.init()`'s own `SessionStore().clear()` — every test needing a session gets one via `makeClientAndSession`, which stores its own token immediately before use, so the clear was redundant. (b) Nested `GroupsUITests`/`FriendsUITests`/`SocialIdentityTests` under one new shared `.serialized` parent suite, `KeychainTouchingSuites` (`KeychainTouchingSuites.swift`), mirroring `StepRegistrySerialization.swift`'s own already-established cross-suite-nesting mechanism exactly.
- **Files modified:** `RithamApp/RithamTests/GroupsUITests.swift`, `RithamApp/RithamTests/KeychainTouchingSuites.swift` (new), `RithamApp/RithamTests/FriendsUITests.swift`, `RithamApp/RithamTests/SocialIdentityTests.swift`
- **Verification:** Two consecutive full-target `xcodebuild test` runs, both green (472 tests, 56 suites). `RithamCore`'s full `swift test` suite (436 tests, 32 suites) unaffected and still green.
- **Committed in:** `9a497cc` (post-Task-3 fix commit)
