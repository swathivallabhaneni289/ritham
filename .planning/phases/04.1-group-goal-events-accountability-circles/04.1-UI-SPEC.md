# Phase 4.1 — UI Design Contract

> Visual and interaction contract for Ritham's first multi-user social surface: friends,
> accountability groups, Goal-Events, RSVP, completion logging (with the off-by-default own-time
> prompt), photo/location attach + Privacy Zones, a group-only feed with fixed non-comparative
> cheers, digital certificates, and the Sign in with Apple entry point. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker. This document states the resulting *look and
> behavior* only — data model, backend, EXIF/geocoding pipeline mechanics belong to
> `04.1-RESEARCH.md`/`04.1-CONTEXT.md` and the planner.
>
> **This phase introduces zero new design-token primitives.** Every color, type role, and spacing
> value below already exists in `RithamColor.swift`/`RithamType.swift`/`RithamSpacing.swift`
> (locked since Phase 1, `01-UI-SPEC.md`) and is transcribed here, not reinvented. What *is* new
> this phase: the cheer-reaction component, an activity-type icon mapping (corrects a mistaken
> claim in `04.1-RESEARCH.md` that one already exists — it does not, see New Components below),
> client-side certificate composition, and the `SignInWithAppleButton` entry point (a
> platform-mandated component Ritham cannot restyle).
>
> **Structural theme of this entire document:** every visual decision below exists to make the
> PRD's "no comparison, ever" rule true by *construction* — never a badge, count, color-code, or
> layout choice that could read as ranking, even where the underlying data genuinely differs
> (own-time-added vs. not, organizer vs. member, sensor-verified vs. manual). Where a screen
> tempts an "obvious" comparative treatment, this document says so explicitly and states the
> non-comparative alternative — read those call-outs as load-bearing, not decorative advice.

## Spacing Scale

Declared values (existing `RithamSpacing` tokens, unchanged — multiples of 4):

| Token | Value | Usage in this phase |
|-------|-------|-------|
| xs | 4pt | Icon gaps, inline padding (activity-type glyph to label) |
| sm | 8pt | Compact element spacing; card corner radius (feed cards, group rows, friend rows, certificate frame) |
| md | 16pt | Default element spacing; screen margin; card internal padding; gap between feed cards |
| lg | 24pt | Section padding (e.g. above the cheer row, above the "Add friend" three-path list) |
| xl | 32pt | Layout gaps (e.g. between the completion-confirmation headline and the own-time prompt) |
| xxl | 48pt | Major section breaks (e.g. above/below the Sign in with Apple button on its entry screen) |
| xxxl | 64pt | Page-level spacing (certificate reveal screen top inset) |
| minimumTapTarget | 44pt | Every tappable control: cheer buttons, RSVP action, Add/Skip time actions, member-row leave/remove affordances, the "6 friends are in" row is display-only and exempt |

**Phase-specific rule — equal-prominence pair:** the completion-logging screen's "Add time" / "Skip"
pair (locked PRD requirement, §2's copy table) uses `HStack(spacing: RithamSpacing.md)` with both
actions rendered as `SecondaryCTAButton` (same size, same style, same tap target) — never one
`PrimaryCTAButton` paired with a de-emphasized skip link. This is the one place in this phase where
using two `SecondaryCTAButton`s side by side, rather than a `PrimaryCTAButton` + text link, is the
correct pattern specifically *because* the PRD requires equal prominence, not because
`PrimaryCTAButton` is unavailable.

Exceptions: none.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Display | 28pt (`.title`) | Semibold | System default |
| Heading | 22pt (`.title2`) | Semibold | System default |
| Body | 17pt (`.body`) | Regular | System default |
| Label | 16pt (`.callout`) | Regular | System default — **the floor**; nothing in this phase renders smaller |

**Phase-specific rules (carrying forward the locked, closed 4-role scale — no `.caption`/`.footnote` anywhere, structurally enforced project-wide):**

- Feed card body ("Priya completed the Saturday 5K Walk") — `RithamType.body`.
- Feed card metadata (completion date, generalized place name, personal caption) — `RithamType.label`, with `RithamType.fineprint()` if it needs to read as secondary. **Never a smaller point size to fit a card's compact layout** — if a place name or caption is long, wrap it (reuse `ChoiceQuestionView`'s `WrapLayout`/`fixedSize(horizontal: false, vertical: true)` precedent), never truncate to a caption-sized ellipsis.
- Own-completion-time value ("32:14") and RSVP headcount ("6") both use `RithamType.numerals()` (`.monospacedDigit()`) — counting values, matching `MomentumCopy`'s existing precedent for streak/shield counts.
- Certificate text (event name, participant name, date, time) — `RithamType.body` for the participant name (the certificate's visual focal point), `RithamType.label` for every other field. No field on the certificate renders below the 16pt floor, including the fine-print-style "Ritham" wordmark credit line.
- Sign in with Apple entry screen body copy — `RithamType.body`, matching every other Phase 1-3 explainer screen (Privacy Explainer precedent), not a smaller "legal disclaimer" size.

## Color

| Role | Value | Usage in this phase |
|------|-------|-------|
| Dominant (60%) | `RithamColor.ink` (#0E100D) | Screen background across every screen in this phase, unchanged |
| Secondary (30%) | `RithamColor.paper` (#F5F3EC) | Primary text/label color on charcoal; low-opacity card fills (`paper.opacity(0.06)`, matching Phase 4's Dashboard Section Card); certificate card surface (see Digital Certificate below) |
| Accent (10%) | `RithamColor.hot` (#FF5C39) | **Reserved for, and only for:** the primary CTA fill on this phase's genuine primary actions — "Start a Group Goal," "You're in" (RSVP), "Log completion," "Send friend request," "Export" on the certificate screen |
| Destructive | `RithamColor.destructive` (#FF3B30, iOS system red) | **First activation of this token** — Phase 1 reserved it with no consumer yet ("Phase 1 has no destructive action"); this phase is that later phase. Used for: Leave Group confirmation, Remove Member confirmation (see Copywriting Contract) |

**Locked rules this phase must not violate (already structural in `RithamColor.swift`, restated here because this phase's UI is dense with candidate misuses):**

- `RithamColor.volt` (#C6F24E) stays reserved for the static ring-and-dot header ornament only. **No screen in this phase may use `volt` for anything else** — not a cheer-sent indicator, not an "own time added" marker, not a certificate accent, not a group/friend online-status dot.
- Label color on any `hot` or `volt` fill goes through `RithamColor.label(on:)` — never a hardcoded `paper` label on those fills (both fail AA contrast per `RithamColor.swift`'s measured table).
- **Do not extend `hot`'s reserved list to any status/badge use, however tempting.** This phase has several places where a color-coded badge is the "obvious" solution and is explicitly wrong here:
  - **"Own time added" vs. "no time"** (feed card, certificate): per the locked PRD copy table, these two states are "never styled differently... beyond the number itself." No color, no icon, no badge distinguishes them — only the literal presence or absence of the time substring in the sentence. A colored badge on "who added a time" would itself be a subtle comparison signal, exactly what the PRD prohibits (this rationale is stated directly in this phase's own scoping instructions, not inferred).
  - **Organizer vs. member** (group member list): the PRD is explicit that "organizer" is "a convenience role, not a title with public weight." No crown/star/color-coded name treatment, no `hot`-filled badge, no distinguishing font weight beyond what's needed for the row's own leave/remove action affordance. If the UI needs to indicate who can remove members under an organizer-only group setting, do it with plain body text ("Group settings: only the organizer can remove members") on a settings screen, never a per-row visual marker on the organizer's own identity.
  - **Sensor-verified vs. manually-entered** (if a Goal-Event completion ever surfaces this distinction, carried over from Momentum precedent): reuse `MomentumCopy.Verification`'s existing *text label* pattern (`RithamType.label`, no color/icon difference), never invent a color-coded variant for this phase.
  - **Cheer-sent state**: see Cheer Reaction Component below — deliberately does *not* use `hot`.

**Accent (`hot`) reserved for, explicitly, nothing beyond:** the primary CTA fill on this phase's named primary actions (above). Every other interactive element in this phase (chips, cheer buttons, secondary actions, member-row leave affordances) uses the existing `paper`-outline/`paper`-fill vocabulary already established by `SecondaryCTAButton`/`ChoiceChip`.

## Non-Comparative Structural Visual Rules (cross-cutting — apply to every screen below)

These restate GROUPEVENTS-02/04/05's locked decisions as concrete, checkable visual rules, since
this is the part of the phase most likely to regress toward a "normal social app" default under
time pressure:

1. **No ranking visual of any kind, anywhere**: no ordinal badge ("1st"), no medal icon, no sort
   control on the feed, no progress bar/ring showing "X of Y completed," no leaderboard list sorted
   by time or pace.
2. **No denominator paired with a completion count**, on any screen. The RSVP headcount ("6 friends
   are in") lives *only* on the pre-event RSVP screen and must never be re-rendered, referenced, or
   made navigable-to from the completion feed or the group history screen. A completion feed/history
   screen that shows completion cards must never also show "X of Y" or "6 invited" nearby.
3. **No greyed-out / "hasn't finished" state.** Non-completion renders nothing — there is no row,
   avatar, or placeholder for a person who hasn't logged a completion. Do not build an empty-state
   row per non-completer "for symmetry."
4. **No expiry/closing UI.** When a Goal-Event's target date/window passes, nothing changes visually
   for anyone who didn't complete it — no banner, no strikethrough, no "missed" tag. The event
   simply stops appearing in the upcoming/active list.
5. **No data-bearing ring, arc, or radial progress indicator anywhere in this phase's UI** — this
   extends the existing Ring Collision rule (previously scoped to Momentum-adjacent content) to the
   whole phase, because an RSVP-headcount ring or a "completion progress" arc would itself read as
   exactly the comparison mechanic this feature exists to avoid. `DecorativeSurface.ringAndDot` (the
   static header ornament) is unaffected — it is not data-bearing and may still appear per the
   Layout & Screen Contract below.
6. **Feed order is chronological only** — no `Picker`, segmented control, or menu offering
   "sort by" anywhere near the feed. If a filter is ever needed (e.g. by Goal-Event), filtering by
   *which event*, never by *time/pace/rank*, is the only sanctioned axis.

## Cheer Reaction Component

**Locks in Ritham's first implementation of the fixed, non-ranked cheer set** referenced (but not
yet built) by `HOUSEHOLD-01`'s requirement text — this phase's `CheerReactionRow` is the canonical
first build; Phase 4 round 2 (`HOUSEHOLD-01`) should reuse this exact component and string set for
household cheers rather than building a second, potentially-divergent one.

**Fixed set, exactly two, no more:** "Nice work" and "Keep going" — transcribed verbatim from
`REQUIREMENTS.md`'s `HOUSEHOLD-01` wording ("nice work"/"keep going"), reused here to keep the two
features' eventual cheer sets identical rather than inventing a third, phase-4.1-specific pair.

**Visual treatment — deliberately not `ChoiceChip`'s `hot`-fill-on-select pattern:**

| Property | Value |
|---|---|
| Layout | Two `SecondaryCTAButton`-style chips (not full-width `SecondaryCTAButton`s — sized to content, `HStack(spacing: RithamSpacing.sm)`, wrapped via the existing `WrapLayout` at accessibility text sizes) below each feed card |
| Unselected (not yet sent by this user) | `paper`-outline, `paper` label — matches `SecondaryCTAButton`'s stroke treatment |
| Sent-by-this-user state | `paper`-filled, `ink` label (i.e. inverted fill, **not `hot`**) — a plain "you did this" affordance state, not a status badge announced to the group |
| Never shown | A count of how many people sent this cheer, a "most-cheered" ordering, any per-person list of who cheered |

**Why not reuse `ChoiceChip`'s existing `hot`-on-select treatment**, even though it's already a
locked precedent elsewhere in the app: `ChoiceChip`'s selected state marks a *data answer*
(a screening choice, a preference) where showing which option is chosen is the entire point.
A cheer is a *social* action on a feed multiple people see — an `hot`-filled cheer button risks
reading as "the important/correct one to tap" or, worse, drawing the eye toward whichever reaction
has more taps if a future iteration ever surfaces counts by accident. Keeping cheers on the
neutral `paper`/`ink` inversion (already used elsewhere for non-CTA selected states) sidesteps that
risk entirely and keeps `hot` scoped to the reserved list above. Document this rationale inline in
the component's header comment when built, so a future editor doesn't "fix" it back to `ChoiceChip`.

## Layout & Screen Contract

Every screen in this phase uses `RithamScreen` with one of two `DecorativeSurface` presets — no
screen in this phase uses `.welcome`, `.calibration`, `.calibrationSession`, or `heroRing` (those
stay scoped to onboarding/calibration). Per Rule 5 above, no screen's content area may add a ring,
arc, or radial progress form regardless of header choice.

| Surface | Screens |
|---|---|
| `.flat` | Friends list, Add Friend, Group list, Group detail / member list, Goal-Event list, RSVP screen, Completion logging screen, Group feed, Group history (post-window), Privacy Zones settings — every data-dense/functional screen, matching Phase 4's revised (2026-09-09) direction of maximizing content space over decoration |
| `.boundedHeaderOnly` | Sign in with Apple entry screen (explains, doesn't collect data — same treatment as the Privacy Explainer precedent), Certificate reveal screen (celebratory, introduces a new artifact rather than collecting data) |

### Friends

- **Friends list**: plain `VStack` of friend rows — circular avatar (photo or initials fallback;
  avatars are the one sanctioned circular shape in this phase, a standard identity convention, not
  a progress form, so Rule 5 does not apply to them), name, `RithamType.body`. No status/online
  indicator, no mutual-groups-count badge.
- **Add Friend**: exactly three rows, one per closed-loop connection path (Contact matching /
  Invite link or QR / In-person share), each a tappable `SecondaryCTAButton`-style row with a
  leading `SectionIconBadge` (rounded-square, not circular — this is an action-entry icon, not an
  identity avatar). Contact-matching's per-side opt-in toggle reuses the two-option
  `ChoiceQuestionView` chip control (03-09's `MovementSnapshotToggleView` precedent), never a native
  `SwiftUI.Toggle`.
- **Incoming friend request**: name + Accept (`PrimaryCTAButton`) + Decline (`SecondaryCTAButton`,
  not destructive-red — declining doesn't delete existing data, it's a neutral non-connection).

### Groups

- **Group list / Group detail**: group icon uses a rounded-square `SectionIconBadge` (a generic
  group glyph, e.g. `person.3.fill`, or a cropped rounded-square photo if the group sets one) —
  **not circular**, distinguishing group identity from person identity at a glance, consistent with
  `SectionIconBadge`'s existing rounded-square-vs-circular convention.
- **Member row**: circular avatar + name, plus a leave/remove affordance sized to
  `minimumTapTarget`. No organizer badge on the organizer's own row (see Color section above).
- **Leave Group**: confirmation sheet, `RithamColor.destructive`-styled confirm action
  (first activation of this token), offering the "also remove my past posts" choice explicitly at
  this step per the locked PRD requirement — a `ChoiceQuestionView` two-option chip
  ("Keep my past posts" / "Remove my past posts too"), never a silent default either way.
- **Remove Member**: same destructive confirmation pattern.

### Goal-Events, RSVP, and Completion Logging

- **Create Goal-Event**: form fields for activity type (`ActivityTypeIcon` picker, reusing the
  `WrapLayout` chip grid), optional target (distance/duration text entry), target date/window
  (native `DatePicker`). `PrimaryCTAButton` labeled per the locked copy: "Start a Group Goal" —
  never "Challenge," anywhere in this flow, including button labels, screen titles, and empty
  states.
- **RSVP screen** (separate screen from the feed, per the locked structural requirement):
  headline copy + `PrimaryCTAButton` "I'm in" + the headcount line below it
  (`RithamType.body` + `numerals()`), e.g. "6 friends are in." This number and this screen **never**
  appear again once the event has completions to show (Rule 2).
- **Completion logging**: binary "done" action (`PrimaryCTAButton`) → confirmation headline (locked
  copy, emoji preserved as specified — see Copywriting Contract note) → the equal-prominence
  Add time / Skip pair (see Spacing Scale above) → if "Add time" chosen, an inline numeric duration
  field (`RithamType.numerals()` on the entered value) with its own `PrimaryCTAButton` "Save," and
  "Skip"/"Never mind" still reachable to back out. Personal distance/duration/route fields, if the
  screen offers them at all, render under a clearly separate "Just for you — private" heading using
  `RithamType.fineprint()`, visually distinct from the group-shared fields above it, so the
  structural client/server separation (private fields never serialize into the group-visible
  request) has a matching visual separation a reviewer can eyeball.

### Photo + Location Attach, Privacy Zones

- **Photo attach**: native `PhotosPicker` (SwiftUI built-in, no custom picker UI to design). No
  visible EXIF-strip progress/spinner needed beyond the existing generic loading pattern — stripping
  is server-side and effectively invisible to the user.
- **Location attach**: separate, explicit opt-in from photo sharing (two independent
  `ChoiceQuestionView` two-option chips, never one combined switch). When enabled and a place
  resolves, show the resulting coarse place name as confirmation text before posting (e.g. "Griffith
  Park") — never a map, pin, or numeric distance. When the location falls inside a Privacy Zone and
  is suppressed, show a plain-language note instead of silently omitting the field:
  "This location is private and won't be shown." (new copy, see Copywriting Contract). If reverse
  geocoding fails, show no location field at all and no error — a silent no-op, matching the
  locked "never fall back to coordinates, never retry with a wider request" rule.
- **Privacy Zones settings**: a plain list of the user's saved zones, each shown only by its
  **user-given label** ("Home," "Workplace") — never a coordinate, address, or map thumbnail
  rendered in this list (the zone's precise definition lives entirely client-side per
  `04.1-RESEARCH.md` Pattern 3; the settings *list* itself should not re-expose that precision even
  to the owning user, keeping the UI's own visual habits from working against the "don't retain
  precision you don't need to display" principle the whole feature is built on). Add-zone flow uses
  a native map picker to *set* the zone (unavoidable — setting a zone requires picking a point) but
  the resulting saved-zone row never re-displays coordinates afterward.

### Group Feed and History

- **Feed card** (per completion, per §4's locked field list): circular avatar + name,
  `ActivityTypeIcon` badge + Goal-Event name + activity type, completion date, optional
  EXIF-stripped photo, optional generalized place name, optional short caption, `CheerReactionRow`.
  Card container: `RoundedRectangle(cornerRadius: RithamSpacing.sm)` on `paper.opacity(0.06)`,
  matching the Dashboard Section Card precedent — internal padding `RithamSpacing.md`.
- **Card renders identically regardless of own-time presence** except for the literal trailing time
  substring (see Color section — no color/badge differentiation). Verified by eye: a screenshot of a
  time-included and a time-omitted card, side by side, should differ *only* in that one substring.
- **Group history** (post-window): reuses the same feed-card component under a "Completed by:"
  heading, per the locked copy — no count, no fraction, ever (Rule 2).

### Digital Certificate

- **Reveal screen** (`.boundedHeaderOnly`): certificate composed via `ImageRenderer`
  (`CertificateComposer`), portrait card on a **`paper`-colored surface** (a deliberate local
  inversion from the app's usual `ink`-dominant screens — this artifact is designed to be exported
  and viewed outside Ritham's own charcoal-dominant chrome, so it reads correctly as a standalone
  image). Certificate content: Ritham wordmark, `ActivityTypeIcon` + event name + activity type,
  participant's own name (`RithamType.body`, the card's focal point), completion date
  (`RithamType.label`), own time only if opted in (`RithamType.label` + `numerals()`). Frame
  treatment reuses `HeroBandMotif`'s three-stripe hot/volt/paper diagonal band as a corner
  accent — a static brand ornament, not a ring, so Rule 5 does not apply to it.
- **Export flow**: a preview labeled "This is what will be shared outside Ritham," an editable
  display-name field (pre-filled from the event name, per the locked two-moment disclosure
  requirement) using a plain text field (not `ChoiceQuestionView` — free text is correct here, this
  is the one sanctioned free-text field in this phase's export path, distinct from HEALTH-01's
  no-free-text rule which governs the screening questionnaire only, not this feature). If the
  certificate's photo (non-default, user-selected group photo) contains other visible members, the
  export action is disabled with an inline note until every visible person's export-consent grant is
  recorded, or the user swaps in a solo photo/the default badge template. `PrimaryCTAButton`
  "Export."
- **Creation-time nudge** (on the Create Goal-Event screen, not the certificate screen): a single
  `RithamType.fineprint()` line beneath the event-name field — "This name will be visible on any
  exported certificate" (new copy, see below) — not a blocking interstitial, matching the PRD's
  "brief nudge" framing.

### Sign in with Apple entry point

- First-time-social-feature-use screen, `.boundedHeaderOnly`, plain-language explainer body
  (matching the Privacy Explainer precedent's tone and reading level — no legal-disclaimer sizing,
  per Typography above) stating this is optional and not required for core tracking.
- `SignInWithAppleButton` (`AuthenticationServices`), style `.white` (Apple's own guidance for a
  button on a dark/charcoal background — `.whiteOutline` is the closest visually-outlined
  alternative if `.white`'s solid fill reads too heavy against the surrounding `ink` screen; either
  is acceptable, `.black` is not, since it would nearly disappear against `ink`). Corner radius may
  be set to `RithamSpacing.sm` for visual consistency with every other rounded control in the app —
  this is one of the parameters Apple's HIG permits customizing; the button's internal label/logo
  content is not customizable and must not be recreated with `RithamColor`/`RithamType` tokens.
  Minimum height already satisfies `minimumTapTarget` by Apple's own default sizing.
- No `PrimaryCTAButton`/`SecondaryCTAButton` substitute for this control anywhere — Apple's App
  Store Review Guideline 4.8 requires the platform's own button for this specific action; do not
  reskin it to match the rest of the app's button vocabulary.

ranking — log it..." and "...5K Walk — 32:14."). Every existing `*Copy` file in this codebase

each substitution inline where the source text used one (see `MomentumCopy.swift`'s header
comment for the established precedent). `SocialCopy.swift` must do the same: the two rewrites above
preserve meaning, and each should carry the same kind of inline doc-comment explaining the
substitution when the file is built, so a future editor doesn't "restore" the em dash thinking it
was dropped by accident.

**Emoji note:** "🎉" is the **first emoji to appear in any of this project's locked `*Copy`
namespaces** — no existing copy file uses one. Because CONTEXT.md marks the full §2 table as locked
