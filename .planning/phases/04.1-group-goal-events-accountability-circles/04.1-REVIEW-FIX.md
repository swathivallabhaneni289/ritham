## Fixed Issues

### CR-01: Export-consent status endpoint has no authorization check, letting any authenticated user (including a departed group member) enumerate who is still withholding consent on a photo

**Files modified:** `RithamService/internal/feed/exportconsent.go`, `RithamService/internal/feed/exportconsent_test.go`
**Commit:** `b36a5e1`
**Status:** fixed

**Applied fix:** `ExportAllowed` now requires the caller to be either the photo's owner or one of its recorded subjects, exactly as the review's Fix section suggested — added `isRecordedSubject` alongside the existing `isPhotoOwner`, and short-circuits with the existing `ErrNotPhotoOwner` sentinel (already mapped to 403 by `statusForFeedError`, and already message-mapped by `feedErrorMessage`) when the caller is neither. No new sentinel error or status-mapping change was needed since `ErrNotPhotoOwner`'s existing 403 mapping already matches the review's suggested outcome for this route. This closes the gap regardless of the caller's current group membership: a former member (or any bystander) who is not a recorded subject or the owner is denied identically, with no separate membership lookup involved — recorded-subject status is the only durable grant this file makes, and it is unaffected by (and does not need to check) `group_members`.

**Regression test added:** `TestExportAllowed_BystanderDenied` — a bystander (never named as owner or subject) and a never-recorded caller (standing in for a departed group member reachable via `events.Completions`'s `photoAssetId`) both get `ErrNotPhotoOwner`; the real owner and the real recorded subject are confirmed unaffected in the same test. Follow-up commit `448c965` adds a handler-layer test, `TestHandleGetExportConsent_BystanderDenied`, asserting both halves of the fix task's stated proof obligation directly against `GET /v1/photos/{id}/export-consent`: the HTTP status is 403, and separately, the response body contains no `awaitingSubjectIds` key (nor decodes to a non-empty `ExportConsentResponse`) — the service-layer test alone only proved the sentinel error, not what the wire response actually contains.

**Deviation from the fix task's literal instruction (documented per instructions):** The fix task prompt describing this finding said "the caller must be a current member of the group the photo belongs to." The implemented fix instead requires owner-or-recorded-subject, matching `04.1-REVIEW.md`'s own Fix section verbatim rather than the paraphrase. These are not equivalent: owner-or-subject is *stricter* in one direction (a current group member who is neither the photo's owner nor a recorded subject — a bystander with no stake in the photo — is now denied, which a bare membership check would not catch) and *looser* in another (a recorded subject who is not, or is no longer, a group member is still let through). The looser direction is intentional and matches the review's own point 3: `RequestExportConsent` accepts subject IDs with no group-membership constraint at all, so a group-membership check here would either wrongly deny a legitimately-recorded subject who has left the group, or require inventing a group-membership backfill this file has no reason to own. Owner-or-subject is the correct scoping boundary for *this specific query* (who has a legitimate stake in a photo's consent status), not membership in whatever group the photo happens to be associated with. Flagging this explicitly so a future pass comparing against the fix task's literal wording doesn't re-raise it as unaddressed.

### WR-02: `SystemLocationFixProvider.currentFix()` drops and misattributes continuations when two calls overlap

**Files modified:** `RithamApp/Ritham/Social/Completion/LocationFixProviding.swift`, `RithamApp/RithamTests/CompletionLoggingTests.swift`
**Commit:** `41f1da9`
**Status:** fixed

**Applied fix:** `currentFix()` now captures the prior `pendingContinuation`/`activeManager` before overwriting them, detaches the prior manager's delegate (`previousManager?.delegate = nil`, so its callback can never reach `resume(with:)` once superseded), and resumes the prior continuation with `nil` immediately after — exactly the review's suggested fix, applied verbatim.

**Regression test added:** `systemLocationFixProviderResumesSupersededCallWithNil` (`CompletionLoggingTests.swift`) — exercises the real `SystemLocationFixProvider` (not a stub) against a new `NoOpCLLocationManager` subclass (overrides `requestWhenInUseAuthorization`/`requestLocation` as no-ops, so no real location hardware or authorization prompt is touched). Spawns two overlapping `currentFix()` calls via unstructured `Task`s, asserts the superseded first call resolves to `nil` (not a hang), then fires the delegate callback and asserts the still-active second call receives exactly its own fix.

**Test-ordering follow-up (commit `a0a9550`):** The original version of this test used a bare `Task.yield()` between spawning the two overlapping calls to order them, which only hints at scheduling order rather than proving it — under adversarial scheduling the second call's setup could in principle run before the first's, swapping the two assertions and failing the test on an unrelated ordering flake rather than a real regression. Replaced with a `LockedCounter` incremented from inside the injected `makeLocationManager` factory closure: `currentFix()` only calls that factory after `pendingContinuation`/`activeManager` are already assigned under its own lock, so waiting for the counter to reach 1 (then 2) proves each call's setup has fully completed before the next step proceeds. Verified deterministic across 5 consecutive isolated runs plus the full-suite run.
