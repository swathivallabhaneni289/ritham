## Fixed Issues

### CR-01: Export-consent status endpoint has no authorization check, letting any authenticated user (including a departed group member) enumerate who is still withholding consent on a photo

**Files modified:** `RithamService/internal/feed/exportconsent.go`, `RithamService/internal/feed/exportconsent_test.go`
**Commit:** `b36a5e1`
**Status:** fixed

**Applied fix:** `ExportAllowed` now requires the caller to be either the photo's owner or one of its recorded subjects, exactly as the review's Fix section suggested — added `isRecordedSubject` alongside the existing `isPhotoOwner`, and short-circuits with the existing `ErrNotPhotoOwner` sentinel (already mapped to 403 by `statusForFeedError`, and already message-mapped by `feedErrorMessage`) when the caller is neither. No new sentinel error or status-mapping change was needed since `ErrNotPhotoOwner`'s existing 403 mapping already matches the review's suggested outcome for this route. This closes the gap regardless of the caller's current group membership: a former member (or any bystander) who is not a recorded subject or the owner is denied identically, with no separate membership lookup involved — recorded-subject status is the only durable grant this file makes, and it is unaffected by (and does not need to check) `group_members`.

**Regression test added:** `TestExportAllowed_BystanderDenied` — a bystander (never named as owner or subject) and a never-recorded caller (standing in for a departed group member reachable via `events.Completions`'s `photoAssetId`) both get `ErrNotPhotoOwner`; the real owner and the real recorded subject are confirmed unaffected in the same test.

### WR-01: Certificate export flow shows a false "everyone must approve" message on a network failure, with no recovery path

**Files modified:** `RithamApp/Ritham/Social/Certificate/CertificateExportView.swift`, `RithamCore/Sources/RithamCore/Copy/SocialCopy.swift`
**Commit:** `da495fa`
**Status:** fixed

**Applied fix:** Added two new `SocialCopy.Certificate` strings — `exportGateCheckFailed` (transport-failure-specific copy that makes no claim about other people's consent state) and `retryExportGateCheckCTA` — and wired the `.failed` gate-state branch in `gateSection` to show the new copy plus a "Try again" `SecondaryCTAButton` that re-runs `model.checkExportGate(for:)` with the same photo-or-nil argument the view's own `.task(id: useDefaultTemplate)` modifier already passes. Kept the existing `useDefaultTemplateCTA` fallback button available in the `.failed` branch too (previously only present in `.blocked`), so a transient network failure no longer strands the user with two ways forward instead of zero.

**Note:** No existing test asserted the exact copy string shown in the `.failed` state (only the `gateState == .failed` enum transition itself, in `CertificateTests.swift`'s `"a failed gate query fails closed -- export stays unavailable"`), so no test needed updating; the existing `"CertificateExportView.swift references SocialCopy.Certificate at least three times"` count-based test still passes with the two new references added.

### WR-02: `SystemLocationFixProvider.currentFix()` drops and misattributes continuations when two calls overlap

**Files modified:** `RithamApp/Ritham/Social/Completion/LocationFixProviding.swift`, `RithamApp/RithamTests/CompletionLoggingTests.swift`
**Commit:** `41f1da9`
**Status:** fixed

**Applied fix:** `currentFix()` now captures the prior `pendingContinuation`/`activeManager` before overwriting them, detaches the prior manager's delegate (`previousManager?.delegate = nil`, so its callback can never reach `resume(with:)` once superseded), and resumes the prior continuation with `nil` immediately after — exactly the review's suggested fix, applied verbatim.

**Regression test added:** `systemLocationFixProviderResumesSupersededCallWithNil` (`CompletionLoggingTests.swift`) — exercises the real `SystemLocationFixProvider` (not a stub) against a new `NoOpCLLocationManager` subclass (overrides `requestWhenInUseAuthorization`/`requestLocation` as no-ops, so no real location hardware or authorization prompt is touched). Spawns two overlapping `currentFix()` calls via unstructured `Task`s with `Task.yield()` between them to deterministically order the overlap, asserts the superseded first call resolves to `nil` (not a hang), then fires the delegate callback and asserts the still-active second call receives exactly its own fix. Passed both in isolation and as part of the full suite run.
