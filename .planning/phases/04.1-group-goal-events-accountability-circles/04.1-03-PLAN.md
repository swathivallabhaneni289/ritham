<objective>
Give `RithamService` its first real identity: Sign in with Apple verification, an opaque revocable
session token, and the bearer-authentication middleware every later route in this phase sits
behind.

Purpose: `cmd/ritham-service/main.go`'s own header comment states the precondition this plan
resolves — "This endpoint has no authentication in this first pass... Adding real hosting requires
deciding an authentication story first." 04.1-CONTEXT.md's Identity and Account Recovery section
locks that story as **Sign in with Apple only**, superseding 04.1-RESEARCH.md Pattern 6's
device-keypair recommendation. The session and token architecture around identity issuance is
unchanged by that supersession and is still Pattern 6's: an opaque, high-entropy, server-side
revocable token stored only as a hash, not a stateless JWT, so a lost device can actually be cut
off.

Cross-device continuity falls out of this rather than needing its own flow: the same Apple ID on a
new device resolves to the same `users.id`, which is what every later table keys off, so the friend
graph, group memberships, and certificate archive come back with the account.

Output: the `internal/identity` package, `httpapi` authentication middleware, two new routes, and
the corrected header comment on `main.go`.
</objective>

  <behavior>
    - First sign-in with a given Apple subject inserts a user row and returns a new user id.
    - Second sign-in with the same subject returns the same user id — the cross-device continuity
      guarantee — and does not insert a duplicate row.
    - Two different Apple subjects never resolve to the same user id.
    - An issued session token is at least 32 bytes of entropy, base64url-encoded, and is returned
      to the caller exactly once.
    - The `sessions` row for an issued token contains a 32-byte digest; a query for the plaintext
      token value against every text column of the row finds nothing.
    - Authenticating with a valid unexpired token yields its user id.
    - Authenticating with a token that was revoked fails on the very next call.
    - Authenticating with a token past its expiry fails, evaluated against the injected clock.
    - Authenticating with a token that was never issued fails with the same sentinel as a revoked
      one, so a caller cannot distinguish the two.
    - A display name longer than the maximum length is rejected rather than truncated.
  </behavior>
  <action>
    Write `identity_test.go` first. It requires a database, so follow plan 04.1-01's
    `store_test.go` convention exactly: run against `RITHAM_DATABASE_URL` when set, and `t.Skip`
    with an actionable message naming the compose command when it is not.

    Implement `session.go`. `IssueSession` generates the token with `crypto/rand`, encodes it
    base64url, computes `hashToken` with `crypto/sha256`, and inserts only the digest, the user id,
    and `now + sessionTTL`. The plaintext is returned to the caller and never stored, logged, or
    included in any error string.

    `AuthenticateBearer` hashes the presented token and selects the session by digest with
    `revoked_at IS NULL AND expires_at > now()` as part of the query's own WHERE clause, not as a
    separate Go-side check — so an expired or revoked row cannot be resurrected by a later code
    path that forgets to test it. Any miss returns `ErrSessionInvalid`; there is exactly one
    sentinel for every failure so the caller cannot leak which condition failed.

    `RevokeSession` stamps `revoked_at`. `SignInWithApple` verifies the token via Task 1, upserts
    the user on `apple_subject` with `ON CONFLICT (apple_subject) DO UPDATE` returning the id, sets
    the display name when one is supplied and the stored one is empty, then issues a session.
    `SetDisplayName` bounds length at `displayNameMaxLen` and rejects rather than truncates.

    Never hand-roll a signing or hashing scheme: `crypto/rand` for entropy and `crypto/sha256` for
    the digest are the whole cryptographic surface here, per 04.1-RESEARCH.md's Don't Hand-Roll
    table and Security Domain V6.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → `POST /v1/identity/apple` | An untrusted, attacker-controllable identity token enters the system |
| Apple JWKS endpoint → service | External key material the signature check depends on |
