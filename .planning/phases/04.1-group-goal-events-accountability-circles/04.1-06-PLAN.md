<objective>
Build the mutual friend graph and its three closed-loop connection paths, server-side.

Purpose: HOUSEHOLD-02 asks for a friend-level accountability circle beyond household, and
GROUPEVENTS-01 constrains exactly how a person can become reachable: mutual and request-based
only, never a one-directional follow, with no public profile search and no contact scan that runs
without explicit per-side opt-in. `docs/group-events.md` §1 names the reason — Peloton's May 2024
incident made full legal names and searchable profiles visible by default, so Ritham has no state
a user can be in without having said yes twice. Exactly three paths exist, and this plan builds all
three and nothing else.

Output: the `internal/friends` package, migration `0003_friends`, and seven authenticated routes.
</objective>

  <behavior>
    - Sending a request creates no friendship; listing friends for either party returns nothing
      until the recipient accepts.
    - Accepting creates exactly one friendship row, and both users then list each other.
    - The stored pair is unordered: whichever direction the request went, the row satisfies the
      ordering constraint, and no second row is ever created for the reverse direction.
    - Declining resolves the request and creates nothing.
    - A user cannot send a request to themselves.
    - A second pending request between the same ordered pair is rejected rather than duplicated.
    - Sending a request to someone who is already a friend is rejected.
    - Accepting or declining a request addressed to someone else fails, and fails with the same
      not-found sentinel as a request that does not exist.
    - Unfriending removes the single pair row, and afterwards neither user lists the other.
    - `AreFriends` is symmetric: it returns the same answer for either argument order.
  </behavior>

  <behavior>
    - A created invite returns its token once; the stored row holds only a digest.
    - Redeeming a valid invite creates a friend request from the issuer to the redeemer, and marks
      the invite consumed.
    - Redeeming the same invite a second time fails with the consumed sentinel and creates nothing.
    - Redeeming after the expiry window fails with the expired sentinel, evaluated against the
      injected clock.
    - Redeeming an unknown token fails with the unknown sentinel, and the error is indistinguishable
      from a consumed one at the HTTP layer.
    - The issuer redeeming their own invite fails.
    - Contact matching with the caller opted out returns the opted-out sentinel and performs no
      lookup at all.
    - Contact matching with the caller opted in but the candidate opted out returns no match.
    - A match is returned only when both the caller and the candidate are opted in and the
      candidate's stored digest set contains one of the submitted digests.
    - Submitting more than the per-request digest cap is rejected.
    - Turning the opt-in off deletes the user's stored digests, so opting out is not merely a flag.
  </behavior>
  <action>
    Write both test files first.

    Implement `invites.go`. Generate the token with `crypto/rand`, return the plaintext once, store
    only a SHA-256 digest — the same discipline plan 04.1-03 applied to session tokens, for the same
    reason. Redemption is a single transaction that conditionally updates the row on
    `consumed_at IS NULL AND expires_at > now()` and creates the friend request only if that update
    affected a row, so two concurrent redemptions cannot both succeed. `docs/group-events.md` §1's
    requirement is that links die: a permanent forwardable link is public discoverability wearing a
    different hat, so the TTL and the single-use rule are both enforced in that one statement's
    WHERE clause rather than by a pre-check the second caller could race past.

    Implement `contactmatch.go`. The client sends digests, never raw contact identifiers — the doc
    comment states that Ritham's backend has no reason to hold a contact list and does not. Digests
    are salted with a fixed server-side application salt so the stored values are not a plain
    dictionary of hashed identifiers; the salt is read from the environment with a documented
    default for local development.

    `SetContactMatchOptIn(optedIn: false)` deletes the user's digest rows in the same transaction
    as the flag update. `MatchContacts` returns the opted-out sentinel before touching the digest
    table when the caller is not opted in, and its query joins the candidate's own opt-in row so a
    candidate who never opted in cannot be surfaced by anyone. Bound the submitted digest count.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → friends routes | A caller asserts who they want to connect to, and which request to resolve |
| invite token → friend request | A bearer-style secret grants the ability to open a connection |
| contact digests → match results | Data derived from a device address book crosses into the server |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04.1-29 | Spoofing | invite-link forgery, reuse, or forwarding | high | mitigate | Tokens are `crypto/rand` values stored only as digests, single-use and window-expiring, with both conditions enforced inside the conditional update's WHERE clause so concurrent redemptions cannot both win. Implements 04.1-RESEARCH.md's "Invite-link forgery/reuse" row and `docs/group-events.md` §1's links-die requirement. |
| T-04.1-30 | Elevation of Privilege | resolving a friend request addressed to someone else | high | mitigate | Every mutating query is scoped by the context user id; acting on another user's request returns the same not-found sentinel as a nonexistent one. Implements Security Domain V4. |
| T-04.1-31 | Information Disclosure | probing which invite tokens have ever existed | medium | mitigate | Unknown, consumed, and expired invites all map to one status and one message, asserted byte-identical by test. |
| T-04.1-32 | Information Disclosure | contact matching revealing a user who never opted in | high | mitigate | The match query joins the candidate's own opt-in row, so a one-sided opt-in returns nothing; opting out deletes the stored digests rather than only clearing a flag. Implements GROUPEVENTS-01's both-sides-opt-in requirement. |
| T-04.1-33 | Information Disclosure | the server accumulating a contact address book | high | mitigate | Only salted digests are accepted and stored; no route accepts a raw contact identifier, and the digest table has no column for one. |
| T-04.1-34 | Denial of Service | oversized contact-match submissions | medium | mitigate | Per-request digest cap plus the existing body-size bound on every route. Implements Security Domain V5. |
| T-04.1-35 | Spoofing | a request body naming a different acting user | high | mitigate | No request type in this plan has an actor field; the acting id comes only from the authenticated context. |
</threat_model>
