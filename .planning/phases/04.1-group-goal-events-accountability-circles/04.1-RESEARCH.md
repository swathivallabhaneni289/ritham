### Locked Decisions

Every decision below is locked from `docs/group-events.md` (the full PRD) unless flagged
otherwise. Section references (§1-§5) point back to that document.

**Friends & Groups (HOUSEHOLD-02, GROUPEVENTS-01) — §1**
- Friending is mutual/request-based only — never a one-directional follow. No public profile
  search, no contact-scan without explicit per-side opt-in.
- Exactly three closed-loop connection paths, no others: (1) contact matching, off by default,
  match surfaces only when both sides opted in; (2) invite link/QR, expires after a set window or
  first use, never permanent/forwardable; (3) in-person/direct share, no in-app directory.
- Groups are small, closed, invite-only, sent only to existing friends. No public/joinable tier.
  Invisible to search, not listed on any profile, generates no public/aggregate signal.
- Any member can leave anytime, no ownership-transfer gate. Organizer leaving → group continues,
  no auto-promotion.
- Removing a member: any member, or organizer-only, per group preference. No admin-approval queue.
- Group size intentionally small (no PRD-given cap — Claude's Discretion, see Assumptions Log).
- Visibility ladder capped at exactly three rungs: Only Me → Household → this specific group. No
  "friends of friends," no "Public/Everyone," anywhere in this feature. Anything shared beyond the
  group boundary is a deliberate, individual export (§5), never a setting that widens passive
  visibility.

**Goal-Events (GROUPEVENTS-02) — §2**
- A Goal-Event is a shared, non-timed commitment, not a race. Organizer sets: activity type,
  optional target (distance/duration), target date/window. No synchronized start, no clock.
- RSVP is individual, shown pre-event only as a headcount, on a screen separate from the
  post-event completion feed (deliberate separation).
- Logging completion is binary: done. Own distance/duration/route optionally recorded to the
  user's personal, private log only — never travels to group feed, certificate, or export.
- Adding own completion time is optional, off by default, asked at the moment of logging,
  skippable with zero friction. Never ranked/sorted/scored against anyone else's.
- No ranking mechanism of any kind: no pooled total, no contribution ranking, no leaderboard sort,
  no score, no winner, no comparison of who did/didn't include a time.
- Feed order is chronological by post time — never sorted fastest-to-slowest. No ordinal position,
  medal, or "1st" marker, ever.
- Non-completion is a non-event: completion feed shows positive completions only — no greyed-out
  avatar, no "hasn't finished" state, no denominator paired with the completion view. Event closes
  silently at the target date/window. Already-logged completions stand permanently.
- Literal copy strings are locked verbatim from §2's table — carry into a copy catalog rather than
  re-authoring equivalents.

**Photo + Location Privacy (GROUPEVENTS-03) — §3**
- Standing structural exclusion, permanent: Ritham will never build a cross-user aggregate
  location visualization (heatmap, "most active area," any multi-user map feature).
- EXIF GPS and all EXIF metadata is stripped server-side, unconditionally, before any image is
  written to group-visible or exportable storage — regardless of what the client claims to have
  stripped. A required negative test: no code path may write an image to shared/exportable storage
  without having gone through server-side EXIF stripping first.
- Original file (metadata intact) retained only in the user's own private library — never in the
  group-served or exported copy.
- Location sharing is a separate, explicit opt-in from photo sharing — never bundled.
- Precise coordinates for a completion log are not captured/stored at all by default — not
  captured-then-hidden. Exception: a user separately opting into a personal route view (own
  private map only) — that data never reaches the group feed, certificate, any aggregate, or any
  export.
- Default display (if location shared): reverse-geocoded coarse named place — never coordinates,
  a pin, an address, or any numeric radius/distance figure.
- Privacy Zones: user-set sensitive locations (home, workplace), set once. Any activity/photo
  whose location falls inside a zone is automatically generalized or fully suppressed across every
  shared surface without re-toggling per-post.
- An event's coordination location (e.g., exact trailhead address) must never leak into anything
  the group later shares outside itself.

**Shared Feed (GROUPEVENTS-04) — §4**
- Visibility: the group, and only the group, by default and permanently. Not public, not
  discoverable, not indexed, no generic shareable link.
- Leaving/removal ends future feed access; past completion cards remain visible to the group. A
  leaving user may also choose to remove their own past posts as part of the leave flow — offer
  explicitly at the leave step.
- Per-completion card shows: name/avatar, Goal-Event name + activity type, completion date,
  optional photo (EXIF-stripped), optional generalized location, optional short caption, fixed
  non-comparative cheers (same cheer set used elsewhere in Ritham — no kudos count).
- Never shows: pace, time-based rank, "first to complete," a denominator paired against
  completions, or anyone's precise location.
- Group goal-event history (past events + who completed each) lives in this same closed space.

**Digital Certificate (GROUPEVENTS-05) — §5**
- On it: Ritham branding, Goal-Event name + activity type, participant's own name, completion
  date, own completion time only if opted in.
- Never on it: pace, measured distance, place/rank within the group, exact GPS/address, any other
  member's name/photo/status/time, any "X of Y completed" figure.
- Auto-generates per person the moment they log completion. Default template is a branded
  graphic/badge, not the user's own photo — deliberate default.
- Posts to the group feed alongside/as the completion card automatically — no separate send step.
- External export contains only the exporting user's own data. Must never contain a member
  count/roster/"X of Y" figure, a person-identifying group name, or any other member's
  name/photo/status. If a group photo (not the default badge) contains other visible members,
  external export requires either every visible person's separate export-consent grant for that
  specific photo, or the exporter crops/selects a solo shot.
- Event names are free text and can be a location/identity disclosure. Two-moment check required:
  (1) creation-time nudge to the organizer; (2) export-time editable display-name field for the
  exporter, without altering what the group sees.
- The export path goes through the same server-side EXIF-stripping guarantee as any other shared
  image — no exemption.
- Past certificates accumulate in the user's own private record (visible to them and, at most,
  their household) — never ranked/ordered against anyone else's.

## Summary

This phase adds Ritham's first real multi-user backend surface. Today `RithamService` is a single
unauthenticated, loopback-only Go endpoint with zero persistence, and `RithamApp` has zero
multi-user identity concept (`UserProfile` is one local-device record; `MomentumVisibility` has
exactly one case, `.privateToDevice`). Nothing about identity, sessions, a friend graph, group
membership, photo storage, or real-time feed delivery exists to build on. This phase must build all
of it, not extend something partial — including the fixed "cheer" reaction mechanic, which
CONTEXT.md's canonical refs describe as something to "locate and extend": **it does not exist
anywhere in the codebase** (verified by grep across `RithamApp` and `RithamCore` for
cheer/kudos/reaction/niceWork/keepGoing terms — zero hits). Only the *product rule* it should
follow (fixed, non-comparative reactions) is established precedent; the code is not.

The product-privacy rules in `docs/group-events.md` are unambiguous and should be implemented
literally — they are the highest-confidence part of this research. The technical infrastructure
choices (identity/auth model, database, object storage, real hosting, push vs. polling) have no
precedent in this codebase and are reasoned defaults, each tagged `[ASSUMED]` and logged for
confirmation. Two hard correctness gaps were found during this research that the PRD does not
anticipate and the planner must account for: (1) Go's standard `image` package cannot decode HEIC,
the format iPhones capture by default, so the EXIF-strip pipeline will silently reject most real
uploads unless the client transcodes to JPEG first; (2) evaluating a Privacy Zone requires the
precise coordinate at the moment of capture, which forces a specific on-device evaluation order
before any coordinate is discarded or geocoded — get this order wrong and either the zone
protection or the "never store precise coordinates" guarantee breaks.

**Primary recommendation:** Build identity as a device-keypair-issued opaque user ID with a
revocable server-issued session token (not email/password, not a stateless JWT alone); stand up a
Postgres-backed Go service behind real (non-loopback) hosting with an S3-compatible object store
for photos; strip EXIF via Go's stdlib decode/re-encode cycle (which is metadata-blind by
construction) after the client transcodes HEIC→JPEG; reverse-geocode client-side via `CLGeocoder`
(which calls Apple's servers, not Ritham's — flag as a processor disclosure for Phase 5) with a
hard field allowlist and a Privacy-Zone check that runs *before* geocoding; render the certificate
client-side with SwiftUI's `ImageRenderer`; and ship the visibility ladder as two rungs now (Only
Me → this group), with the Household rung's slot reserved in the data model per the exact precedent
Phase 3 already set for this identical problem (`MomentumVisibility`/MOMENTUM-06).

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Identity/session (opaque user ID, bearer token) | API/Backend | Browser/Client (keypair + Keychain) | Server issues and can revoke the identity token; client generates and privately holds the signing key |
| Friend graph (requests, mutual accept, contact-match, invite tokens) | API/Backend | Client (local cache for offline view) | Mutual state must be server-authoritative so both sides see the same truth |
| Group membership (create/join/leave/remove) | API/Backend | Client | Same reason — membership is shared, multi-device state |
| Goal-Event definition + RSVP headcount | API/Backend | Client (local RSVP cache) | Shared across group members; needs one source of truth |
| Completion logging — binary "done" + optional public time | API/Backend | Client | The fact of completion and an optionally-shared time are group-visible, server-persisted facts |
| Completion logging — private distance/duration/route | Client only | — | By construction never leaves the device; no backend field should exist for it |
| Photo upload + EXIF stripping | API/Backend | Client (HEIC→JPEG transcode pre-upload) | Stripping must be server-side and unconditional per GROUPEVENTS-03; client only prepares a decodable format |
| Location capture, Privacy Zone evaluation, reverse geocoding | Client only | — | Precise coordinates must never reach the backend; the entire capture→zone-check→geocode→discard sequence is on-device |
| Privacy Zone definitions (home/workplace) | Client only | — | Storing a user's home address server-side is exactly the leak this feature exists to prevent |
| Shared feed (query, pagination, ordering) | API/Backend | Client (rendering, poll cache) | Membership-scoped, multi-device shared state |
| Digital certificate rendering | Client only | API/Backend (supplies the underlying fields) | No server-side templating/rendering service needed; SwiftUI can compose the whole artifact locally |
| Export consent gating (multi-person-photo grants) | API/Backend | Client (consent UI) | Consent grants are cross-user facts that must be checked from any exporting device |
| Real-time-ish delivery (feed/RSVP/friend-request updates) | API/Backend | Client (poll timer, pull-to-refresh) | No push infrastructure exists (see Environment Availability); REST polling is both the safe and the only currently available mechanism |

### Alternatives Considered

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| Device keypair + opaque server ID (recommended identity model) | Full email/password account system (promoting Phase 999.2) | Heavier scope now (password reset, email verification/deliverability, credential-compromise handling) for a benefit (cross-device continuity) this phase's PRD doesn't strictly require; also collides with the still-open device-continuity question in `STATE.md` (GitHub issue #1) — flagged in Open Questions, not resolved here |
| Postgres (recommended) | SQLite (`modernc.org/sqlite`) | SQLite is lower-friction for local dev before a hosting provider is chosen, but weaker for concurrent multi-writer access once real users exist; recommend Postgres for the shipped backend, SQLite only as a dev/CI convenience |

| Polling (recommended for phase 1) | APNs push for feed/RSVP/friend-request events | No push entitlement exists in this project yet (`find` for `*.entitlements` returns nothing) and no real hosting/cert story exists either — APNs needs both; polling matches the only existing networking pattern (`WorkoutPlanClient`'s single-shot request/response) and needs zero new infrastructure decisions to ship this phase |
| Server-side reverse geocoding (a Go-side geocoding API/dataset) | Client-side `CLGeocoder` (recommended) | Server-side would require Ritham's backend to receive and process a coordinate at least once, plus a geocoding API key/dataset dependency; client-side means Ritham's servers *never* receive a coordinate for the default share path — stronger match for GROUPEVENTS-03's "don't capture precise coordinates" language, at the cost of Apple (not Ritham) becoming a processor of that coordinate |
| `rwcarlsen/goexif` for orientation only (recommended) + hand-rolled rotation | `github.com/go-oss/image/imageutil.RemoveExif` (does strip+rotate in one call) | `go-oss/image` is more convenient but last released 2018 with low adoption — worse legitimacy profile than a narrow, read-only use of a merely-stale-but-widely-used library; see Don't Hand-Roll for why the rotation step itself is a deliberate exception to "don't hand-roll" |

### Pattern 1: Data-minimization request-shape discipline (extend existing precedent, don't invent a new one)

**What:** `RithamService/internal/httpapi/contract.go`'s `WorkoutPlanRequest` is a documented,
test-locked "entire set of values permitted to leave the device" — its exact three-field shape is
asserted by reflection in `handler_test.go`, and the client-side mirror in `WorkoutPlanClient.swift`
carries the identical warning and an equivalent test. Every new request/response type this phase
introduces (completion-log payload, photo-upload metadata, location payload) must follow the same
discipline: a header comment stating the complete field list and why each field is there, plus a
shape-locking test (reflection-based in Go, JSON-key-set assertion in Swift) so a future edit that
widens the boundary (e.g., accidentally adding a raw coordinate field) fails a test, not a review.

**When to use:** Every new endpoint this phase adds, especially the completion-log and photo/location
endpoints, since those are exactly where GROUPEVENTS-02's "private route/pace never leaves the
device" and GROUPEVENTS-03's "precise coordinates never captured" guarantees must be structurally
enforced, not just documented.

**Example (illustrative — pattern derived from `RithamService/internal/httpapi/contract.go`):**
```go
// CompletionRequest is the entire set of values permitted to leave the device when logging a
// Goal-Event completion. It intentionally has NO distance/pace/route field -- those stay in the
// user's personal, private log only (GROUPEVENTS-02). CompletionRequestFieldsTest asserts this
// exact field count by reflection, so widening this struct fails a test gate rather than shipping
// silently.
type CompletionRequest struct {
    EventID       string  `json:"eventId"`
    CompletedAt   string  `json:"completedAt"`   // RFC3339
    OwnTimeSeconds *int   `json:"ownTimeSeconds,omitempty"` // nil unless the user explicitly opted in
}
```

### Pattern 2: EXIF-strip pipeline (structural, not filter-based)

**What:** Go's `image` package (`image.Decode`) discards all metadata by construction — an
`image.Image` value has no field that could carry an EXIF/XMP segment. A decode-then-re-encode
round trip through only the standard library therefore cannot emit metadata, regardless of what
was in the source bytes. This is the structural guarantee GROUPEVENTS-03 asks for ("a required
negative test: no code path may write an image to shared/exportable storage without having gone
through server-side EXIF stripping first").

**Critical gap this research found:** Go's standard `image` package registers JPEG, PNG, and GIF
decoders only — **there is no HEIC/HEIF decoder in the standard library**, and iPhones capture
HEIC by default. `image.Decode` will fail outright on a raw HEIC upload. **Recommendation: the
client transcodes HEIC→JPEG on-device before upload**, using Apple's own `ImageIO`/
`UIImage.jpegData(compressionQuality:)` (built into the iOS SDK, zero third-party dependency) — the
client already has the original HEIC file in its private library regardless, so this transcode is a
one-time, local, no-new-dependency step. This keeps the server-side pipeline entirely within Go's
stdlib decoder set and avoids taking a cgo/libheif dependency on the security-critical path.

**Orientation correctness:** A naive decode/re-encode strips the EXIF orientation tag along with
everything else, which can make a sideways/upside-down photo render sideways after stripping. The
pipeline must read the orientation tag (via `rwcarlsen/goexif`, read-only, narrow use — see
Standard Stack) **before** discarding metadata, apply the corresponding rotation to the decoded
pixel buffer, and only then re-encode. See Don't Hand-Roll for why the rotation step itself should
be hand-rolled rather than adding a second, less-legitimate image-processing dependency.

**Required negative test (tightened from a naive "no APP1/Exif" check):** APP1 also carries XMP
under a different signature, and PNG carries `eXIf`/`tEXt` chunks — a narrow "no `Exif` string"
check would miss those. Assert instead that the re-encoded output contains **no APPn segment other
than APP0/JFIF** (for JPEG) and **no `eXIf`/`tEXt`/`zTXt`/`iTXt` chunk** (for PNG), plus a
belt-and-suspenders parse-and-assert-no-GPS-IFD check using the same read-only EXIF reader used for
orientation.

**Example (illustrative pipeline shape):**
```go
// StripAndReencode is the ONLY code path permitted to write an image to group-visible or
// exportable storage (GROUPEVENTS-03). It never receives raw client bytes directly -- callers
// must route every upload through this function. img must already be JPEG or PNG (client
// transcodes HEIC before upload).
func StripAndReencode(raw []byte) ([]byte, error) {
    orientation := readOrientationOnly(raw) // narrow EXIF read, orientation tag only -- never GPS
    img, _, err := image.Decode(bytes.NewReader(raw)) // metadata-blind by construction
    if err != nil {
        return nil, fmt.Errorf("decode: %w", err) // e.g. unsupported format (HEIC) fails here
    }
    img = applyOrientation(img, orientation) // hand-rolled 8-case pixel rotation/flip
    var out bytes.Buffer
    if err := jpeg.Encode(&out, img, &jpeg.Options{Quality: 85}); err != nil {
        return nil, fmt.Errorf("encode: %w", err)
    }
    return out.Bytes(), nil // guaranteed: no APPn beyond APP0, asserted by StripAndReencodeTest
}
```

### Pattern 3: Privacy Zone evaluation ordering (load-bearing sequence, all on-device)

**What:** Evaluating "does this location fall inside a Privacy Zone" requires the precise
coordinate at evaluation time — Privacy Zones cannot be checked against a coarse place name. This
means the "never capture precise coordinates" guarantee and the Privacy Zone guarantee are only
both true if the sequence is followed exactly, entirely on the client:

1. Capture a **transient** location fix (`CoreLocation`) — held only in memory, never persisted as
   raw coordinates.
2. Evaluate the fix against the user's Privacy Zones (stored **on-device only** — see below).
3. **If inside any zone:** suppress or generalize per the zone's setting, and stop — no geocoding
   call is made, nothing is sent to the server.
4. **If outside every zone:** reverse-geocode via `CLGeocoder`, extract only an allowlisted field
   set (`locality`, `subLocality`, `areasOfInterest`, `administrativeArea` — never `thoroughfare`
   or `subThoroughfare`, which carry street-level precision), and send only the resulting place-name
   *string* to the server.
5. Discard the coordinate. It is never written to any store, on-device or server-side, beyond this
   in-memory sequence (except the separate, explicitly-opted-into personal route view, which is a
   different, private-only data path per §3).

**Privacy Zone definitions must themselves live on-device only** (e.g., the same
file-protection-backed local storage tier the health screening data already uses — see the
file-protection read-back precedent noted for `01-11` in `STATE.md`). A server-stored home address
is precisely the leak this feature exists to prevent; there is no reason for Ritham's backend to
ever see a Privacy Zone's coordinates.

**Processor-disclosure note for Phase 5 (LAUNCH-04):** `CLGeocoder` is **not** on-device processing
— `reverseGeocodeLocation` sends the coordinate to Apple's own geocoding servers and returns a
`CLPlacemark`. Ritham's backend never receives the coordinate, but Apple does, making Apple a
third-party processor of that (transient, in-memory-only, immediately-discarded) coordinate. Flag
this explicitly for Phase 5's GDPR/CCPA review rather than assuming "on-device" covers it.

**Fallback behavior:** `CLGeocoder` is rate-limited and network-dependent. If a reverse-geocode
call fails or times out, the completion must post with **no location at all** — never fall back to
showing coordinates, and never silently retry with a wider/less specific request that could leak
more.

### Pattern 4: Client-side certificate composition with a server-stripped-image guarantee

**What:** Compose the certificate entirely on-device using SwiftUI's `ImageRenderer` (available at
the project's iOS 17 floor) — brand frame + event name + participant name + date + optional time,
merged into a rendered image, with no server-side template/rendering service needed for a phase
that is already introducing substantial new backend surface.

**Structural catch (a second required negative test):** if a user chooses to composite their own
event photo into their certificate instead of the default branded badge, **the certificate must use
the server-stripped copy of that photo, never the client's local original** — otherwise the export
path silently bypasses GROUPEVENTS-03's EXIF-stripping guarantee even though the pipeline
technically ran (it just wasn't the copy that got used). The certificate-composition code should
only ever have a reference to the stripped, group-visible photo asset, never a file-system path to
the private-library original — making the bypass structurally unreachable rather than a
convention to remember.

### Pattern 6: Identity — minimum viable model (Claude's Discretion item 2)

**What:** No accounts/auth/server-side user record exist anywhere in this codebase today.
`RithamService/cmd/ritham-service/main.go`'s own header comment states the precondition this phase
must satisfy: *"This endpoint has no authentication in this first pass. It is bound to the loopback
interface for exactly that reason... Adding real hosting requires deciding an authentication story
first."* This phase is that decision.

**Recommendation:** a device-generated asymmetric keypair (via `CryptoKit`, private key in
Keychain) registers with the server on first social-feature use (not mandatory at onboarding — this
matches CROSSGEN-03's "nothing shared/synced by default" and the app's existing local-first
posture). The server issues an **opaque user ID** and a **revocable session token** — a random
high-entropy value, stored server-side only as a hash (matching common Go API-token patterns), not
a stateless JWT. Recommend opaque-and-revocable over pure JWT specifically because device loss
needs to be a real "revoke this device's access" action, which a stateless JWT cannot do without a
blocklist; `golang-jwt/jwt` is kept in Supporting Stack for a possible future email/login layer
(Phase 999.2), not as this phase's core mechanism.

**This is the single highest-stakes `[ASSUMED]` claim in this research** — see Open Questions and
the Assumptions Log. A device-keypair-only model means losing a phone loses that device's identity,
friend graph, group memberships, and certificate archive, with no recovery path, unless a future
phase adds account recovery. This directly intersects the still-open, still-undecided
device-continuity question already logged in `STATE.md` ("GitHub issue #1's device-continuity
question is still open... Not yet decided or built"). This research recommends proceeding with the
keypair-only model for this phase (it is sufficient for the PRD's stated mutual-friending/group
mechanics) while shaping the server-side user record so an email/login credential could be attached
to an existing opaque user ID later with no migration — but this needs explicit user confirmation
before being treated as locked, given the data-loss stakes.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| Session/bearer token authentication | A custom crypto scheme for signing/verifying tokens | Opaque high-entropy tokens (Go stdlib `crypto/rand` + `crypto/sha256` for at-rest hashing) or, for a future stateless layer, `golang-jwt/jwt/v5` | Token forgery/replay is a well-studied failure mode; hand-rolled signing schemes are exactly the ASVS V6 anti-pattern |
| Device keypair generation | A custom key-generation/storage routine | `CryptoKit` + Keychain | Apple's own frameworks are the audited, platform-integrated choice for exactly this; nothing about this phase's needs justifies a custom implementation |
| EXIF metadata stripping (the *decode/re-encode* step) | A hand-written EXIF-segment parser/stripper | Go stdlib `image`/`image/jpeg`/`image/png` decode-then-re-encode | The stdlib is metadata-blind by construction — this is the one case where the "obvious" library-shaped solution (a dedicated EXIF-stripping library) is *less* structurally sound than just using the stdlib's own decode/encode behavior |
| Reverse geocoding (coordinate → place name) | A self-hosted geocoding dataset/service | `CLGeocoder` (client-side, via Apple's servers) | Apple already operates this service and Ritham's backend never needs to touch a coordinate for the default flow — building/hosting a geocoding dataset is unjustified scope for this phase |
| **Exception — orientation-tag pixel rotation** | Don't reach for a full third-party image-processing library (`disintegration/imaging`, `go-oss/image`) for this one step | Hand-roll the 8-case EXIF-orientation pixel transform (rotate 90/180/270, flip horizontal/vertical, and the 3 combined cases) directly | Both available third-party options are stale (2018/2019, low ongoing adoption — see Package Legitimacy Audit) for a security-relevant code path; the transform itself is simple, well-documented, mechanically testable pixel remapping — one of the rare cases where a small hand-rolled implementation is the *lower*-risk choice than adding a barely-maintained dependency |

**Key insight:** In most domains "don't hand-roll" points toward a library. In this phase's photo
pipeline it sometimes points *away* from one — the safest EXIF-stripping mechanism is the Go
standard library's own metadata-blindness, and the safest orientation-fix is a small, reviewable,
in-house function rather than a dependency whose maintenance status doesn't match the sensitivity
of the code path it would sit on.

## Common Pitfalls

### Pitfall 1: Treating "the app strips EXIF" as already true because CONTEXT.md references a cheer mechanic and a household tier that don't exist yet

**What goes wrong:** CONTEXT.md's canonical refs describe "Ritham's existing fixed, non-ranked
cheer mechanic (used by household/Momentum)" as something to "locate and extend." **It does not
exist.** A grep across `RithamApp` and `RithamCore` for cheer/kudos/reaction/niceWork/keepGoing
returns zero hits — the *product rule* (fixed, non-comparative reactions) is established, the code
is not. Similarly, `MomentumVisibility` has exactly one case; there is no household visibility
mechanism to extend.
**Why it happens:** CONTEXT.md's canonical refs read like a pointer to shipped code because Phase 4
round 1 shipped a dashboard and Phase 3 shipped Momentum, creating an impression of more
cross-feature infrastructure than actually landed.
**How to avoid:** Build the cheer mechanic as new code in this phase, following the described
product rule (fixed set, no counts, no "most-cheered" surface) — do not spend planning time
searching for code to extend.
**Warning signs:** A plan task phrased as "extend the existing cheer component" that can't cite a
specific file.

### Pitfall 2: The EXIF-strip pipeline silently rejecting real-world uploads

**What goes wrong:** Go's `image.Decode` has no HEIC/HEIF decoder registered. iPhones capture HEIC
by default. A server pipeline built assuming "any photo the client sends will decode" will reject
most real uploads with a decode error, and — worse — if that error path isn't handled defensively,
it risks a developer "fixing" it by adding a permissive fallback that writes the undecoded original
bytes through, which would bypass EXIF stripping entirely.
**Why it happens:** The PRD describes the privacy behavior, not the file-format mechanics; this gap
is invisible until a real HEIC file is tested against the pipeline.
**How to avoid:** Client transcodes HEIC→JPEG via `ImageIO`/`UIImage.jpegData` before upload (see
Pattern 2). Server-side, treat any decode failure as a hard reject — never a passthrough.
**Warning signs:** The EXIF-strip pipeline's tests only use JPEG/PNG fixtures and never a real
iPhone-captured HEIC file.

### Pitfall 3: Evaluating Privacy Zones after the coordinate has already been discarded or geocoded

**What goes wrong:** If reverse-geocoding happens before (or instead of) the Privacy Zone check, a
location inside a zone could still resolve to a named place and get shared — the zone protection
silently does nothing. If the raw coordinate is discarded before the zone check runs (e.g., because
a "don't store coordinates" rule was applied too early), the zone check has nothing to evaluate
against and either fails closed (over-suppressing) or fails open (leaking).
**Why it happens:** "Never store precise coordinates" and "check Privacy Zones" read like two
independent rules; they are actually sequentially dependent (Pattern 3).
**How to avoid:** Implement the exact 5-step sequence in Pattern 3 as one function/flow, with the
zone check as an early, blocking step — not two features built by two different plans that happen
to both touch location.
**Warning signs:** A Privacy Zone data model and a reverse-geocoding call implemented in separate
plans/PRs with no explicit ordering test between them.

### Pitfall 4: Widening `WorkoutPlanRequest` (or copying its pattern loosely) instead of adding new, separately-scoped endpoints

**What goes wrong:** `WorkoutPlanRequest`'s three-field shape is deliberately locked — its own
header comment states "No stable per-user or per-device identifier is accepted here, or ever will
be for this endpoint's current scope." Adding a `userId` field to this struct to "wire up" identity
would violate that documented boundary and fail the existing reflection test in `handler_test.go`.
**Why it happens:** Once identity exists, it's tempting to thread it through every existing
endpoint rather than scoping new endpoints per capability.
**How to avoid:** New, separately-authenticated routes (`/v1/friends`, `/v1/groups`, etc.) — the
plan-generation endpoint stays exactly as it is.
**Warning signs:** Any diff touching `RithamService/internal/httpapi/contract.go`'s
`WorkoutPlanRequest` struct.

### Pitfall 5: Certificate export using the local original instead of the server-stripped copy

**What goes wrong:** If a user composites their own photo into a certificate and the client
references the local (metadata-intact) file rather than the server-stripped, group-visible copy,
the exported certificate can leak EXIF/GPS data even though the strip pipeline itself is correct —
the guarantee was bypassed by which copy got used, not by a pipeline bug.
**Why it happens:** The client already has the original file in its private library for its own
convenience; reaching for that reference is the path of least resistance in UI code.
**How to avoid:** Certificate composition code should have no addressable reference to the private
original at all — only ever hold a reference to the stripped asset (see Pattern 4).
**Warning signs:** A certificate-composition view/model that imports or has access to the private
photo library's file paths.

### Membership-scoped feed query (Go) — prevents IDOR on group/event IDs
```go
// FeedForGroup returns the group's feed page ONLY if requestingUserID is a current member --
// never a bare fetch-by-groupID. Opaque UUIDs (github.com/google/uuid) make group/event IDs
// unguessable, but membership-scoping is the actual access-control boundary, not ID opacity alone.
func (s *Store) FeedForGroup(ctx context.Context, requestingUserID, groupID uuid.UUID, cursor string) ([]FeedItem, error) {
    const q = `
        SELECT f.id, f.event_id, f.actor_user_id, f.completed_at, f.own_time_seconds,
               f.photo_asset_id, f.place_name, f.caption, f.posted_at
        FROM feed_items f
        JOIN group_members m ON m.group_id = f.group_id
        WHERE f.group_id = $1
          AND m.user_id = $2      -- membership check is part of the query, not a separate step
          AND f.posted_at < $3
        ORDER BY f.posted_at DESC -- chronological only; never ORDER BY own_time_seconds
        LIMIT 50`
    // ...
}
```

### Swift: transient location capture, on-device Privacy Zone check, then geocode-or-discard
```swift
// Implements Pattern 3's 5-step ordering as one function. `coordinate` never escapes this
// function's scope beyond the geocode call itself, and is never passed to a persistence layer.
func attachLocation(to draft: inout CompletionDraft, zones: [PrivacyZone]) async {
    guard let coordinate = await LocationCapture.transientFix() else { return } // in-memory only

    if let matchedZone = zones.first(where: { $0.contains(coordinate) }) {
        draft.placeName = matchedZone.suppressesEntirely ? nil : matchedZone.generalizedLabel
        return // no geocode call is ever made for a zone-matched location
    }

    guard let placemark = try? await CLGeocoder().reverseGeocodeLocation(
        CLLocation(latitude: coordinate.latitude, longitude: coordinate.longitude)
    ).first else {
        draft.placeName = nil // failure -> no location, never a coordinate fallback
        return
    }

    // Hard allowlist -- never thoroughfare/subThoroughfare (street-level precision).
    draft.placeName = [placemark.areasOfInterest?.first, placemark.subLocality,
                        placemark.locality, placemark.administrativeArea]
        .compactMap { $0 }.first
    // `coordinate` goes out of scope here -- never stored.
}
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|---------------|--------|
| Client-side-only EXIF stripping (trust the app to strip before upload) | Server-side, unconditional stripping regardless of client claims | Industry-wide shift post-2018 Strava heatmap incident, reflected directly in this PRD's own §3 reasoning | Removes an entire bypass class (a different/future client, a replayed request) that client-only stripping can't close |
| Fixed-radius "excluded zone" geofencing (Strava's Map Visibility) | Named-place-only display with no exposed radius/boundary at all | Strava's own documentation still acknowledges the fixed-radius approach is defeatable by correlation across multiple activities | This phase avoids the pattern entirely rather than reimplementing a known-imperfect mitigation |
| Stateless JWT-only session auth | Revocable opaque server-side session tokens (JWT reserved for a possible future stateless layer) | N/A — project-specific choice for this phase, not an industry-wide shift | Supports "revoke a lost/stolen device's access," which a pure stateless JWT can't do without an additional blocklist mechanism |

**Deprecated/outdated:** Nothing in this domain is deprecated by this research; the pitfalls above
are gaps this specific codebase hasn't hit yet, not obsolete industry practice.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|-----------------|---------|--------------------|
| V2 Authentication | Yes — but not classic password auth | Device-keypair-based identity assertion (`CryptoKit`); no passwords exist in this model, so most V2 password-specific controls are N/A, but V2's session-binding intent still applies |
| V3 Session Management | Yes | Revocable, server-side-hashed opaque bearer tokens (not a bare stateless JWT — see Pattern 6); short expiry + explicit revoke-on-device-loss path |
| V4 Access Control | Yes — this is the highest-relevance category for this phase | Membership-scoped queries on every group/event/feed endpoint (Pattern: Membership-scoped feed query); opaque UUIDs to prevent enumeration; never a bare fetch-by-ID |
| V5 Input Validation | Yes | Reuse `RithamService/internal/httpapi/handler.go`'s existing `MaxBytesReader` + `DisallowUnknownFields()` pattern on every new endpoint; explicit length bounds on free-text fields (event name, caption) |
| V6 Cryptography | Yes | Never hand-roll token signing/hashing — use Go stdlib `crypto/rand`/`crypto/sha256` for opaque token generation/hashing, `CryptoKit` client-side for keypair generation; TLS termination required once real (non-loopback) hosting exists (currently absent — flagged in Environment Availability) |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|-------------------------|
| EXIF/GPS metadata leak via photo upload | Information Disclosure | Server-side unconditional strip (Pattern 2), structural negative test, HEIC-transcode-first client requirement |
| Location triangulation via a returned radius/distance figure | Information Disclosure | Never return a numeric radius/distance; coarse named place only; hard field allowlist on `CLPlacemark` |
| IDOR on group/event/feed resource IDs | Elevation of Privilege / Info Disclosure | Opaque UUIDs (`google/uuid`) + membership-scoped queries on every read/write, never fetch-by-bare-ID |
| Invite-link forgery/reuse (permanent/forwardable link) | Spoofing | Single-use or window-expiring invite tokens, server-side consumption tracking, per the PRD's own §1 requirement |
| Token theft/replay | Spoofing | Short-lived, revocable, server-side-hashed opaque tokens; TLS required in production (not yet available — loopback only today) |
| Decompression-bomb / oversized photo upload | Denial of Service | Extend the existing `maxRequestBodyBytes` precedent (`handler.go`) to the new photo-upload endpoint, plus an explicit pixel-dimension cap checked before `image.Decode` fully allocates a buffer |
| Certificate export bypassing the strip guarantee via the local original | Information Disclosure | Certificate composition code holds no reference to the private-library original (Pattern 4 / Pitfall 5) |
