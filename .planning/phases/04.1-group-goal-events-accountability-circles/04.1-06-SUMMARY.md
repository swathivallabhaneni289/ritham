# Phase 04.1 Plan 06: Friend Graph, Invites, and Contact Matching Summary

**Mutual friend graph, crypto/rand single-use expiring invite links, and HMAC-SHA256-salted both-sides-opt-in contact matching, all reachable over ten new RequireSession-gated HTTP routes**

## Performance

- **Duration:** ~70 min
- **Started:** 2026-09-10T09:00:00Z (approx)
- **Completed:** 2026-09-10T09:19:44Z (approx, per final commit)
- **Tasks:** 3 (2 TDD tasks with RED/GREEN commits, 1 auto task)
- **Files modified:** 15

## Accomplishments
- `internal/friends` package built from nothing: `SendRequest`/`Accept`/`Decline`/`Incoming`/`List`/`Unfriend`/`AreFriends` implement the mutual friend graph over a schema (migration `0003_friends`) whose `friendships` table structurally cannot represent a one-directional follow (`PRIMARY KEY (user_a_id, user_b_id)` + `CHECK (user_a_id < user_b_id)`)
- `Accept` runs the request state-transition and the friendship insert in one transaction, normalizing the pair via `orderPair` (byte comparison of the 16 canonical UUID bytes, matching PostgreSQL's own `uuid_cmp`); handles the edge case where both directions of a pending request pair get accepted separately via `ON CONFLICT DO NOTHING` + a fallback read, rather than 500ing on the primary key
- `CreateInvite`/`RedeemInvite` (invites.go): `crypto/rand`-generated tokens, SHA-256 digest-only storage, and a single conditional `UPDATE ... WHERE consumed_at IS NULL AND expires_at > now()` that is simultaneously the single-use enforcement, the window-expiry enforcement, and the concurrency-safety mechanism -- no separate pre-check exists for a racing second redeemer to slip past
- `SetContactMatchOptIn`/`MatchContacts` (contactmatch.go): every submitted digest is HMAC-SHA256-salted with a fixed, server-side application salt (`RITHAM_CONTACT_MATCH_SALT`, read once at startup) before storage or comparison; `MatchContacts` returns the opted-out sentinel before touching the digest table at all when the caller isn't opted in, and the match query's own JOIN against the candidate's opt-in row means a one-sided opt-in can never surface a match in either direction
- Ten HTTP routes wired on `NewMux` behind `RequireSession`, with wire types declared in `friends_handler.go` (not the locked `contract.go`) and handlers depending on a narrow `friendsService` interface so `friends_handler_test.go` runs every case with a stub and no database
- Unknown, consumed, and expired invites all collapse to one byte-identical 404 response (asserted by a dedicated test) so a caller cannot probe which invite tokens have ever existed
- Manually smoke-tested the actual running binary: `GET /v1/friends` with no bearer token returns 401 end-to-end through the real HTTP server

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `friends.New` needed a third `contactMatchSalt` parameter not in the plan's artifact signature**
- **Found during:** Task 2 (pre-implementation design, confirmed by advisor review)
- **Issue:** The plan's `<artifacts_produced>` lists `friends.New(st *store.Store, now func() time.Time) *Service`, but Task 2's action text requires contact digests to be "salted with a fixed server-side application salt," and per-call `os.Getenv` reads would make the salt non-hermetic in tests and allow a mid-run salt change to silently and partially break matching.
- **Fix:** Added `contactMatchSalt []byte` as a third constructor parameter, read once by `main.go` at startup via `ContactMatchSaltFromEnv`.
- **Files modified:** `RithamService/internal/friends/friends.go`, `friends_test.go`, `contactmatch.go`, `cmd/ritham-service/main.go`
- **Verification:** All `friends`-package tests pass with the harness's fixed test salt; `main.go` builds and the running binary serves friends routes correctly (manual curl smoke test).
- **Committed in:** `621971e` (New's signature), `c239470` (contactmatch.go's use of it), `91de1a0` (main.go wiring)

**2. [Rule 3 - Blocking] `contactmatch.go` needed an `ErrTooManyContactDigests` export not in the plan's export list**
- **Found during:** Task 2
- **Issue:** The plan's `must_haves.artifacts` for `contactmatch.go` lists only `ErrContactMatchOptedOut` as an export, but Task 2's own behavior list requires rejecting over-cap submissions, and Task 3's action text explicitly requires `statusForFriendsError` to map "over-cap to 400" -- both structurally require a sentinel to exist.
- **Fix:** Added and exported `ErrTooManyContactDigests`, enforced identically in both `SetContactMatchOptIn` and `MatchContacts`.
- **Files modified:** `RithamService/internal/friends/contactmatch.go`, `contactmatch_test.go`, `internal/httpapi/friends_handler.go`
- **Verification:** `TestSetContactMatchOptIn_OverCapDigestsRejected`, `TestMatchContacts_OverCapDigestsRejected` pass.
- **Committed in:** `c239470`, `91de1a0`

**3. [Rule 1 - Bug, caught pre-implementation] `Accept`'s friendship INSERT would 500 on a legitimate reverse-direction accept**
- **Found during:** Task 1 (pre-implementation design, confirmed by advisor review)
- **Issue:** The plan explicitly allows both A->B and B->A to be pending simultaneously (the unique index scopes to the ordered pair). If both get accepted -- B accepts A->B first (creating the friendship row), then A accepts B->A -- a bare `INSERT INTO friendships` on the second accept would violate the `PRIMARY KEY (user_a_id, user_b_id)` constraint and surface as an uncaught 500.
- **Fix:** `INSERT ... ON CONFLICT (user_a_id, user_b_id) DO NOTHING RETURNING established_at`, with a fallback `SELECT` when the conflict branch returns no row.
- **Files modified:** `RithamService/internal/friends/friends.go`, `friends_test.go`
- **Verification:** `TestFriendGraph_ReverseDirectionRequestAlsoAcceptedResolvesWithoutError` passes.
- **Committed in:** `87dd7cd`

**4. [Rule 2 - Missing Critical] `statusForFriendsError` needed explicit mappings for `ErrRequestExists`/`ErrNotFriends`/`ErrInviteSelfRedeem`**
- **Found during:** Task 3
- **Issue:** The plan's action text names explicit HTTP mappings for self-request, already-friends, over-cap, unknown/consumed/expired invites, not-found request, and opted-out -- but omits these three sentinels. Falling through to the 500 default for a legitimate client-side condition (a duplicate pending request, unfriending a non-friend, or an issuer redeeming their own invite) would be a correctness bug, not a permissible gap.
- **Fix:** Mapped `ErrRequestExists`/`ErrNotFriends` to 409 and `ErrInviteSelfRedeem` to 400, each with its own descriptive message.
- **Files modified:** `RithamService/internal/httpapi/friends_handler.go`
- **Verification:** Code review against the full sentinel list exported by `internal/friends`; no sentinel falls through to the `default: 500` branch.
- **Committed in:** `91de1a0`

**5. [Rule 3 - Blocking] Dedicated `maxContactMatchBodyBytes` needed for the two contact-match routes**
- **Found during:** Task 3 (pre-implementation design, confirmed by advisor review)
- **Issue:** The pre-existing `maxRequestBodyBytes` (64 KiB) is sized for a three-field workout-plan body. A legitimate submission at `maxContactDigestsPerRequest` (2000 digests) marshals to roughly 94 KB as base64-encoded `[][]byte`, which would be rejected by `MaxBytesReader` with a generic 400 before `SetContactMatchOptIn`/`MatchContacts`' own over-cap sentinel could ever fire.
- **Fix:** Declared `maxContactMatchBodyBytes` (128 KiB) and applied it only to `PUT /v1/friends/contact-match` and `POST /v1/friends/contact-match/query`, mirroring `photo_handler.go`'s `maxPhotoUploadBytes` precedent.
- **Files modified:** `RithamService/internal/httpapi/friends_handler.go`
- **Verification:** Manual arithmetic check against the digest cap; no dedicated over-cap-at-the-wire test was added (out of this plan's stated acceptance criteria), but the bound is sized with documented headroom.
- **Committed in:** `91de1a0`

**6. [Rule 3 - Blocking] `NewMux`/`main.go` fan-out for `friendssvc`, outside Task 3's stated file list**
- **Found during:** Task 3
- **Issue:** Wiring friends_handler.go's ten routes requires `NewMux` to accept a `*friends.Service` parameter, which in turn requires `main.go` to construct one -- neither file is in Task 3's own `<files>` list, but both are structurally unavoidable, matching 04.1-03's documented precedent for the identical situation with `idsvc`.
- **Fix:** Added `friendssvc *friends.Service` as `NewMux`'s fourth parameter and `buildFriendsService` to `main.go`; updated all ~10 `handler_test.go` call sites for the new arity and added a `TestNewMux_FriendsRoutesRegisteredOnlyWhenServiceProvided` test mirroring the identity/photo precedent.
- **Files modified:** `RithamService/internal/httpapi/handler.go`, `handler_test.go`, `RithamService/cmd/ritham-service/main.go`
- **Verification:** `go build ./...`, `go vet ./...`, full `go test ./...` all pass; `TestWorkoutPlanRequest_StillHasExactlyOriginalThreeFieldsAfterIdentityRoutesAdded` still passes unchanged.
- **Committed in:** `91de1a0`

**7. [Rule 2 - Missing Critical] Documented `RITHAM_CONTACT_MATCH_SALT` and the ten new routes in README.md**
