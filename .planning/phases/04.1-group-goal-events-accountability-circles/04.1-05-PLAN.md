<objective>
Give the client its identity half: a shared social API client, Keychain-backed sessions, the
Sign in with Apple entry screen, and the dashboard entry point that leads to it.

Purpose: ACCOUNT-01 requires an optional, opt-in account created the first time a user touches a
social feature — never mandatory, never required for core tracking, matching CROSSGEN-03's
"nothing shared or synced by default" and the App Store's no-account-required guideline. This plan
also lands the shared networking foundation (base URL resolution, bearer injection, typed errors)
that the friends, groups, events, feed, and certificate clients in later plans all build on, so
none of them invents its own.

This is the first client plan in the phase, so it also opens the `Social/` feature directory and
the `SocialStepRegistration` aggregate registrar. That registrar follows the single-call-site
pattern `StepBootstrap.swift`'s own header comment established and `Phase2StepRegistration`
repeated: `StepBootstrap` gains exactly one new line, and every later social plan edits only its
own feature registrar.

Output: the `Social/Identity/` directory, the phase's first entitlements file, one new step case,
and a social section on the dashboard.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app → Apple authorization services | The identity assertion originates outside the app |
| app → Ritham backend | Every social request carries a bearer token over the network |
| app → device Keychain | The session token at rest on the device |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04.1-23 | Spoofing | identity-token replay against the sign-in endpoint | high | mitigate | The model generates a random nonce, sends its digest to Apple and its raw value to the server, and the server's nonce check from plan 04.1-03 rejects a mismatch. |
| T-04.1-24 | Information Disclosure | session token readable from a device backup or synced to another device | high | mitigate | Keychain item uses the after-first-unlock, this-device-only accessibility class, so it neither syncs nor restores; continuity comes from signing in again with the same Apple ID. |
| T-04.1-25 | Spoofing | bearer token sent over an untrusted network | high | mitigate | Transport security is required in production and does not exist yet — the backend is still loopback-bound and the release base URL is a documented placeholder. Recorded here and in `RithamService/README.md` as an unresolved deployment prerequisite gating any real two-device use. |
| T-04.1-26 | Information Disclosure | a failed request rendering as a benign empty state | medium | mitigate | `SocialAPIError` distinguishes transport, unauthenticated, status, and decoding failures, and the identity model's state machine has an explicit failed case; tests assert a transport failure never yields a successful empty result. |
| T-04.1-27 | Elevation of Privilege | a stale client session surviving a server-side revocation | medium | mitigate | `refresh()` calls the identity endpoint on appear and drops to signed out on an unauthenticated response. |
| T-04.1-28 | Information Disclosure | account creation becoming a precondition for core tracking | high | mitigate | The sign-in step is reachable only from the social dashboard section, is never in the router's advance path, and Task 4 step 7 verifies onboarding and tracking still complete with no account. Implements ACCOUNT-01 and CROSSGEN-03. |
</threat_model>
