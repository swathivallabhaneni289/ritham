# Phase 04.1: Code Review Report

**Reviewed:** 2026-09-11T07:51:51Z
**Depth:** standard
**Files Reviewed:** 129 (source files; test files were read for reliability concerns only, per review policy)
**Status:** issues_found

## Summary

This phase stands up the project's first multi-user backend (Go, Postgres, S3-compatible object
storage) and a large new iOS social feature surface (friends, groups, goal-events, photo/location
sharing, feed, digital certificates). The implementation is unusually disciplined: the EXIF-strip
pipeline (`RithamService/internal/photo`) is structurally unbypassable (an unexported-field
`StrippedImage` type is the only thing `PutShared` accepts, and it can only be produced by
`StripAndReencode`); session/identity handling uses constant-time-safe, digest-only storage with a
single generic 401 for every failure mode; every group/event/feed read in `internal/groups`,
`internal/events`, and `internal/feed` is scoped through a membership predicate baked into the SQL
itself (never a preceding, skippable check); and the Privacy Zone evaluation order
(`LocationAttachment.resolveSharedPlaceName`) checks zones before ever invoking the geocoder,
exactly as required. The client-side certificate composer's `StrippedPhotoAsset` type has a
private initializer reachable only from a real server upload response, which is a genuinely
strong structural guarantee against a local/original photo ever reaching an exported certificate.

Against that backdrop, one real authorization gap survived: the export-consent status endpoint
(`GET /v1/photos/{id}/export-consent`) performs no ownership, subject, or group-membership check
at all, breaking the "every read is membership/ownership-scoped" invariant this phase otherwise
enforces everywhere else. Two further issues — a misleading error message in the certificate
export flow, and a continuation-handling bug in the location-fix provider — are documented below.

## Critical Issues

### CR-01: Export-consent status endpoint has no authorization check, letting any authenticated user (including a departed group member) enumerate who is still withholding consent on a photo

**File:** `RithamService/internal/feed/exportconsent.go:90-119` (`ExportAllowed`), wired via `RithamService/internal/httpapi/feed_handler.go:185-200` (`handleGetExportConsent`), route `GET /v1/photos/{id}/export-consent` (`RithamService/internal/httpapi/handler.go:138`)

**Issue:** Every other read in this phase is scoped through membership or ownership baked into the
query itself (`groups.RequireMember`, `events.requireEventMembership`,
`feed.requireVisibleCompletion`, `photo.Service.Asset`'s owner-scoped `SELECT`). `ExportAllowed` is
the one exception:

```go
func (s *Service) ExportAllowed(ctx context.Context, exporterUserID, photoAssetID uuid.UUID) (ExportGate, error) {
	_ = exporterUserID // not yet used to restrict who may check -- any authenticated caller may
	// ask a photo's export status; the handler layer still requires a valid session for every
	// route (T-04.1-13). Kept as a parameter to match this plan's own artifact signature and to
	// leave room for a future caller-scoped restriction without an API break.

	const query = `
		SELECT subject_user_id FROM photo_export_consents
		WHERE photo_asset_id = $1 AND granted_at IS NULL
	`
	...
}
```

The comment frames this as "not yet restricted," but the gap is concretely reachable, not
theoretical:

1. `photoAssetID` is not a secret. `GET /v1/events/{id}/completions` (`events_handler.go`'s
   `completionResponse`) includes `photoAssetId` for every completion in a group's event —
   `events.Service.Completions` is gated only by "is a member of this group," per
   `events_handler.go:203-221`. Any current member can harvest every other member's photo asset
   IDs from that route and then query `GET /v1/photos/{id}/export-consent` for each one.
2. **Revocation does not apply here.** `groups.Service.Leave` deletes the caller's
   `group_members` row, and `events.requireEventMembership`/`feed.requireVisibleCompletion`
   correctly stop returning data to a departed member the instant that row is gone. `ExportAllowed`
   has no membership check of any kind, so a member who has left the group (or was removed) keeps
   an open channel to query consent state for photos belonging to a group they can no longer see.
3. **Subjects need not be group members at all.** `RequestExportConsent` accepts an arbitrary list
   of `subjectUserIDs` from the photo's owner with no group-membership constraint
   (`exportconsent.go:43-63`), so `awaitingSubjectIds` can name identities that a group member
   would otherwise have no way to learn.

The net effect: any authenticated Ritham user who can obtain a `photoAssetId` (trivially available
to any current or former group member via the completions route) can learn exactly which specific
user IDs have not yet granted export consent for that photo — an information disclosure the rest
of this phase's design explicitly treats as sensitive (this is precisely the "presence in a group
feed vs. presence on the public internet" boundary the file's own header comment describes).

**Fix:** Scope the query the same way every other read in this phase is scoped — require the
caller to be either the photo's owner or one of the recorded subjects (a bystander with no stake in
the photo has no legitimate reason to see its consent status):

```go
func (s *Service) ExportAllowed(ctx context.Context, exporterUserID, photoAssetID uuid.UUID) (ExportGate, error) {
	isOwner, err := s.isPhotoOwner(ctx, exporterUserID, photoAssetID)
	if err != nil {
		return ExportGate{}, err
	}
	if !isOwner {
		isSubject, err := s.isRecordedSubject(ctx, exporterUserID, photoAssetID)
		if err != nil {
			return ExportGate{}, err
		}
		if !isSubject {
			return ExportGate{}, ErrNotPhotoOwner // or a dedicated ErrNotAuthorizedForPhoto
		}
	}
	// ... existing query unchanged
}

func (s *Service) isRecordedSubject(ctx context.Context, userID, photoAssetID uuid.UUID) (bool, error) {
	var exists bool
	err := s.store.Pool().QueryRow(ctx,
		`SELECT EXISTS(SELECT 1 FROM photo_export_consents WHERE photo_asset_id = $1 AND subject_user_id = $2)`,
		photoAssetID, userID,
	).Scan(&exists)
	return exists, err
}
```

Update `handleGetExportConsent`/`statusForFeedError` to map the new denial to 403 (matching
`ErrNotPhotoOwner`'s existing 403 mapping) or 404 (to avoid confirming the asset exists — pick
whichever this project's `T-04.1-45`-style non-confirmation convention prefers for this route).

## Warnings

### WR-01: Certificate export flow shows a false "everyone must approve" message on a network failure, with no recovery path

**File:** `RithamApp/Ritham/Social/Certificate/CertificateExportView.swift:106-112` (`gateSection`, `.failed` case)

**Issue:** `checkExportGate(for:)` sets `gateState = .failed` on any thrown error from
`client.exportConsentStatus(...)` — which includes an ordinary transport failure
(`SocialAPIError.transport`), not just a genuine "not everyone has consented" outcome. The
`.failed` branch renders the identical copy used for `.blocked`:

```swift
case .failed:
    Text(SocialCopy.Certificate.multiPersonExportBlock)
        .font(RithamType.label)
        .foregroundStyle(RithamColor.hot)
        .fixedSize(horizontal: false, vertical: true)
```

`multiPersonExportBlock` reads "Everyone visible in this photo needs to approve sharing it outside
Ritham before you can export it" — a specific claim about other people's consent state that was
never actually established; the real cause was the network call failing. This is misleading to the
user, and — unlike `.blocked`, which offers `SocialCopy.Certificate.useDefaultTemplateCTA` as an
escape hatch — the `.failed` branch offers no button of any kind. Since `canExport` is (correctly)
`false` for `.failed`, and this same `.task(id: useDefaultTemplate)` is the only thing that can
re-run the check, a transient network failure leaves the user stuck: there is no retry action and
no visible way to reach the default-template fallback without already knowing to dismiss and
reopen the whole export sheet.

**Fix:** Give `.failed` its own message and its own recovery action, distinct from `.blocked`:

```swift
case .failed:
    Text("Couldn't check whether this photo is ready to export. Check your connection and try again.")
        .font(RithamType.label)
        .foregroundStyle(RithamColor.hot)
        .fixedSize(horizontal: false, vertical: true)

    SecondaryCTAButton(title: "Try again") {
        Task { await model.checkExportGate(for: useDefaultTemplate ? nil : content.photo) }
    }

    SecondaryCTAButton(title: SocialCopy.Certificate.useDefaultTemplateCTA) {
        useDefaultTemplate = true
    }
```

### WR-02: `SystemLocationFixProvider.currentFix()` drops and misattributes continuations when two calls overlap

**File:** `RithamApp/Ritham/Social/Completion/LocationFixProviding.swift:49-77`

**Issue:** `currentFix()` unconditionally overwrites `pendingContinuation` and `activeManager` with
no check for an already-in-flight request:

```swift
func currentFix() async -> CLLocationCoordinate2D? {
    await withCheckedContinuation { continuation in
        lock.lock()
        pendingContinuation = continuation   // overwrites any prior, still-unresumed continuation
        let manager = makeLocationManager()
        manager.delegate = self
        activeManager = manager              // drops the reference to any prior manager
        lock.unlock()
        manager.requestWhenInUseAuthorization()
        manager.requestLocation()
    }
}
```

If `currentFix()` is called again before a prior call's `CLLocationManager` delegate callback has
fired, the first call's `CheckedContinuation` is orphaned (never resumed — a leaked
`CheckedContinuation` traps at runtime in debug builds with "SWIFT TASK CONTINUATION MISUSE:
currentFix() leaked its continuation!", and simply hangs the awaiting `Task` forever in release).
Worse, if the *first* manager's delegate callback fires after the second call has already
overwritten `pendingContinuation`, `resume(with:)` resumes the *second* call's continuation with
the *first* call's result — silently misattributing one location fix (or failure) to an unrelated
caller.

This is reachable, not merely theoretical: `CompletionLoggingModel.setLocationSharingEnabled` calls
`locationFixProvider.currentFix()` from a fresh `Task` spawned by
`CompletionLoggingView`'s `.onChange(of: locationSelection)` (`CompletionLoggingView.swift:92-94`).
A user toggling the location-sharing chip off and back on again while the first fix is still
resolving (a normal, easy interaction — GPS acquisition can take a few seconds) fires a second
`currentFix()` call on the same shared `SystemLocationFixProvider` instance before the first
resolves.

**Fix:** Either serialize calls (reject/queue a second call while one is in flight) or resume the
prior continuation with `nil` before starting a new request:

```swift
func currentFix() async -> CLLocationCoordinate2D? {
    await withCheckedContinuation { continuation in
        lock.lock()
        let previousContinuation = pendingContinuation
        let previousManager = activeManager
        pendingContinuation = continuation
        let manager = makeLocationManager()
        manager.delegate = self
        activeManager = manager
        lock.unlock()

        previousManager?.delegate = nil
        previousContinuation?.resume(returning: nil)

        manager.requestWhenInUseAuthorization()
        manager.requestLocation()
    }
}
```
