# Phase 04.1: Group Goal-Events & Accountability Circles - Context

**Gathered:** 2026-09-09
**Status:** Ready for planning
**Source:** PRD Express Path (docs/group-events.md)

<domain>
## Phase Boundary

Users can build a friend-level accountability circle beyond household (mutual/request-based
friending, small closed invite-only groups), organize a Goal-Event (a shared, non-timed
commitment — not a race), log completion independently with an optional self-reported time,
share an EXIF-stripped photo and an optional coarse named location, see a group-only
chronological feed, and generate a per-person digital finisher certificate on completion.

Every mechanism in this phase is structurally non-comparative and non-ranking: no leaderboard,
no pooled total, no "first to complete," no denominator paired with a completion count, no
precise location anywhere shared, no cross-user aggregate location view ever. This is the same
standing product rule ("no comparison, ever") applied to a new surface, not a new value.

This phase was previously v2-scoped (`docs/roadmap.md` §"v2", `PROJECT.md` Out of Scope) purely
to keep Phase 5's pre-launch GDPR/CCPA privacy review narrow. The user explicitly chose to pull
it into v1 on 2026-09-09, accepting the wider review surface (see `PROJECT.md` Key Decisions).
Phase 5 now depends on this phase (`ROADMAP.md`), so its review must cover whatever this phase
actually collects/stores.

**Not in this phase's boundary** (see Deferred below and Claude's Discretion): HOUSEHOLD-01
(household grouping itself) is a separate, still-open Phase 4 requirement — this phase must not
silently assume it exists.

</domain>

<decisions>
## Implementation Decisions

Every decision below is locked from `docs/group-events.md` (the full PRD) unless flagged
otherwise. Section references (§1-§5) point back to that document.

### Friends & Groups (HOUSEHOLD-02, GROUPEVENTS-01) — §1

- Friending is mutual/request-based only — never a one-directional follow. No public profile
  search, no contact-scan without explicit per-side opt-in.
- Exactly three closed-loop connection paths, no others:
  1. Contact matching — off by default per side; a match surfaces only when both sides opted in.
  2. Invite link/QR — generated per-invite, expires after a set window or first use. Never a
     permanent/forwardable link.
  3. In-person/direct share (text, AirDrop-style) — no in-app directory involved.
- Groups are small, closed, invite-only, sent only to existing friends. No "public group anyone
  can join" tier exists at all. A group is invisible to search, not listed on any profile,
  generates no public/aggregate signal.
- Any member can leave anytime, no ownership-transfer gate. If the organizer (a convenience role,
  not a title with public weight) leaves, the group simply continues — no auto-promotion, no
  "ownership vacuum" state.
- Removing a member: available to any member, or restricted to the organizer, per group
  preference. No admin-approval queue or join-request inbox (nobody outside the mutual friend
  graph can request to join).
- Group size is intentionally small — bias toward "people doing this together," not toward a
  scaling club. (PRD doesn't give a hard numeric cap — flagged in Claude's Discretion.)
- Visibility ladder is capped at exactly three rungs: **Only Me → Household → this specific
  group.** No "friends of friends" rung, no "Public/Everyone" rung, anywhere in this feature —
  not for a friend's profile, a group, a completion post, or a certificate. Anything shared
  beyond the group boundary is a deliberate, individual **export** (§5), never a setting that
  widens passive visibility.

### Goal-Events (GROUPEVENTS-02) — §2

- A Goal-Event is a shared, **non-timed** commitment, not a race/challenge. Organizer sets:
  activity type, an optional target (distance or duration), and a target date or window (single
  day or open window). No synchronized start, no clock.
- RSVP is individual ("I'm in"), shown pre-event only as a headcount ("6 friends are in") — a
  low-stakes pre-commitment signal on a screen **separate from** the post-event completion feed.
  This separation is deliberate (prevents the app from ever showing "went in" vs. "came out").
- Logging completion is binary: **done**. Own distance/duration/route may optionally be recorded
  to the user's **personal, private log only** — never travels to the group feed, certificate, or
  export, by construction (not a filter that could fail).
- Adding one's own completion **time** is optional, off by default, asked (not assumed) at the
  moment of logging, skippable with zero friction. When shown, it is never ranked/sorted/scored
  against anyone else's.
- No ranking mechanism of any kind: no pooled total, no contribution ranking, no leaderboard
  sort, no score, no winner, no comparison of who did/didn't include a time.
- Feed order is chronological by post time — never sorted fastest-to-slowest. No ordinal
  position, medal, or "1st" marker on any card, ever.
- Non-completion is a non-event: completion feed shows **positive completions only** — no
  greyed-out avatar, no "hasn't finished" state, no red X, no countdown-pressure banner, and no
  denominator paired with the completion view (RSVP headcount never re-appears next to completion
  count). Event closes silently at the target date/window — no expiry notice, no nudge, no
  "missed it" surface. Already-logged completions stand permanently in group history.
- Literal copy strings are locked verbatim from §2's table (e.g. "Start a Group Goal" — never
  "Challenge"; "You did it! 🎉 Logged for the Saturday 5K Walk."; the skip action for adding a
  time must be exactly as prominent as the add-time action) — the planner/executor should carry
  these into a copy catalog rather than re-authoring equivalents.

### Photo + Location Privacy (GROUPEVENTS-03) — §3

- **Standing structural exclusion, permanent regardless of milestone**: Ritham will never build a
  cross-user aggregate location visualization (heatmap, "most active area," any feature plotting
  multiple users' activity onto one map). This is a locked product-category exclusion, not a
  phase-scoped decision — already recorded in `PROJECT.md` Key Decisions.
- EXIF GPS and all EXIF metadata is stripped **server-side, unconditionally**, before any image
  is written to group-visible or exportable storage — regardless of what the client claims to
  have stripped. Never rely on client-side stripping alone.
  - **Prohibition, not just a rule** — a required negative test: no code path may write an image
    to shared/exportable storage without having gone through server-side EXIF stripping first.
- Original file (metadata intact) is retained only in the user's own private library — never in
  the group-served or exported copy.
  - Existing precedent: recorded in `PROJECT.md` Key Decisions already ("Server-side EXIF
    stripping is unconditional...").
- Location sharing is a separate, explicit opt-in from photo sharing — attaching a photo never
  implies attaching a place; the two are always two separate switches, never bundled as one.
- Precise coordinates for a completion log are **not captured/stored at all** by default — not
  captured-then-hidden. The only exception: a user separately opting into a *personal* route view
  (their own private map, same tier as a personal photo library) — even then that data never
  reaches the group feed, certificate, any aggregate, or any export; there is no shared code path
  that could leak it, because it was never written to shared storage.
- If a user opts into sharing location, the default display is a **reverse-geocoded coarse named
  place** ("Griffith Park," "near Austin, TX") — never coordinates, a pin, an address, or any
  numeric radius/distance figure (a determined viewer could triangulate a derived number back to
  a point, per the Tinder 2016 precedent cited in the PRD).
- Privacy Zones: a user can set one or more sensitive locations (home, workplace) once, in
  settings. Any activity/photo whose location falls inside a zone is **automatically generalized
  or fully suppressed across every shared surface** (feed, certificate, export) without the user
  re-toggling anything per-post.
- An event's *coordination* location (e.g., the exact trailhead address an organizer shares with
  the group to plan a meetup) must never leak into anything the group later shares outside itself
  — coordination detail and shareable/export detail are different data with different audiences.

### Shared Feed (GROUPEVENTS-04) — §4

- Visibility: the group, and only the group, by default and permanently. Not public, not
  discoverable, not indexed, no generic shareable link. No tier above "this group" exists for
  this surface.
- Leaving/removal ends future feed access; past completion cards the person posted remain visible
  to the group (same as leaving a shared chat). A leaving user may also choose to remove their own
  past posts as part of the leave flow — offer this explicitly at the leave step, don't leave it
  as an unstated default either way.
- Per-completion card shows: name/avatar, Goal-Event name + activity type, completion date,
  optional photo (EXIF-stripped), optional generalized location (named place only), optional
  short personal caption, fixed non-comparative cheers from the group (same cheer set used
  elsewhere in Ritham — no kudos count, no "most-cheered" surface).
- Never shows: pace, time-based rank, "first to complete," a denominator paired against
  completions, or anyone's precise location.
- Group goal-event history (past events + who completed each) lives in this same closed space —
  a shared archive, never an individual public trophy wall.

### Identity & Account Recovery (ACCOUNT-01) — supersedes research Pattern 6

*Locked 2026-09-09, after 04.1-RESEARCH.md.* The researcher's device-keypair-only identity model
(no account, no recovery — losing a phone permanently loses the friend graph, groups, and
certificate archive) was explicitly flagged as needing user confirmation before being locked,
given the data-loss stakes. Told this directly, the user chose to **build real account recovery
into this phase now**, not defer it.

- This phase absorbs Phase 999.2's backlog scope ("Optional cross-device account/sync (email
  login)," `ROADMAP.md`) rather than shipping device-bound identity now and account recovery
  later — one identity system, not two to reconcile.
- **Sign in with Apple only** (`AuthenticationServices`/`ASAuthorizationAppleIDProvider`), not
  email+password. This is a scope-minimizing choice, not a half-measure: Sign in with Apple
  eliminates the exact heavier-scope items the research flagged for a full email/password system
  (password reset, email verification/deliverability, credential-compromise handling) while still
  giving every user real account recovery via their existing Apple ID — no new credential surface
  Ritham has to build, store, or secure. Server-side verifies Apple's identity token (JWT) against
  Apple's published public keys; Ritham's backend stores only the resulting stable Apple user
  identifier plus its own opaque user ID, session token, and the same revocable-session model
  the research already recommended in Pattern 6 (still correct — only the identity-issuance step
  changes, not the session/token architecture around it).
- Matches App Store Guideline 4.8 practice (any third-party-login-equivalent surface should offer
  Sign in with Apple) and Phase 999.2's own noted preference — the phase's original open question
  ("email+password, Sign in with Apple, or both?") is resolved as Sign in with Apple, alone.
- Account creation stays **opt-in, on first social-feature use** — not mandatory at onboarding,
  not required for core tracking. Matches CROSSGEN-03 ("nothing shared/synced by default") and the
  App Store's no-account-required guideline (5.1.1(v)) for features that don't need one.
- **Cross-device continuity**: signing in with the same Apple ID on a new device restores the
  user's friend graph, group memberships, and certificate archive — no separate "recovery flow"
  needs to be built; this falls out of using Apple's account system as the identity anchor rather
  than a device-local keypair.
- Server-side session/token model, membership-scoped access control, and every other
  Architecture Pattern in 04.1-RESEARCH.md (EXIF pipeline, Privacy Zone ordering, visibility
  ladder, feed/certificate patterns) are unchanged by this decision — only Pattern 6's specific
  "device-keypair + opaque ID, no recovery" claim is superseded.

### Digital Certificate (GROUPEVENTS-05) — §5

- On it: Ritham branding, Goal-Event name + activity type, participant's own name, completion
  date, own completion time only if they opted in when logging (same opt-in as the feed card).
- Never on it, regardless of the time opt-in: pace, measured distance, place/rank within the
  group, exact GPS/address, any other member's name/photo/status/time, any "X of Y completed"
  figure.
- Auto-generates per person the moment they log completion (template merge: brand frame + event
  name + participant name + date). Default template is a **branded graphic/badge**, not the
  user's own photo — a deliberate default (see export rules below), not just aesthetic.
- Posts to the group feed alongside/as the completion card automatically — no separate send step.
- **External export** (outside Ritham) contains only the exporting user's own data: their name,
  event name, completion date, Ritham branding, plus a generalized location only if that user
  specifically opted into showing it on *their own* export. Must never contain: a member
  count/roster/"X of Y" figure, the group's name if it is person-identifying, or any other
  member's name/photo/status.
  - If a group photo (not the default badge template) contains other visible members, external
    export of that image requires either every visible person's separate "okay to share this
    outside Ritham" grant for that specific photo, or the exporting user crops/selects a solo
    shot. Group-feed presence and public-internet presence are different consent decisions —
    never assume the second from the first.
  - Event names are free text and can themselves be a location/identity disclosure. Two-moment
    check required: (1) at creation, nudge the organizer that the name will be visible on any
    exported certificate; (2) at export time, show an editable display-name field so the
    exporting user (often not the organizer) can rename their own certificate copy without
    altering what the group sees or needing the organizer's involvement.
  - The export path goes through the same server-side EXIF-stripping guarantee as any other
    shared image — no exemption for the export code path.
- Past certificates accumulate in the user's own private record (visible to them and, at most,
  their household per the existing spectrum) — a personal keepsake trail, never ranked/ordered
  against anyone else's.

### Claude's Discretion

sections above): the Household-rung ladder shape, the cheer-mechanic build-vs-extend question,
the dependency qualification, and the identity/account model are no longer open.

Still open — implementation choices the planner should pick and document, not re-litigate with

- **Group size cap.** PRD says "intentionally small," no number given — pick and document a
  concrete default.

  store (`minio-go`) against an as-yet-unchosen hosting provider — planner should treat "real
  hosting provider" as a flagged deployment prerequisite (RESEARCH.md Open Question 3), not a
  planning blocker; local dev can proceed against a MinIO container.
- **Reverse-geocoding provider.** `04.1-RESEARCH.md` recommends client-side `CLGeocoder` (never
  server-side) — locked by the research's Pattern 3 privacy-ordering argument, not left open.
- **Push/real-time delivery.** `04.1-RESEARCH.md` recommends REST polling for this phase (no
  APNs entitlement exists yet) — locked, not left open.
