## Summary

This phase is almost entirely a content-transcription and thin-UI exercise, not a new technical
domain. Every pattern it needs — a Settings-reached sheet screen, a single `HealthDataStore`
persistence facade extension, a `RithamCore` `Copy`/`Guidance` namespace pair for locked strings —
already exists in this codebase with multiple prior implementations to mirror exactly (`DietPlanView`
plus `DietPlanQuickEditView`/`SettingsView` for the entry point; `NutritionGuidanceCatalog`/
`WorkoutGuidanceCatalog` for the citation discipline; `PrivacyZoneRecord`'s CRUD-by-identity shape
for the multi-entry child record). No new third-party package, framework, or network dependency is
needed anywhere in this phase.

The one genuinely load-bearing research deliverable — required by CONTEXT.md D-01/D-02, not
optional background reading — was producing `docs/kid-content.md`: identifying real, current,
citable public health guidance for preteens and transcribing it verbatim, the same discipline
`NutritionGuidanceCatalog.swift`'s own header comment describes. That document now exists at
`docs/kid-content.md` (repo root, sibling to `docs/dietary-pattern.md`) and contains nineteen food
ideas (from two official USDA "10 Tips Nutrition Education Series" tipsheets: DG TipSheet No. 11,
"Kid-Friendly Veggies and Fruits," June 2011; and DG TipSheet No. 24, "Snack Tips for Parents,"
March 2013 — both via ChooseMyPlate.gov) and CDC/HHS Physical Activity Guidelines for Americans
movement guidance for ages 6-17 (60+ minutes daily, aerobic/muscle-strengthening/bone-strengthening
components), every item cited by name, publisher, and publication date, with one source tip
deliberately excluded for conflicting with D-03 (documented, not silently dropped). The planner
should cite `docs/kid-content.md` directly in PLAN.md tasks rather than re-deriving or re-sourcing
any content — that research work is already complete.

The one place this phase carries genuine, non-boilerplate design judgment is the child-entry
record shape (KIDCONTENT-02): because a parent can record *multiple* children and *edit* each one
independently, the correct persistence precedent in this codebase is `PrivacyZoneRecord`'s
per-entry-UUID CRUD (save/rename/delete by identifier), not `FoodAllergenRecord`'s
delete-then-reinsert-the-whole-set pattern — the latter would silently clobber every other child
entry on any single edit. See Architecture Patterns §Pattern 2 below.

**Primary recommendation:** Build `KidContentCatalog`/`KidContentCopy` in `RithamCore` directly
from `docs/kid-content.md` (transcribe, do not re-research), add one new `ChildEntryRecord`
SwiftData model with per-entry CRUD on `HealthDataStore` (mirroring `PrivacyZoneRecord`), and add
one new Settings-reached sheet screen (mirroring `DietPlanView`) with no favoriting/tracking state
of any kind.

### Pattern 1: Settings-reached sheet screen (mirror `DietPlanView`/`WorkoutFrequencyView`)
**What:** A screen reached exclusively via `SettingsView`'s `.sheet(isPresented:)` (a plain
`@State private var isShowingKidIdeas = false` boolean), never pushed onto the app's one
`NavigationStack` (`OnboardingRootView` per CROSSGEN-05's structural rule) and never registered as
an `OnboardingStep`.
**When to use:** Any Settings-only sub-screen that is not part of the onboarding flow and is not a
health-screening section edit. `DietPlanView`, `WorkoutFrequencyView`, `MomentumTargetView`,
`MovementSnapshotToggleView`, and `PrivacyZonesView` all follow this shape today; `KidIdeasView`
should too.
**Example:**
```swift
// SettingsView.swift additions (mirrors the existing isEditingDietPlan / isEditingPrivacyZones state)
@State private var isShowingKidIdeas = false
// ... inside body, alongside the other SecondaryCTAButton rows:
SecondaryCTAButton(title: "Kid Ideas") {
    isShowingKidIdeas = true
}
// ... alongside the other .sheet(isPresented:) modifiers:
.sheet(isPresented: $isShowingKidIdeas) {
    KidIdeasView()
}
```
Note `KidIdeasView` needs no `flow: OnboardingFlow` parameter the way `DietPlanView` does —
`DietPlanView` needs `flow` only because it also edits the food-allergy *screening* answer
(`checklistBinding`, per its own header comment); `KidIdeasView` writes no screening data at all,
so it can take a plain `Environment(\.modelContext)` and construct its own `HealthDataStore`,
the same way `PrivacyZonesView` does.

### Pattern 2: Per-entry-identity CRUD for the multi-child record (mirror `PrivacyZoneRecord`, not `FoodAllergenRecord`)
**What:** `ChildEntryRecord` needs independent add/rename/delete per child, because D-07 requires
recording *more than one* child and editing them. `PrivacyZoneRecord`'s CRUD trio
(`savePrivacyZone`/`renamePrivacyZone`/`deletePrivacyZone`, each keyed by the entry's own `UUID`)
is the correct precedent — full-replace-the-whole-set patterns like `saveFoodAllergens`
(delete every existing row, reinsert the full incoming set) would silently delete every other
child entry whenever the parent edits or adds one.
**When to use:** Any preference that is a *list of independently-editable items* rather than a
single scalar or a single interchangeable set.
**Example:**
```swift
// ChildEntryRecord.swift -- new file, mirrors FoodAllergenRecord.swift's minimalism and
// PrivacyZoneRecord.swift's per-entry-UUID identity shape *exactly*, including its plain
// (non-unique-constrained) `id: UUID` field -- PrivacyZoneRecord.swift (read directly to confirm
// this) uses a plain `public var id: UUID`, not `@Attribute(.unique)`; identity/no-duplication is
// enforced by the store's fetch-by-id accessors below, the same way PrivacyZoneRecord's are, not
// by a SwiftData-level uniqueness constraint.
import SwiftData

// Per D-07 and CONTEXT.md's Claude's Discretion: no name, no age, no weight/growth/history field.
// The record's entire purpose is "this parent has recorded a preteen exists," nothing more.
// `nickname` is optional and user-editable; a nil value renders as an ordinal default
// ("Child 1", "Child 2", ...) computed at the view layer from creation order, never stored as
// a second source of truth for the ordinal position.
@Model
public final class ChildEntryRecord {
    public var id: UUID
    public var nickname: String?
    public var createdAt: Date

    public init(id: UUID = UUID(), nickname: String? = nil, createdAt: Date = Date()) {
        self.id = id
        self.nickname = nickname
        self.createdAt = createdAt
    }
}
```
```swift
// HealthDataStore.swift additions -- new "MARK: - Child entries" section, mirrors the existing
// "MARK: - Privacy Zones" section's *actual* three-method shape: a delete-then-reinsert `save`
// for create (mirrors `savePrivacyZone`), a lightweight in-place `rename` for editing just the
// nickname (mirrors `renamePrivacyZone`), and a `delete` that throws when nothing matches (mirrors
// `deletePrivacyZone`). Load-all is sorted by `createdAt` so ordinal labels ("Child 1", "Child 2")
// computed at the view layer stay stable across relaunches.
public func loadChildEntries() throws -> [ChildEntryRecord] {
    try context.fetch(FetchDescriptor<ChildEntryRecord>(
        sortBy: [SortDescriptor(\.createdAt, order: .forward)]
    ))
}

/// Full-replace on the matching identifier -- same discipline `savePrivacyZone`/
/// `saveCardioSession` use -- so a re-save can never leave a stale field behind. Used for adding
/// a brand-new child entry (caller mints a fresh `UUID`).
public func saveChildEntry(_ entry: ChildEntryRecord) throws {
    if let existing = try fetchChildEntryRecord(id: entry.id) {
        context.delete(existing)
    }
    context.insert(ChildEntryRecord(id: entry.id, nickname: entry.nickname, createdAt: entry.createdAt))
    try context.save()
}

/// Renames a stored entry's own nickname only -- never touches `createdAt` (which anchors its
/// ordinal position). Mirrors `renamePrivacyZone` exactly. Throws `childEntryNotFound` when no
/// stored entry matches `id`.
public func renameChildEntry(id: UUID, to nickname: String?) throws {
    guard let record = try fetchChildEntryRecord(id: id) else {
        throw HealthDataStoreError.childEntryNotFound // new case, mirrors .zoneNotFound
    }
    record.nickname = nickname
    try context.save()
}

/// Throws `childEntryNotFound` when no stored entry matches `id`, mirroring
/// `deletePrivacyZone`/`deleteCardioSession`'s "not found is an error, not a silent no-op"
/// discipline.
public func deleteChildEntry(id: UUID) throws {
    guard let record = try fetchChildEntryRecord(id: id) else {
        throw HealthDataStoreError.childEntryNotFound
    }
    context.delete(record)
    try context.save()
}

private func fetchChildEntryRecord(id: UUID) throws -> ChildEntryRecord? {
    let records = try context.fetch(FetchDescriptor<ChildEntryRecord>())
    return records.first { $0.id == id }
}
```
Register `ChildEntryRecord.self` in `RithamModelContainer.models`, in the same array every other
model is listed in.

### Anti-Patterns to Avoid
- **Paraphrasing source content "for readability":** D-01's entire point is verbatim transcription.
  An executor lightly editing a USDA tip's wording for flow breaks the citation discipline this
  whole codebase enforces for health-adjacent content (`NutritionGuidanceCatalog`'s own header:
  "transcribed verbatim... rather than paraphrased or generated").
- **A per-tag/per-condition switch statement:** Unlike `NutritionGuidanceCatalog`/
  `WorkoutGuidanceCatalog`, this content has no `ConditionTag` dimension at all — do not force this
  catalog into that shape just because it is the nearest precedent in the same directory.
- **Full-set replace for child entries:** See Pattern 2 above — `saveFoodAllergens`'s
  delete-then-reinsert-the-whole-set shape is the wrong precedent for a multi-entry, individually
  editable list.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Citing a source per content item | A new, bespoke citation struct from scratch | `NutritionGuidanceCatalog.ReferenceFigure`'s label/value/publishingBody shape as the model (or reuse it directly if its "value" field can stretch to "document identifier") | Already reviewed, already tested, already the established pattern reviewers (and eventually counsel/clinician per LAUNCH-02/03) expect to see for citation-bearing content in this codebase. |
| Storing a per-child record | A generic "profile" or "family member" abstraction | The minimal `ChildEntryRecord` in Pattern 2 above (id + optional nickname + createdAt only) | Any richer shape (age, birthdate, avatar, etc.) risks becoming identifying or health-adjacent data about a specific child, which is exactly what D-07 and the phase's own COPPA-avoidance reasoning forbid. |
| Content permission/gating for this screen | Wiring this content through `GuidanceCatalog.contentPermission(for:domain:)` the way `NutritionGuidanceCatalog`/`WorkoutGuidanceCatalog` do | Nothing — this content has no gate at all (see Architectural Responsibility Map) | This content is not personalized to the *user's own* condition tags; it's general preteen-facing content the parent opts into by recording a child exists. Building a fake gate here would be over-engineering against a requirement that doesn't exist. |

**Key insight:** This phase's only real engineering risk is over-building — reaching for the
nearest same-directory precedent (`NutritionGuidanceCatalog`'s per-tag switch, or a richer child
"profile" model) when a much flatter shape is what D-01 through D-09 actually call for.

## Common Pitfalls

### Pitfall 1: Defaulting to a new top-level dashboard section
**What goes wrong:** `HomeHubView` is this app's dashboard, and CROSSGEN-01 explicitly grew it
into "a real dashboard, not a vertical button list" with sections for every major feature
(exercise, sleep, diet plan, workout plan). An executor following that recent, strong precedent
could default to adding a "Kid Ideas" dashboard section out of habit.
**Why it happens:** CROSSGEN-01 is the most recently reinforced pattern in this codebase (7 rounds
of checkpoint feedback per `STATE.md`), so it's the most available mental model.
**How to avoid:** D-04 is explicit and locked: this is a nested Settings/Diet-Plan sub-screen, not
a dashboard section, specifically because not every user has a child. Route only through
`SettingsView` (or a link from `DietPlanView`), never `HomeHubView`.
**Warning signs:** Any new `HomeHubView` section, any new always-visible dashboard card for this
feature.

### Pitfall 2: A mandatory name field on the child entry
**What goes wrong:** The natural UI instinct for "add a child" is a name text field, matching how
most apps model a person.
**Why it happens:** No other precedent in this codebase for "record a person who is not the
account holder" exists to counter-model against.
**How to avoid:** CONTEXT.md's Claude's Discretion section flags this explicitly: default to
ordinal slots ("Child 1," "Child 2") with an *optional* short nickname field, never a required
name. A mandatory name field is a deviation that needs a beat of user confirmation before shipping,
not a default.
**Warning signs:** A `@Attribute` or form field labeled "Name" (rather than "Nickname (optional)")
on the child-entry editor.

### Pitfall 3: Adding any favorite/tried/viewed-state persistence
**What goes wrong:** `AlwaysFreeListView` and most list-of-items screens in consumer apps
naturally invite a "mark as done" or "save for later" affordance.
**Why it happens:** It's the default mental model for a browsable content list.
**How to avoid:** D-09 is explicit and locked: read-only, no interaction beyond viewing. No
favoriting, no "tried" marking, no per-idea saved state, on-device or otherwise — this is
deliberate, to avoid anything that could read as a child activity log.
**Warning signs:** Any new SwiftData field or record tracking per-idea interaction state.

### Pitfall 4: Reaching for `GuidanceCatalog.contentPermission(for:domain:)`
**What goes wrong:** Every other content catalog in `RithamCore/Sources/RithamCore/Guidance/`
gates its output through the shared permission-check function
(`NutritionGuidanceCatalog.presentableGuidance(for:)`, `WorkoutGuidanceCatalog
.presentableAdjustment(for:)`), so an executor copying that file's shape closely might wire this
catalog through the same gate reflexively.
**Why it happens:** It is the strongest, most consistent pattern in the directory this new file
lives in.
**How to avoid:** This content has no `ConditionTag` dimension and is never blocked by a Clearance
Gate — it is general preteen-facing content, unconditional on the parent's own screening answers.
Do not add a `domain` case, and do not call `contentPermission` anywhere in this catalog.
**Warning signs:** A new `.kidContent` (or similar) case appearing in `GuidanceCatalog`'s
`domain`/permission enums.

### Pitfall 5: Losing the exclusion note for the "keep an eye on the size" tip
**What goes wrong:** `docs/kid-content.md` §3 documents one source tip (from the same USDA
tipsheet the other nine snack tips come from) as *deliberately excluded* for conflicting with D-03.
An executor skimming the source tipsheet directly (rather than `docs/kid-content.md`) could
re-include it, not realizing it was already reviewed and rejected.
**Why it happens:** The excluded tip sits in the same official document as nine included ones, with
no obvious visual flag in the original PDF.
**How to avoid:** Transcribe only from `docs/kid-content.md` (already curated), not from the
original USDA PDFs directly. If a future content-catalog revision does go back to the primary
source, re-check every new tip against D-03 before including it, the same way this document's own
§3 did.
**Warning signs:** A tenth snack idea appearing in the catalog, or any idea text mentioning serving
size, "how much is enough," or portion control.

## Open Questions

1. **Is a dedicated USDA/CDC/AAP resource scoped specifically to ages 10-12 available, that this
   research pass missed?**
   - What we know: USDA's MyPlate materials segment by rough life stage (toddlers, kids, teens,
     adults) but not by a specific 10-12 band; CDC's Physical Activity Guidelines segment youth as
     one 6-17 band. AAP's HealthyChildren.org segments by "gradeschool" (roughly 5-11) and "teen"
     (roughly 12+), so a preteen at the 10-12 boundary spans both AAP site sections.
   - What's unclear: whether a tighter-fit resource exists that this research pass's WebSearch
     queries simply didn't surface (this is a WebSearch-based finding, not an exhaustive one).
   - Recommendation: ship with the current `docs/kid-content.md` sourcing (it is accurate and
     verbatim for the age range it covers); if the planner or a later reviewer finds a better-fit
     10-12-specific resource, treat `docs/kid-content.md` as a living document to extend, not
     replace — the excluded-tip discipline in §3 should carry forward to any addition.

2. **Should the "keep an eye on the size" tip (Assumption A2) actually be included, with a
   product-level caveat, rather than excluded outright?**
   - What we know: D-03's own wording ("no ... portion targets ... of any kind") is about targets,
     and this tip contains no numeric target.
   - What's unclear: whether "portion-awareness framing without a number" is still disqualified in
     the spirit of D-03, or whether only numeric targets are actually prohibited.
   - Recommendation: leave excluded per this research's conservative reading (documented in
     `docs/kid-content.md` §3); surface this specific judgment call during `/gsd-discuss-phase`
     follow-up or Phase 5 clinical review rather than resolving it unilaterally in code.

3. **Exact entry-point placement (Settings row vs. `DietPlanView` link) — CONTEXT.md leaves this to
   the planner.**
   - What we know: this file's Architecture Patterns recommend a sibling Settings row (matches
     CONTEXT.md's own stated default reasoning: "since the feature spans both food and movement,
     not diet alone").
   - What's unclear: nothing technically blocking either choice; this is a discoverability/UX call.
   - Recommendation: sibling Settings row, per CONTEXT.md's own stated leaning — no further
     research needed, just a planner decision to record.
