# Phase 04.2: Parent-facing kid ideas (food and movement content) - Context

**Gathered:** 2026-09-11
**Status:** Ready for planning

<domain>
## Phase Boundary

A single, read-only "Kid Ideas" screen inside the existing adult/parent Ritham account, offering
general, non-personalized food and movement ideas for **preteens (approximately ages 10-12)
only** — narrower than the original backlog framing ("under-13 child" generally). Toddler/
preschool/school-age content is explicitly out of scope for this phase.

The child never has a Ritham profile, login, or tracked data of their own. A parent may optionally
record one or more children as simple preteen-scoped entries (a persisted Settings-level
preference, not a tracked user) to personalize which ideas surface — nothing about a specific
child's weight, growth, or activity history is ever stored. This is parent-driven content on the
parent's own account, not a child user of the service — it does not reopen Ritham's permanent 13+
age floor (`PROJECT.md` Key Decisions, `01-CONTEXT.md` D-14/D-15) or raise a COPPA concern.

Needs the same dietitian/clinical sign-off discipline as SCOFF and the existing nutrition tables
before shipping (LAUNCH-02/03 precedent) — this phase satisfies that by transcribing content
verbatim from citable public health sources rather than authoring original tips (see Decisions
below).

</domain>

<decisions>
## Implementation Decisions

### Content sourcing (the phase's central constraint)
- **D-01:** Content is transcribed verbatim from well-known, citable public health sources — not
  originally authored. Candidate sources for the phase researcher to confirm and cite (final
  selection is the researcher's call, following `NutritionGuidanceCatalog.swift`'s existing
  citation discipline — every line traceable to a publishing body, no arithmetic, no individually
  computed figures):
  - USDA MyPlate for Kids (ChooseMyPlate.gov) for food ideas
  - AAP (American Academy of Pediatrics) nutrition guidance for children
  - CDC/HHS Physical Activity Guidelines for youth for movement ideas
- **D-02:** A new canonical source document, `docs/kid-content.md`, must be created capturing the
  transcribed content, categories, and any prohibited-content rules — mirroring
  `docs/dietary-pattern.md`/`docs/group-events.md`'s role for their phases. **This document does
  not exist yet.** Creating it (research pass: identify exact source passages, transcribe
  verbatim with citations, apply the standing product-wide prohibitions below) is a prerequisite
  the phase researcher must complete before the planner writes PLAN.md tasks — it is not optional
  background reading, it is a phase deliverable.
- **D-03 [locked, not re-litigated — standing product rule extended]:** No weight-loss framing, no
  calorie/macro/portion targets, no BMI, no weight-management content of any kind for the child —
  same standing prohibition `HEALTH-04`/`REQUIREMENTS.md` already applies to the app's own 13-17
  user (`Under 18 (Minor)` is `required-blocking` for any weight-management feature). This is food-
  variety and movement-idea content only, general education, never a quantity/target.
- Content ships as-is pending final legal/clinical review, same posture as
  `NutritionGuidanceCatalog`/`WorkoutGuidanceCatalog` (Phase 5 gates the review, not this phase's
  build) — flag to the researcher/planner that Phase 5's `LAUNCH-02`/`LAUNCH-03` scope may need to
  explicitly widen to cover this new pediatric content category; that's a `REQUIREMENTS.md` edit
  for whoever plans Phase 5, not a task for this phase.

### Entry point — no new dashboard section
- **D-04:** This is **not** a new top-level dashboard section (unlike Diet Plan/Workout Plan). It
  is reached from Settings (or nested from the existing Diet Plan screen) as a sub-screen, since
  not every user has a child — keeps the default dashboard uncluttered. The planner should decide
  the exact placement (new Settings row vs. a link from `DietPlanView`) — see Claude's Discretion;
  either is consistent with what was decided here.
- **D-05:** Food and movement ideas live in **one combined "Kid Ideas" screen** (not two separate
  sections) — matches the backlog's framing as one feature and avoids growing the app's section
  count.

### Child age input & scope
- **D-06 [narrowed 2026-09-11, confirmed with user]:** Scope is **preteens only** (~ages 10-12),
  not the full under-13 range the original backlog text implied. Toddler/preschool/school-age
  content and age-banding are out of scope for this phase — see Deferred Ideas. Because the scope
  is a single band, the age input is effectively a yes/no "I have a preteen" toggle rather than a
  multi-band picker — the researcher/planner should not build toddler/preschool/school-age bands
  "for future use"; that's new scope for a future phase if ever picked up.
- **D-07:** A parent can record **more than one child**, each scoped as a preteen entry, persisted
  as a Settings-level preference (survives relaunch, editable) — same durability tier as DIET-01's
  dietary-pattern preference. No child weight/growth/session-history field exists on any entry.

### Content format
- **D-08:** A **browsable idea library** — a list/grid of food and movement ideas the parent can
  revisit anytime — not a one-time education block (DIET-03's "shown once" pattern doesn't fit
  "ideas" framing as well as it fit nutrient-awareness disclaimers).
- **D-09:** **Read-only, no interaction beyond viewing** — no favoriting, no "tried" marking, no
  per-idea saved state. Deliberate: avoids building anything that could be read as a child activity
  log, staying clean against "nothing about a specific child is stored or tracked over time."

### Claude's Discretion
- Exact entry-point placement: a new Settings row named something like "Kid Ideas," or a link from
  within `DietPlanView` — both satisfy D-04; the planner picks based on what reads more discoverable
  once the UI is sketched. Since the feature spans both food and movement (not diet alone), a
  sibling Settings row is the more natural default, but this isn't a hard lock.
- Multi-child entry labeling: since no name/identifying data should be stored about a specific
  child (matches the COPPA-avoidance reasoning in the phase's own origin), default to generic,
  ordinal slots ("Child 1," "Child 2," optionally an editable short nickname) rather than a
  required full-name field. Flagged here because a name field would cut against "nothing about a
  specific child is stored" even though it wasn't explicitly asked about — planner should treat a
  mandatory name field as a deviation worth a beat of user confirmation, not a default to just build.
- Exact SwiftData/persistence record shape for child entries and the content catalog's internal
  structure — left to research/planning, following the existing `HealthDataStore` single-facade
  extension pattern and `NutritionGuidanceCatalog`'s `ReferenceFigure`-with-citation shape.
- Visual layout of the combined food/movement screen (tabs vs. two in-page groups) — no reference
  mockup given.

</decisions>
