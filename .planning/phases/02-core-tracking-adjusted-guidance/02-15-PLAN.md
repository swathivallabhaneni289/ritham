<objective>
Build strength training history: the pattern-filterable session list, year-jump date navigation, and
retroactive session editing including merge and split.

Purpose: STRENGTH-04 requires the auto-tagged movement pattern to be filterable in history and
progress; STRENGTH-05 requires full retroactive editing with date-picker and year-jump navigation
plus session merge and split. The pure domain operations and their identity-partition invariant were
built and unit-tested in plan 02-03, and the persistence path in plan 02-08 — this plan is the
surface over them and adds no revision arithmetic of its own.

This plan runs in Wave 4 because it builds on the strength logging screens plan 02-11 lands in
Wave 3, but it deliberately introduces its own editing screen rather than reusing the live logging
screen: retroactive revision and live capture are different concerns with different destructive
consequences, and separating them also keeps this plan's files disjoint from plan 02-12's.

Output: three new views, a rewritten strength-history registrar, and one new app-target test suite.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| retroactive edit → stored history | A revision rewrites already-recorded work; a defect destroys data the user cannot recover |
| filter selection → displayed history | An over-narrow filter can make present data look missing, which reads as data loss |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-09 | Tampering | `SessionEditView` merge and split | high | mitigate | Every revision delegates to the pure `SessionRevision` functions whose identity-partition invariant is proved in the domain suite, and persists through the single `applyRevision` write path; a screen-level test asserts the total stored set count is unchanged after a merge and after a split |
| T-02-43 | Tampering | destructive-action confirmation | high | mitigate | Merge and split require an explicit confirmation before writing, and abandoning it is a no-op asserted by a test, so an accidental tap cannot rewrite history |
| T-02-44 | Denial of Service | degenerate revision inputs | medium | mitigate | The domain functions' no-value returns are handled as refusals with an explanation, never falling through to an empty session; tests cover splitting at the first set and merging a session with itself |
| T-02-45 | Repudiation | set identity across an edit | medium | mitigate | Editing mutates field values on existing sets and never constructs fresh ones, so a set's identity — and therefore its superset membership and its place in any later revision — survives |
| T-02-46 | Denial of Service | filter empty states | low | mitigate | The no-results state and the empty-history state are distinct, so a working filter never reads as data loss |
| T-02-SC | Tampering | Swift Package Manager dependencies | low | accept | Zero third-party packages added. The legitimacy seam has no SPM support; a future SPM addition needs manual vetting behind a blocking human checkpoint |
</threat_model>
