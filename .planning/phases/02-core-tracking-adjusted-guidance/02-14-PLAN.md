<objective>
Add Phase 2's two Settings surfaces: the visible always-free capability list, and the weekly
workout-frequency preference.

Purpose: MONETIZE-01 requires the always-free list to be stated visibly in-app rather than held as
internal policy, and to match what is actually never paywalled elsewhere in the app. This phase and
Phase 1 introduce no paywall infrastructure of any kind, so everything shipped is free — what the
list must get right is naming only capabilities that genuinely exist in the build.
`02-CONTEXT.md`'s Claude's Discretion sets the weekly frequency as an editable Settings preference
following the same pattern the dietary-pattern preference already uses.

Scope note the executor must honour: MONETIZE-01's wording includes heart-rate display when a
device is paired. No wearable pairing exists in this build, and multi-wearable support is an
explicit v2 requirement rather than Phase 2 scope. The list therefore must not name heart-rate
display — claiming a capability that is not present would break the very property MONETIZE-01 asks
for, that the list match reality. Record that reasoning in the file so a later reviewer sees the
omission was deliberate and knows which requirement closes it.

Output: two new Settings screens, two new entry points on the existing Settings screen, and one new
app-target test suite.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| preference write → screening data | A preference must never become an input to, or a mutation of, clearance-gate state |
| in-app policy statement → user expectation | A published always-free list is a commitment a user relies on; overclaiming is a trust failure |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-25 | Elevation of Privilege | `WorkoutFrequencyView` | medium | mitigate | The write goes through the gate-isolated store accessor and the file references no gate, tag or screening symbol — asserted by a source-level criterion and by a test comparing stored tags and dietary pattern before and after the write |
| T-02-41 | Spoofing | always-free list content | medium | mitigate | The list names only capabilities present in this build, omits heart-rate display until wearable support ships, and carries an in-source record of that omission naming the requirement that closes it, so the list matches reality as MONETIZE-01 requires |
| T-02-42 | Tampering | frequency input | low | mitigate | Fixed-choice controls only, with no free-text or arbitrary numeric entry, so an out-of-range value the store would reject can never be submitted from this screen |
| T-02-SC | Tampering | Swift Package Manager dependencies | low | accept | Zero third-party packages added. The legitimacy seam has no SPM support; a future SPM addition needs manual vetting behind a blocking human checkpoint |
