<objective>
Surface condition-adjusted workout and nutrition guidance: inline at the moment a user logs or
plans a session, and on a dedicated guidance screen reachable from the hub.

Purpose: HEALTH-03 requires workout guidance to adjust the moment a user logs or plans a session,
with a blocking tag replaced by generic information and a referral and no other area of the app
restricted. HEALTH-04 requires nutrition guidance from published population-level figures only, with
zero personalized quantity under a blocking gate. DIET-02 requires dietary-pattern-keyed food-swap
examples where the gate permits food content, and DIET-03 requires nutrient-education blocks shown
identically regardless of any condition tag — including under a blocking gate.

Per `02-CONTEXT.md`'s Claude's Discretion, this reuses Phase 1's already-built and verified
disclaimer components rather than inventing a new pattern: the persistent condition disclaimer tag
and the required-blocking message card are embedded as-is.

This plan runs in Wave 4 because it edits the two session screens plans 02-10 and 02-11 create in
Wave 3 — that is what makes the guidance inline rather than a separate destination.

Output: a shared guidance context loader, a reusable inline banner, the dedicated guidance screen
with its nutrition section, a rewritten guidance registrar, and one new app-target test suite.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| stored condition tags → rendered guidance | Special-category health data selects safety-sensitive content; both over-showing and under-showing are defects |
| catalog → view layer | Views are untrusted with respect to gating; any direct catalog call from a view is a potential bypass |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Elevation of Privilege | `AdjustedGuidanceBanner`, `NutritionGuidanceSection` | high | mitigate | Every string comes from a catalog presentable accessor that resolves the content permission internally (ASVS V4); no view computes visibility from a gate value, and an acceptance criterion asserts the two session screens call no catalog directly |
| T-02-13 | Information Disclosure | `GuidanceContext` unscreened state | high | mitigate | A missing profile passes an empty tag list through to the resolver, which returns the zero-content permission, so an unscreened caller sees the referral message rather than full personalization |
| T-02-34 | Information Disclosure | age-based tag re-derivation | medium | mitigate | The context reads tags only via `activeConditionTags`, never the stored age, so expiry and the keep-applying-while-overdue rule cannot be bypassed by a second derivation (02-RESEARCH.md Pitfall 2); asserted by a source-level criterion |
| T-02-22 | Denial of Service | DIET-03 education block | medium | mitigate | The education block renders in its own view branch with no shared enclosing visibility condition, and a head-to-head test asserts it is present and identical under a blocking nutrition tag |
| T-02-35 | Elevation of Privilege | logging availability under a blocking gate | high | mitigate | No control on either session screen is gated on guidance state; tests assert a session can be started, finished and saved under a zero-content workout permission, enforcing HEALTH-06's domain-scoped-never-app-wide rule |
| T-02-36 | Spoofing | severe-allergen food content | medium | mitigate | The independent-verification notice accompanies every food-content surface when the severe-allergen tag applies, per the nutrition rule table's mandatory-every-time flag |
| T-02-SC | Tampering | Swift Package Manager dependencies | low | accept | Zero third-party packages added. The legitimacy seam has no SPM support; a future SPM addition needs manual vetting behind a blocking human checkpoint |
</threat_model>
