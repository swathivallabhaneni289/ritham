<objective>
Build the pure-Swift cardio session domain in `RithamCore`: the extensible activity-type
vocabulary, the session/progress/split value types, the accuracy-filtered distance accumulator,
and grade-adjusted pace with explicit elevation-confidence gating.

Purpose: CARDIO-01 and CARDIO-02 need a Foundation-only domain the app layer's CoreLocation /
CoreMotion adapters (plan 02-09) and the persistence layer (plan 02-08) can both target. Per D-02
this is a new `WorkoutSession`-family domain, deliberately separate from Phase 1's
`CalibrationSession`, but it references `CalibrationThreshold`'s constants for the shared
qualifying-session bar rather than restating them.

Output: four new `RithamCore/Cardio/` source files and three new test suites.
</objective>

  </read_first>
  <behavior>
    - A sample whose `horizontalAccuracy` exceeds the rejection threshold is discarded and contributes zero distance.
    - Two consecutive accepted samples 100 m apart 60 s apart accumulate 100 m of distance.
    - A sample implying an instantaneous speed above the plausibility ceiling is discarded and contributes zero distance.
    - Crossing 1000 m of accumulated distance emits exactly one `CardioSplit` with `index == 1`; crossing 2000 m emits a second with `index == 2`.
    - Accepted samples with poor `verticalAccuracy` leave `elevationConfidence` at `.low` while `horizontalConfidence` may still be `.high`.
    - Elevation gain accumulates only from positive altitude deltas, never from descents.
  </behavior>
  <action>
    Create `CardioTrackAccumulator.swift`, Foundation-only. Define a `LocationSample` value type
    (`latitude`, `longitude`, `altitudeMeters`, `horizontalAccuracyMeters`,
    `verticalAccuracyMeters`, `timestamp`) so the app-layer CoreLocation adapter in plan 02-09 can
    map a `CLLocation` into it without RithamCore ever importing CoreLocation.

    Define `CardioTrackAccumulator` as a struct with `private(set) var progress: CardioProgress`
    and a mutating `accept(_ sample: LocationSample) -> Bool` returning whether the sample was
    used. Filtering rules, in this order: reject when `horizontalAccuracyMeters` is negative or
    greater than a named `rejectionAccuracyMeters` constant (use 50 metres, the upper end of the
    30-50 m band 02-RESEARCH.md cites for pace-sensitive apps); reject when the implied speed
    between the previous accepted sample and this one exceeds a named
    `implausibleSpeedMetersPerSecond` constant (use 12.5 m/s, above elite running pace and below
    vehicle speed) — this is the V5 sanity bound, and a rejected sample must not become part of a
    split; otherwise accumulate great-circle distance via a private haversine helper (RithamCore
    cannot call `CLLocation.distance(from:)`), accumulate positive altitude deltas only into
    elevation gain, and update `progress`.

    Map horizontal confidence from `horizontalAccuracyMeters` and elevation confidence from
    `verticalAccuracyMeters` onto `SignalConfidence` through two separate named
    threshold-to-confidence functions — CARDIO-02 and 02-RESEARCH.md Pitfall 5 require these two
    signals be tracked independently, because iPhone vertical accuracy is materially noisier than
    horizontal.

    Emit a `CardioSplit` each time accumulated distance crosses a whole multiple of a named
    `splitDistanceMeters` constant (1000 m), with `averageSecondsPerKm` computed from the elapsed
    time and distance within that split only.

    Create `CardioTrackAccumulatorTests.swift` as a `@Suite` named `CardioTrackAccumulatorTests`
    covering every behavior above with synthetic samples (no sensor involvement).

  <behavior>
    - Zero grade returns the input pace unchanged.
    - A +5% grade returns a faster adjusted pace (a smaller seconds-per-km value) than the raw pace, because climbing at a given pace reflects more work.
    - A -5% grade returns a slower adjusted pace than the raw pace.
    - A -20% grade returns a pace less favourable than -10% does, reflecting the curve steepening past roughly -10%.
    - `adjustedSecondsPerKm` returns `nil` when `elevationConfidence` is `.unavailable` or `.low`, for every grade value including 0.
    - A non-positive input pace returns `nil` rather than a computed value.
  </behavior>
  <action>
    Create `GradeAdjustedPace.swift`, Foundation-only, as a `public enum GradeAdjustedPace`
    namespace with:

    `public static func gradePercent(elevationGainMeters:distanceMeters:) -> Double?` returning
    `nil` for a non-positive distance.

    `public static func adjustedSecondsPerKm(paceSecondsPerKm:gradePercent:elevationConfidence:) -> Double?`
    which returns `nil` whenever `elevationConfidence` is `.unavailable` or `.low`, and whenever
    `paceSecondsPerKm` is not positive. This nil-on-low-confidence rule is the whole point of the
    function per 02-RESEARCH.md Pitfall 5 — a caller must be structurally unable to render a
    grade-adjusted number computed from a noisy elevation signal, so there must be no overload,
    default argument, or sibling function that skips the confidence parameter.

    Implement the adjustment from the published Minetti-derived approximation 02-RESEARCH.md
    cites: an uphill cost factor of about 2.5% additional metabolic cost per 1% of positive grade;
    a downhill benefit of about 1.5% per 1% of negative grade down to -10%; and past -10% the
    benefit reverses and cost rises again (eccentric braking), so use a named constant for each of
    the three regime coefficients and the -10% inflection point rather than inline literals. Add a
    doc comment naming Minetti et al. (2002) as the grounding and stating explicitly that this is

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| device sensors → cardio domain | GPS/altimeter samples are untrusted numeric input crossing into recorded training data |
| cardio domain → displayed metrics | Derived numbers (pace, distance, grade-adjusted pace) are shown to a user who will act on them |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-03 | Tampering | `CardioTrackAccumulator.accept` | medium | mitigate | Reject samples above `rejectionAccuracyMeters` and above `implausibleSpeedMetersPerSecond` before they reach distance/splits (ASVS V5), so spoofed or glitched location data cannot silently inflate a recorded session |
| T-02-04 | Information Disclosure | `GradeAdjustedPace.adjustedSecondsPerKm` | low | mitigate | Return `nil` for `.unavailable`/`.low` elevation confidence and expose no confidence-free overload, so a noisy signal cannot be rendered as an authoritative figure (CARDIO-02) |
| T-02-05 | Repudiation | `CardioCaptureSource.isSensorVerified` | low | mitigate | Record capture provenance on every session so Phase 3's Momentum can distinguish manually entered from sensor-verified work without backfilling |
| T-02-SC | Tampering | Swift Package Manager dependencies | low | accept | This plan adds zero third-party packages (02-RESEARCH.md Package Legitimacy Audit: none proposed). `gsd-tools query package-legitimacy check` has no SPM ecosystem support, so any future SPM addition must be vetted manually behind a blocking human checkpoint; there is nothing to vet here |
</threat_model>
