<objective>
Create `RithamService`, the Go backend that generates workout plans, as a standard-library-only
module with one endpoint.

Purpose: D-06 makes new server-side logic run behind a Go API starting this phase, beginning with
workout-plan generation; D-07 requires the smallest data surface that still lets the backend do its
job, because whatever leaves the device widens LAUNCH-04's privacy-review scope beyond what Phase 1
assumed under local-first-only storage. This plan builds the service and its contract. The iOS
client that calls it is plan 02-13; nothing Swift is touched here, so this plan runs in parallel
with the whole of Wave 1.

Output: a new top-level `RithamService/` sibling directory alongside `RithamApp/` and
`RithamCore/`, with `go.mod`, one entrypoint, two internal packages, and their tests.

Scope discipline: D-06 records that this decision is driven by the project owner's job search
rather than a Ritham product requirement, and `02-CONTEXT.md` carries the owner's explicit
instruction to build it fast and keep it small. No framework, no router library, no Dockerfile, no
CI config, no deployment manifest, no auth infrastructure.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| iOS client → Go API | The first time any Ritham data leaves the device; everything crossing here widens LAUNCH-04's GDPR/CCPA review surface |
| network → handler | Untrusted, unauthenticated HTTP request bodies reach a decoder |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-02 | Information Disclosure | `httpapi.WorkoutPlanRequest` | high | mitigate | Accept exactly three coarse fields — a weekly frequency preference, a four-bucket experience category derived on-device, and the client's already-resolved three-value workout clearance gate — with no diagnosis-bearing data, no raw screening answers, no precise baseline numbers and no stable per-user or per-device identifier. Enforce with a reflection test asserting the field count and tag names, plus a decoder that rejects unknown fields (D-07) |
| T-02-15 | Denial of Service | `httpapi` handler and `http.Server` | medium | mitigate | Cap request body size before decoding and set explicit read, write and idle timeouts on the server, so a slow or oversized client cannot hold resources indefinitely |
| T-02-16 | Spoofing | unauthenticated endpoint | medium | mitigate | Bind the listener to `127.0.0.1` only, so the unauthenticated first-pass endpoint is unreachable from the local network. Authentication is deliberately not built (`02-CONTEXT.md`'s build-it-fast instruction) and is recorded in `main.go`'s header comment and the README as a prerequisite for any real hosting decision |
| T-02-17 | Tampering | JSON decode path | medium | mitigate | Every decode, generate and encode step has its own error check mapping to an explicit 4xx or 5xx status; type-mismatched and malformed bodies are covered by tests asserting a 400 rather than a panic (02-VALIDATION.md's Go handler row) |
| T-02-SC | Tampering | Go module dependencies | low | mitigate | `go.mod` declares no `require` block and an acceptance criterion asserts that, so the supply-chain surface is the Go standard library only. `gsd-tools query package-legitimacy check` supports npm, PyPI and crates only, so any future Go dependency must be vetted manually behind a blocking human checkpoint |
</threat_model>
