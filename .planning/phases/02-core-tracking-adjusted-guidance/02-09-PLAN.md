<objective>
Build the app-layer cardio capture adapters: the manual stopwatch, the first-class GPS tracking
session, and the CoreMotion auto-detect observer.

Purpose: CARDIO-01 requires a manual stopwatch for non-GPS sessions; CARDIO-02 makes GPS
pace/distance/elevation/splits a first-class feature with a visible confidence indicator;
CROSSGEN-02 requires passive-first capture from motion sensors alongside full manual configuration.
All three are new types, not refactors of Phase 1's calibration sensors — 02-RESEARCH.md Pattern 3
explains why the calibration source protocol's single completion-boolean shape does not stretch to
a live, multi-activity, multi-metric session.

Critical scope correction the executor must carry: `LocationEnrichment.swift`'s rule forbidding an
authorization request is scoped to calibration's no-blocking-prompt decision. It does not
generalize to Phase 2. Here GPS is the feature the user asked for, and requesting when-in-use
authorization at session start is expected and correct. What preserves the phone-only promise is
that the manual stopwatch path never depends on a permission decision — not a blanket ban on
prompting.

Output: three new `RithamApp/Ritham/Cardio/` types, two updated usage-description strings, and one
new app-target test suite.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| OS location/motion services → app | Sensor data and authorization state cross into the app from outside its control |
| app → user's location history | A GPS session records a precise breadcrumb trail, the most sensitive data this phase captures |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-28 | Information Disclosure | `GPSTrackingSession` location lifecycle | high | mitigate | Request when-in-use authorization only, never always authorization, never enable background location updates, and confine the single `startUpdatingLocation` call to the session-start path with a matching stop on end and pause — so no location stream can outlive a session the user started (02-RESEARCH.md Pitfall 4) |
| T-02-29 | Spoofing | user-facing purpose strings | medium | mitigate | Reword both usage descriptions so they describe Phase 2's actual use rather than the calibration walk; an acceptance criterion asserts the location string no longer references calibration, so consent is informed rather than stale |
| T-02-30 | Elevation of Privilege | `MotionActivityDetector` | medium | mitigate | The detector exposes no session-writing path at all — asserted by a source-level acceptance criterion — so a detection can only become a logged session through explicit user confirmation, honoring the no-silent-background-logging decision |
| T-02-31 | Denial of Service | permission-denied path | medium | mitigate | A denied or restricted location state falls back to `StopwatchCardioSession`, which imports no sensor framework, preserving the phone-only functionality promise; the manual path is never gated on a permission decision |
| T-02-03 | Tampering | sensor sample ingestion | medium | mitigate | All accuracy and plausible-speed filtering stays in the pure `CardioTrackAccumulator` this adapter feeds, so spoofed samples are rejected by unit-tested logic rather than by adapter code |
| T-02-SC | Tampering | Swift Package Manager dependencies | low | accept | Zero third-party packages added; CoreLocation and CoreMotion ship with the SDK. The legitimacy seam has no SPM support; a future SPM addition needs manual vetting behind a blocking human checkpoint |
</threat_model>
