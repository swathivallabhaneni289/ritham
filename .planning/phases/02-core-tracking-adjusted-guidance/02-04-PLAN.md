<objective>
Add the content-permission layer to `RithamCore` — the axis the existing three-level
`ClearanceGate` cannot express — plus the workout guidance text catalog transcribed from
`docs/health-screening.md` §2.

Purpose: HEALTH-03 requires workout guidance to adjust per applicable condition tag, with a
required-blocking gate replaced by generic information and a referral. `GateEscalation.swift`'s
own comment records that the gate enum has no narrower state than `requiredBlocking` to express
"no quantity, but generic education still allowed" — that nuance is content-layer. This plan
builds that layer and the workout half of its content. The nutrition half and the dietary-pattern
catalogs follow in plan 02-07, which depends on the types created here.

Output: two new `RithamCore/Guidance/` source files and one new test suite. Gating logic is read,
never rebuilt — `GateResolution` and `GateEscalation` are untouched.
</objective>

    - `.under18Minor` resolves to `.educationOnly` for `.nutrition` — §3 permits general movement and food-variety education while blocking every quantity.

  <action>
    Create `ContentPermission.swift`, Foundation-only. Define `ContentPermission` as a `Sendable`,
    `Equatable`, `Comparable`, `CaseIterable` enum declared in ascending permissiveness order:
    `none` (zero content of any kind — a blocking message and referral only), `educationOnly`
    (general, non-individualized education permitted; zero personalized quantities), `full` (this
    tag's full rule-table content). Mirror `ClearanceGate.swift`'s discipline exactly: provide a
    `static func mostRestrictive(_ permissions: [ContentPermission]) -> ContentPermission` and
    deliberately no averaging, blending or upgrading operation — the absence of such an API is the
    safeguard.

    Define `public enum GuidanceCatalog` with
    `public static func contentPermission(for tag: ConditionTag, domain: GuidanceDomain) -> ContentPermission`
    implemented as an exhaustive `switch` with one `case` per `ConditionTag` and one inline comment
    per case citing the §2 or §3 row it was transcribed from — the same shape and citation
    discipline `GateEscalation.baseGates(for:)` already uses. This lookup must be transcribed from
    the rule tables' prose independently for each tag, not computed from that tag's `ClearanceGate`
    value: §3 gives kidney disease, pregnancy-complicated and a positive eating-disorder screen
    zero content, while giving Under-18, hypertension-uncontrolled and postpartum-uncomplicated
    general education under the same gate level. Any formula over the gate enum would collapse
    those two groups together, which is the exact defect 02-RESEARCH.md's Pitfall 1 describes.

    Add `public static func resolvedPermission(for tags: [ConditionTag], domain: GuidanceDomain) -> ContentPermission`
    folding the per-tag permissions through `mostRestrictive`, and returning `.none` for an empty
    tag array. That empty-set behaviour answers 02-RESEARCH.md Open Question 5: a screened user
    always carries at least `.noneOfTheAboveBaseline`, so an empty set means the caller has no
    screening data and must be treated as unscreened, never as cleared.

    Create `GuidanceCatalogTests.swift` as a `@Suite` named `GuidanceCatalogTests`. Include a
    table-driven test iterating `ConditionTag.allCases` × `GuidanceDomain.allCases` asserting a
    permission is defined for every pair — the same every-case-covered discipline
    `ClearanceGateTests` already applies — plus one test per behavior listed above.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| condition tags → rendered guidance | Screening-derived health data selects which safety-sensitive text a user sees; a wrong selection is a safety defect, not a cosmetic one |
| catalog → view layer | Views are untrusted with respect to gating: any view able to reach personalized text without a permission check is a bypass |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Elevation of Privilege | `GuidanceCatalog.contentPermission` / `WorkoutGuidanceCatalog.presentableAdjustment` | high | mitigate | Resolve the content permission inside the catalog (ASVS V4) and expose a presentable accessor that returns the referral message under a `.none` permission, so a view-layer bug cannot render personalized intensity guidance past a required-blocking gate; raw row accessors carry a doc comment directing views to the presentable accessor and are covered by an exhaustive table-driven test |
| T-02-12 | Tampering | `ContentPermission.mostRestrictive` | high | mitigate | Provide only a never-lowering fold and no averaging, blending or upgrading operation, mirroring `ClearanceGate`'s structural safeguard, so HEALTH-06's most-restrictive-wins rule cannot be softened at the content layer |
| T-02-13 | Information Disclosure | empty-tag-set handling in `resolvedPermission` | medium | mitigate | An empty tag array resolves to `.none`, so a caller with no screening data is treated as unscreened rather than cleared (02-RESEARCH.md Open Question 5) |
| T-02-14 | Spoofing | guidance text provenance | medium | mitigate | Every string is transcribed verbatim from `docs/health-screening.md` §2 with the source cited in the file header, and string interpolation is absent, so no per-user or generated advice can enter the catalog (HEALTH-01) |
| T-02-SC | Tampering | Swift Package Manager dependencies | low | accept | Zero third-party packages added (02-RESEARCH.md Package Legitimacy Audit: none proposed). The legitimacy seam has no SPM support; a future SPM addition needs manual vetting behind a blocking human checkpoint |
