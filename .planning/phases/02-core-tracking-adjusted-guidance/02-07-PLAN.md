<objective>
Complete the guidance content layer: the nutrition text catalog transcribed from
`docs/health-screening.md` §3, and the dietary-pattern food-swap plus nutrient-education catalog
transcribed from `docs/dietary-pattern.md` §3 and §4.

Purpose: HEALTH-04 requires nutrition guidance built only from published population-level reference
figures, with a required-blocking gate showing zero personalized quantity of any kind. DIET-02
requires a dietary-pattern-keyed food-swap lookup that applies only where the nutrition gate
already permits food content. DIET-03 requires nutrient-awareness education blocks shown
identically regardless of any condition tag also present. Those last two have opposite gating
behaviour and 02-RESEARCH.md names conflating them as an anti-pattern — a single
hide-everything-when-blocked check would silently break DIET-03 for every user with any blocking
nutrition tag.

Output: two new `RithamCore/Guidance/` source files and two new test suites, built on the
`ContentPermission` type plan 02-04 created.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| condition tags → nutrition content | Screening-derived health data selects which nutrition text and figures a user sees; over-showing is a clinical-safety defect and under-showing breaks a requirement |
| catalog → view layer | Views are untrusted with respect to gating; any accessor returning gated content without a permission check is a bypass |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Elevation of Privilege | `NutritionGuidanceCatalog.presentableGuidance` / `DietarySwapCatalog.swaps` | high | mitigate | Resolve the nutrition content permission inside the catalog (ASVS V4) so a view cannot render personalized nutrition content or food examples past a zero-content permission; covered by an exhaustive table-driven test over every condition tag |
| T-02-21 | Information Disclosure | `NutritionGuidanceCatalog.referenceFigures` | high | mitigate | Every figure is a fixed transcribed string attributed to its publishing body, and the file contains no arithmetic at all — asserted by an acceptance criterion — so no figure can become an individually calculated number (HEALTH-04) |
| T-02-22 | Denial of Service | `DietarySwapCatalog.educationBlock` | medium | mitigate | The education-block accessor takes no condition tag and no gate parameter, making it structurally impossible for a later edit to suppress DIET-03 content behind a nutrition gate; asserted by a signature-level acceptance criterion and a head-to-head test |
| T-02-23 | Elevation of Privilege | weight-management availability | high | mitigate | `weightLossFeatureAvailable` delegates to the already-built `GateEscalation.weightLossFeatureGate` rather than reimplementing the under-18, positive-screen and below-floor checks, and is documented as the single correct entry point for whichever later phase adds goal setting |
| T-02-14 | Spoofing | guidance text provenance | medium | mitigate | Every string is transcribed verbatim with its source document cited in the file header and no string interpolation present, so no generated or per-user advice can enter either catalog (HEALTH-01) |
| T-02-SC | Tampering | Swift Package Manager dependencies | low | accept | Zero third-party packages added. The legitimacy seam has no SPM support; a future SPM addition needs manual vetting behind a blocking human checkpoint |
</threat_model>
